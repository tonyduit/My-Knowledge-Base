# 内存占用高分析

## Linux物理内存划分

### node划分

现在多cpu机器（非单cpu多核）一般是NUMA架构，如下，每一组cpu都有自己配套的内存，当cpu访问自己本地内存时速度较快，而访问其它cpu的内存，则速度较慢。

<img src="2.%E5%86%85%E5%AD%98%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image-20260310002837512.png" alt="image-20260310002837512" style="zoom:50%;" />

每一组**CPU + 内存**被称为一个节点node，因此，linux上内存首先按照node划分，然后按照node进行划分了之后，linux又会将每个node划分为多个zone

<img src="2.%E5%86%85%E5%AD%98%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image-20260310002914740.png" alt="image-20260310002914740" style="zoom:50%;" />

### zone划分

每个Node，又会划分为多个**Zone（区域）**。

1.**DMA**：地址段最低的一块内存区域，供IO设备DMA访问。

2.**DMA32**：用于支持32位地址总线的DMA设备，64位系统里才有效。

3.**NORMAL**： DMA与DMA32之外的内存，全部在NORMAL中。

<img src="2.%E5%86%85%E5%AD%98%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image-20260310002957711.png" alt="image-20260310002957711" style="zoom:50%;" />

linux中，zone划分情况可通过**/proc/zoneinfo**查看。

### 分页

Linux将区域中的内存划分成各种类型的页面管理，俗称**分页（page）**，页面之间**通过多种链表连接**。

1.空闲页（Free Page）

- **状态**：未被任何进程使用。
- **归属**：属于内核的空闲内存池（如 buddy system 管理）。
- **页表**：**没有任何虚拟地址映射到它**。
- **用途**：等待被分配。

2.匿名页（Anonymous Page）

- **状态**：**已被分配给某个进程**，用于存储数据（如堆、栈）。
- **归属**：属于某个进程的 VMA（类型为 anonymous）。
- **页表**：**有虚拟地址映射到它**。
- **内容**：可能是全零（刚分配时），也可能是用户写入的数据。
- **关键**：即使内容为空（全零），它**仍然是已分配的资源**，不能被其他进程使用。

3.文件页面（file）：已分配的文件关联的内存页面，比如文件缓存Cache与块缓存Buffers，如果页面被修改，称为**脏(dirty)页面**。

linux中，各个页面情况，也可通过**/proc/pagetypeinfo**查看，**/proc/meminfo**则是各个区域的汇总。

| 类型                  | 是否有 backing store？ | 说明                                                         |
| --------------------- | ---------------------- | ------------------------------------------------------------ |
| 文件页（File-backed） | ✅ 有                   | 内容来自磁盘文件（如 ELF 可执行文件、mmap 的普通文件）。如果页被换出，不需要额外保存，因为原始文件就是备份。 |
| 匿名页（Anonymous）   | ❌ 无                   | 没有对应的磁盘文件。例如 `malloc` 的堆、线程栈、`mmap(MAP_ANONYMOUS)`。如果要换出，必须分配 swap 空间 作为临时 backing store。 |

### Buffer与Cache

Linux中有两种类型的磁盘数据缓存，文件缓存Cache与块缓存Buffer。

1.**文件缓存Cache**：用于**缓存文件数据**的内存页面。

2.**块缓存Buffer**：用于直接**缓存块设备（磁盘）数据**的内存页面。

| **特性**           | **Cache (Page Cache)**                         | **Buffer (Buffer Cache)**    |
| ------------------ | ---------------------------------------------- | ---------------------------- |
| **面向对象**       | **文件 (File)**                                | **裸块/磁盘 (Block Device)** |
| **主要内容**       | 文件的具体内容                                 | 磁盘元数据、超级块、目录结构 |
| **数据单位**       | Page (通常 4KB)                                | Block (取决于硬件/文件系统)  |
| **常见场景**       | `cat` 一个大文件                               | `ls -R` 扫描大量目录         |
| **是否包含匿名页** | **不包含** (匿名页属于 `Active/Inactive Anon`) | **不包含**                   |

例如文件系统的超级块，inode索引块等，都是辅助文件存储的磁盘元数据，不属于文件数据，故不在文件缓存Cache中，单独计入块缓存Buffer中。

**超级块 (Superblock)：**

- **地位：** 文件系统的“总纲”。
- **内容：** 记录文件系统的整体信息，比如：文件系统类型、总块数、空闲块数、Inode 总数、挂载时间等。
- **重要性：** 如果超级块损坏，操作系统就不知道如何读取这个分区。

**目录结构 (Directory Structure)：**

- **定义：** 在 Linux 中，“目录也是一种文件”。
- **内容：** 它存储的是一张映射表，记录了“文件名”与“Inode 号”的对应关系。

**举个例子：**

1. 内核想找 `/home/user/a.txt`。
2. 它先从磁盘读取包含该目录信息的“块”。
3. 这个“原始块”的数据会放在 **Buffer** 里。
4. 内核解析这个 Buffer 里的二进制数据，提取出信息，然后在内存里创建一个 `struct dentry` 对象放在 **Slab** 中。

网上有一种说法，Buffer是写缓冲，Cache是读缓存，这种说法是错误的，**Buffer与Cache都涵盖了读和写操作**。

### slab

slab是Linux基于对象的一种内存分配机制，类似于**对象池**的概念，Linux系统会选一些**匿名页**给slab使用，当Linux需要一个内核对象时，如果**slab(对象池)**中有，就可以直接获取对象，而不用申请内存块。

linux中，slab占用情况可通过**/proc/slabinfo**或**slabtop**查看，有些slab可回收，有些不能回收

<img src="2.%E5%86%85%E5%AD%98%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image-20260310003616552.png" alt="image-20260310003616552" style="zoom:50%;" />

#### 什么是“内核对象”？

当内核工作时，它也需要在内存中创建各种“数据结构”来记录信息。这些数据结构就叫 **内核对象**。

举几个例子：

| 内核对象      | 作用                                                         |
| :------------ | :----------------------------------------------------------- |
| `task_struct` | 描述一个**进程**的信息（比如 PID、状态、打开的文件等，即该进程的寄存器上下文信息） |
| `inode`       | 描述一个**文件**的元数据（比如大小、权限、在磁盘的位置）     |
| `dentry`      | 描述一个**目录项**（比如 `/home/user/file.txt` 中的 `file.txt` 这个名字和对应的 inode 的关系） |
| `mm_struct`   | 描述一个进程的**内存布局**（虚拟地址空间怎么划分）           |

> 🔍 这些都是 C 语言定义的结构体（struct），每个都有固定的大小（比如 512 字节、1KB 等）。

**关键点**：

这些对象**数量多、频繁创建/销毁**。比如你每打开一个文件，内核就要创建一个 `inode` 和 `dentry`；你每启动一个程序，就要创建一个 `task_struct`。

#### 什么是“页”（Page）？

- 内存不是按字节管理的，而是按**固定大小的块**来管理。
- 在 Linux 中，**一页 = 4096 字节（4KB）**。
- 所有内存分配最终都要基于“页”来操作。

#### 什么是“页分配器”？

- 内核有一个底层机制，专门负责分配**整页**的内存，叫做 **伙伴系统（Buddy System）**。
- 它只能分配 **1页、2页、4页……** 这种 2 的幂次大小的连续物理内存。
- 它**不关心你要放什么数据**，只管给你一块干净的“空白页”。

> ⚠️ 问题来了：
> 如果我只需要 **200 字节** 来放一个 `dentry`，但页分配器最小只能给 **4096 字节（1页）**，那剩下的 3896 字节就浪费了！这叫 **内部碎片**。

#### 什么是“内存碎片”？

内存碎片分两种：

**1.内部碎片（Internal Fragmentation）**

- 你申请了 200 字节，系统给了你一整页（4096 字节）。
- 但你只用了 200 字节，剩下的 3896 字节**不能给别人用**（因为属于你这个分配）。
- **浪费了内存空间**。

**2.外部碎片（External Fragmentation）**

- 内存中有许多小块空闲区域（比如 1KB、2KB），但没有一个**连续的大块**。
- 当你需要分配 4KB 时，虽然总空闲内存够，但找不到连续的 4KB → 分配失败。
- **看起来有内存，却用不了**。

> 💡 频繁地向页分配器申请小对象，会同时导致 **内部碎片（浪费） + 外部碎片（难分配）**。

#### slab的作用

**如果不用 Slab，会发生什么？**

假设每次要创建一个 `inode`（512 字节），都直接调用页分配器：

```
第1次：申请1页（4096B） → 放1个 inode（512B） → 浪费 3584B
第2次：再申请1页 → 放1个 inode → 又浪费 3584B
...
第1000次：浪费近 3.5MB！
```

而且：

- 每次都要初始化 `inode` 结构（清零、设默认值）→ **慢**
- 释放时直接把整页还回去 → 下次又要重新申请+初始化 → **效率低**

**Slab 是怎么解决这个问题的？**

Slab 的核心思想就一句话：

> **“一次性多拿几页，切成小块，做成‘对象池’，反复使用。”**

具体做法：

1. 第一次需要 `inode` 时：
   - Slab 向页分配器申请 **1 页（4096B）**
   - 把这一页切成 **8 个 512B 的槽位**（因为 4096 ÷ 512 = 8）
   - 每个槽位可以放一个 `inode`
   - 把这 8 个槽位串成一个“空闲链表”
2. 分配 `inode` 时：
   - 直接从空闲链表拿一个槽位 → **不用申请新页！**
   - 如果之前用过，可能已经初始化好了 → **不用重复初始化！**
3. 释放 `inode` 时：
   - 不还给页分配器，而是**放回空闲链表**
   - 下次分配直接复用
4. **只有当整个页都空闲很久了**，才考虑还给页分配器（可选）

> ✅ 效果：
>
> - 内存利用率高（几乎没有内部碎片）
> - 分配/释放极快（O(1) 时间）
> - 减少对底层页分配器的调用 → 避免外部碎片

### free内存指标解释

![image-20260309192824717](2.%E5%86%85%E5%AD%98%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image-20260309192824717.png)

**Mem行**：

- total：总内存大小
- used：使用中的anon内存大小
- free：空闲内存大小
- shared：共享使用的内存大小
- buffers：用于块设备缓存Buffer的内存大小
- cache：用于文件缓存Cache与**slab**的内存大小
- available：可用内存大小，约等于free+buffers+cache

**Swap行**：

- total：你在磁盘上划定的交换分区/文件的**总大小**。
- used：当前**已经**从anon页内存中换出（Swap out）并存储在磁盘上的数据大小。
- free：当前交换分区（Swap Space）中还有多少空闲的磁盘空间。

## Linux虚拟内存划分

linux为隔离各个进程的内存空间，实现了虚拟内存机制，使得每个进程都有单独的虚拟内存空间，同时，为了方便管理，将虚拟内存空间划分成了多个区域(段）。

```batch
高位地址
+---------------------+
|       内核空间       | ← 所有进程共享，也包含内核程序自己的代码段、数据段、内核栈（每个进程私有）、内核堆、内存映射区
+---------------------+
|        ...          |
|        ...          |
|        ...          | ← 非常大的空隙（即未被映射的虚拟内存地址）
|        ...          |
|        ...          |
+---------------------+
|   主线程栈 (Stack)   | ← （高地址，向下增长）
+---------------------+
|        ...          | ← 随机空隙（可能几百 MB 到几 GB）
+---------------------+
|  内存映射段 (mmap)   | ← mmap 区域（如动态库、mmap 分配、非主线程栈）（多个不连续的 VMA）
+---------------------+
|        ...          |
|        ...          | ← 更大的随机空隙
|        ...          |
+---------------------+
|      堆 (Heap)      | ← 向上增长（由 brk/sbrk 管理）
+---------------------+
|  数据段 (.data/.bss) |
+---------------------+
|   代码段 (.text)     |
+---------------------+
低位地址
```

虚拟内存区域划分：

栈(Stack）: 存储线程运行的栈数据，向下生长

内存映射段：**通过 `mmap()` c语言库函数（底层是mmap()系统调用）动态映射内存或文件**

堆(Heap)： 进程堆内存区域，

- 对于小块内存扩容，通过`brk()`系统调用向上扩展大小
- 对于大块内存扩容，通过`mmap()`系统调用在`mmap段`创建新的VMA

数据段(.data)：存储C等程序中的常量等

代码段(.text）：存储C等程序中的程序指令

### **VMA是什么？**

所属空间

用户进程虚拟地址空间的逻辑描述（内核数据结构）

VMA的作用

描述一段连续虚拟地址的属性：

- 起止地址
- 读写/执行权限
- 是否映射文件（file-backed）还是匿名（anonymous）
- 是否可共享、是否在 swap 中等等

按“区域”（region）来划分，比如 **mmap 段内部映射的一个区域、堆、栈各是一个 VMA**；

进程创建时就建立（如代码段、堆、栈的 VMA），即使页尚未分配；

内核（`mm_struct` 中的 `mmap` 链表或红黑树）负责维护VMA。

举例：

```batch
虚拟地址 0x400000 ～ 0x401000 （程序代码段）
  └─ 对应一个 VMA：file-backed, read-execute, mapped to /bin/ls
        ↓
当 CPU 访问 0x400123 时：
  → MMU 查页表 → 发现 PTE 无效 → 触发 page fault
  → 内核查 VMA：知道这段属于 /bin/ls 的 offset X
  → 分配物理页，从磁盘读数据，填入页表
  → 下次访问直接通过页表翻译
```

### 堆、栈和 mmap 段：它们是怎么扩容的？

这是最关键的部分。**堆、栈、mmap 段虽然都在同一个虚拟地址空间里，但它们的扩容逻辑并不完全一样。**

**① 堆段 (Heap) 的扩容**

堆通常位于进程空间的低地址向上增长。

- **小额申请**：通过 `brk` 系统调用，直接抬高堆顶指针。内核会直接修改原有堆 VMA 的 `vm_end`。
- **大额申请**：当 `malloc` 申请超过阈值（默认 128KB）时，它**不再操作堆段**，而是改用 `mmap` 系统调用。
- **结论**：堆的扩容**不一定**在 mmap 段，只有申请大内存时才会“跑”到 mmap 段去开辟新领地。

**② 栈段 (Stack) 的扩容**

栈位于高地址向下增长。

- **自动扩容**：栈的 VMA 有一个特殊的标志位 `VM_GROWSDOWN`。
- **触发机制**：当程序进入深层递归导致栈溢出时，会触发缺页异常。内核发现地址紧挨着栈 VMA 的边界，就会自动把栈 VMA 的 `vm_start` 调低，实现自动扩容。
- **结论**：栈在自己的专属 VMA 区域扩容，**不占用 mmap 段**。

**③ mmap 段 (Memory Mapping Segment)**

这是进程空间中最大的一块“自由区”，位于堆和栈之间。

- **扩容方式**：当你调用 `mmap()`（无论是加载 `.so` 库，还是 `malloc` 申请大内存，或是 `MAP_ANONYMOUS`），内核都会在这一区域寻找一块足够大的空闲地址，并**创建一个全新的 VMA**。
- **结论**：mmap 段的“扩容”其实是** VMA 数量的增加**和空闲空间的消耗。

| **区域**       | **扩容方式**              | **是否在 mmap 段？** | **增长方向**               |
| -------------- | ------------------------- | -------------------- | -------------------------- |
| **栈 (Stack)** | 缺页异常自动扩展 VMA 边界 | **否**               | 向下 (低地址)              |
| **堆 (Heap)**  | `brk` 修改 VMA 边界       | **否** (仅限小内存)  | 向上 (高地址)              |
| **mmap 段**    | `mmap` 创建新的独立 VMA   | **是**               | 随机/向下 (取决于内核版本) |

### **mmap()与brk()两种系统调用的区别**

**1. brk()：堆的“边界推移器”**

`brk` 是最传统的内存分配方式，它直接操作的是进程的 **堆段（Heap）**。

- **工作原理**：堆在内存布局中是一块连续的区域。`brk` 通过移动一个名为 `program break` 的指针来扩大或缩小堆。
- **分配方式**：它是**顺序连贯**的。就像拉伸皮尺一样，你想要更多内存，就把指针往高处推，**抬高堆顶**。
- **回收限制**：由于是连续的，`brk` 必须遵循“后进先出”。如果你在堆底释放了一块内存，但堆顶还有数据，导致堆底的虚拟内存无法弹出释放，这块空间无法直接还给内核（只能由 `malloc` 库留作复用），这会导致**内存碎片**。

**“后进先出”与内存碎片的真相**

为什么说 `brk` 释放内存有局限性？想象堆是一根可以拉伸的“橡胶管”：

1. **申请内存 A, B, C**：你依次调用 `malloc` 申请了三块内存。`brk` 指针被推到了 C 的上方。此时，堆顶在 C 的位置。
2. **释放内存 A**：你调用 `free(A)`。此时，由于 A 处于“堆底”（靠近低地址），而它上方还有 B 和 C 压着，`brk` 指针**无法向下移动**。
3. **结果**：A 原本占用的物理内存虽然可以被内核回收，但 **A 占用的虚拟地址空间**依然被包裹在堆里。内核认为这块地还是你的，`malloc` 库只能把它标记为“空闲”，等下次你要申请小内存时再塞给别人。

**这就是“无法直接还给内核”的意思**：虚拟地址空间没有缩减，只有当处于**堆顶**（最高地址）的 C 被释放时，`brk` 指针才能安全地向低地址回退，真正把这块“地皮”还给系统。

**2. mmap()：内存的“灵活布局者”**

`mmap` 则是在进程空间的 **mmap 映射段**（通常在堆和栈之间）寻找空闲区域。

- **工作原理**：它不依赖堆指针，而是在虚拟地址空间中寻找一块足够大的空闲区域，建立一个新的 **VMA**（虚拟内存区域）。
- **分配方式**：它是**离散**的。每次 `mmap` 申请的内存块在虚拟地址上可能互不相连。
- **独立回收**：每一块 `mmap` 分配的内存都有独立的 VMA。当你调用 `munmap` 时，这块内存可以**立即归还给内核**，不受其他内存块的影响。

| **特性**       | **brk()**                        | **mmap()**                                  |
| -------------- | -------------------------------- | ------------------------------------------- |
| **操作对象**   | 堆段 (Heap)                      | mmap 映射段                                 |
| **内存连续性** | 必须连续                         | 可以是离散的碎片化区域                      |
| **分配开销**   | **低**。只需移动指针，开销极小。 | **高**。内核需搜索空闲地址、创建/维护 VMA。 |
| **回收机制**   | 只能从顶部缩小 (容易产生碎片)    | 可以随时释放任意一块内存                    |
| **典型用途**   | 小块内存分配 (默认 < 128KB)      | 大块内存分配、文件映射、共享内存            |

###  为什么 malloc 要混用brk()和mmap()？

现代 `malloc`（如 Glibc）会根据申请的大小自动切换策略，这被称为 **阈值机制（M_MMAP_THRESHOLD）**：

1. **小块内存 (< 128KB)**：使用 `brk`。
   - 原因：小内存申请非常频繁，如果每次都用 `mmap` 去创建 VMA 并引发内核搜索，系统调用开销太重。通过 `brk` 快速推指针，然后在用户态由 `malloc` 自己切分管理更高效。
2. **大块内存 (≥ 128KB)**：使用 `mmap`。
   - 原因：大块内存如果放在堆里，一旦不释放（或者被堆顶挡住），会造成严重的内存空洞。用 `mmap` 可以保证这块大内存用完后能立刻还给系统。

### **内存映射段使用流程**

**进程通过 `mmap()` 向内核“申请”一块虚拟地址范围，并指定它要映射什么（匿名内存 or 文件）。**

- 内核会在 **内存映射段的空闲区域** 中找一块合适的虚拟地址（比如 `0x7f1234000000`），建立 VMA（`vm_area_struct`），并返回给用户。
- **物理内存是按需分配的**：只有当程序真正访问这块虚拟内存时（触发缺页异常），内核才分配物理页框，内核：
  1. 查看该虚拟地址对应的 VMA → 发现是 `MAP_ANONYMOUS`匿名映射
  2. 从 **空闲页链表** 中取一个物理页框
  3. 清零该页
  4. 在页表中建立 **虚拟页 → 物理页** 的映射
  5. 继续执行

内存映射段内存分配并不是有序的，而是分配到多个独立的VMA区域

**mmap段只有两种映射：**

在 `mmap`段 的世界里，内存映射分为两大类：

- **文件映射 (File-backed Mapping):** 将虚拟地址映射到磁盘文件（如数据库文件、共享库 `.so`）。读写这块内存等同于读写磁盘文件。
- **匿名映射 (Anonymous Mapping):** 也就是设置了 `MAP_ANONYMOUS`。它不关联任何文件。当你访问它时，内核分配的物理页被称为**匿名页 (Anonymous Page)**。

### 页表是什么？

所属空间

CPU 硬件用于地址翻译的结构（软硬件协同）

页表的作用

将虚拟地址 → 物理地址逐页映射，供 MMU 硬件查表；

每个页有独立的页表项（PTE）；

页表项在缺页异常发生后才填充（按需分页，demand paging）；

内核 + MMU 硬件（内核设置，硬件使用）负责维护页表。

### MMU是什么？

| 组件                          | 职责                                                         |
| ----------------------------- | ------------------------------------------------------------ |
| 操作系统内核                  | 分配和管理页表（`pgd`, `pud`, `pmd`, `pte` 等多级结构），设置页表项内容（物理页帧号、权限位等） |
| 主存（RAM）                   | CPU 可直接通过地址总线访问的、**易失性**的半导体存储器。用于存储完整的多级页表结构 |
| MMU（Memory Management Unit） | 接收 CPU 发出的虚拟地址根据 CR3 寄存器（指向当前进程的页目录基址）遍历页表将虚拟地址转换为物理地址利用 TLB（Translation Lookaside Buffer） 缓存最近用过的页表项，加速转换 |

**关键点：**

- MMU **不存储页表**，它只是“查表引擎”，类似于DNS解析。
- 页表本身是普通内存，由内核动态维护，相当于权威DNS服务器。
- TLB 是 MMU 内部的**高速缓存**，缓存的是“虚拟页号 → 物理页帧号”的映射，相当于本地Host文件。
- 当页表被修改（如缺页处理后更新 PTE），必须**刷新 TLB**（或让对应项失效），否则 MMU 会用旧映射。

✅ 所以：**页表在 RAM 中，MMU 用 TLB 缓存部分映射，加速地址转换**。

## Linux物理内存分配

### 缺页中断

进程通过brk/mmap申请虚拟内存时，linux并未给其实际分配物理内存，直到当 CPU 通过 MMU 访问一个虚拟地址，但该地址对应的页表项标记为“不存在”（Present=0）时，MMU 会触发一个 **PF（Page Fault）异常**，内核为进程分配实际的物理内存页框。

minor faults：轻微缺页，缺页中断分配物理内存页面后，不需要从磁盘或swap中加载数据到内存页。

major faults：严重缺页，缺页中断分配物理内存页面后，还需要从磁盘或swap中加载数据到内存页。

**轻微缺页**：所需数据**已在物理内存中**（可能是文件页或匿名页），只需建立映射。
**严重缺页**：所需数据**不在内存中**，需**分配一个空闲物理页帧**，**从磁盘读取数据填入**，再建立映射。

### 内存回收

缺页中断会在空闲内存页链表中查找可分配的物理内存页，若**空闲内存不足**，可能会触发linux的**内存回收机制**，linux为空闲内存设置了high，low，min这三个水位，以确定内存回收的时机，如下：

1.**high水位**：安全水位，直接分配内存

2.**low水位**：当空闲内存低于low时，说明内存开始不足了，分配内存后，会唤醒**kswapd内核线程异步回收内存**，直到内存回收到high水位。

3.**min水位**：当空闲内存低于min时，说明内存严重不足了，这时会**同步等待**回收内存完成，然后再分配内存，这种叫`direct reclaim`。 

通过**vm.watermark_scale_factor**内核参数，可调整内存水位之间的差值，通过**grep -E 'pageoutrun|allocstall'  /proc/vmstat**可观察`kswapd`和`direct reclaim`运行次数。

![image-20260309220849513](2.%E5%86%85%E5%AD%98%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image-20260309220849513.png)

linux会根据配置和页面类型，去已分配的页面链表中找到合适的可回收页面，各种页面的回收动作如下：

1.**anon  page**：若开启了swap，会将数据swap到磁盘后，物理内存页放入到空闲链表。（**不开启swap，匿名页就无法被回收**，除非他的进程被杀了）

2.**file  page(clean)**：直接回收，然后放入空闲链表。# 文件页（干净的文件页）

3.**file  page(dirty)**：先将内存数据同步到磁盘后，然后放入空闲链表。# 文件页（被修改过的脏页）

linux通过**vm.swappiness内核配置**，决定回收多少anon  page和file page，**值越大，回收anon page比例越大**，swappiness=1表示尽量不回收anon  page，swappiness=100时，回收一样多的anon  page与file  page。

<img src="2.%E5%86%85%E5%AD%98%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image-20260310002738037.png" alt="image-20260310002738037" style="zoom:50%;" />

若内存回收过程中，没有`anon page`或`file page`可以回收了，这时会启用**`OOM Killer`**杀掉进程来释放内存，OOM killer会根据各进程的内存占用情况，进程优先级来对进程打分，找出打分高的**bad process**来Kill。

**可通过choom命令来调整进程OOM优先级配置**，以避免重要进程被kill。

<img src="2.%E5%86%85%E5%AD%98%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image-20260310004812322.png" alt="image-20260310004812322" style="zoom:50%;" />

**问题：关闭了swap，是否意味着缺页中断不会有磁盘io？**

不一定，如果内存分配时，空闲内存不足，这时会触发内存回收，这种情况下，如果**回收了脏页(dirty page)**，需要先将脏页数据**同步到磁盘**，然后才能回收。

对于开启swap场景的内存分配，最坏情况可能会有3种磁盘io产生：

- anon page被回收，内存数据**swap out**到磁盘。
- dirty page被回收，内存数据**sync**到磁盘。
- 程序正要访问某个匿名页之前，该页被swap out了，进程在访问的时候会产生major faults（严重缺页），需要**swap in**磁盘数据到分配的内存页。或是用mmap()把文件映射到了内存，但是进程在访问的时候发现没有物理内存，这时候也会触发严重缺页，需要**load**磁盘数据到分配的内存页中。

## 总结

### **Linux物理内存划分**

**分节点、分区、分页**

在多个CPU的系统中，Linux将每一组**CPU + 内存**划分为一个节点node，每个node有分为3个区域：DMA（供io设备访问使用）、DMA32、Normal，只需要重点关注Normal区即可，Normal区中的物理内存页帧又分为3种：

- 空闲页：没有被使用的页
- 匿名页：已经被分配给进程的页（**可被swap交换到磁盘**）
- 文件页：已被分配的，与文件有关的页（如果页面被修改，则该页是**脏页**）

这些页之间通过链表连接。

**buffer/cache、slab**

Linux中有两种类型的磁盘数据缓存，文件缓存Cache与块缓存Buffer。

1.**文件缓存Cache**：用于**缓存文件数据**的内存页面。

2.**块缓存Buffer**：用于直接**缓存块设备（磁盘）数据**的内存页面。

slab是Linux的一种内存分配机制，相当于维护了一个**“内核对象池”**，当需要对象时可以直接去slab中，从而避免了创建和销毁对象的开销以及频繁像内存分配器申请小对象场景下导致的内部（浪费空间）与外部（难分配）内存碎片问题。

### **Linux虚拟内存划分**

**虚拟内存区域划分**

栈(Stack）: 存储线程运行的栈数据，向下生长

内存映射段：**通过 `mmap()` c语言库函数（底层是mmap()系统调用）动态映射内存或文件**

堆(Heap)： 进程堆内存区域

- 对于小块内存扩容，通过`brk()`系统调用向上扩展大小
- 对于大块内存扩容，通过`mmap()`系统调用在`mmap段`创建新的VMA

数据段(.data)：存储C等程序中的常量等

代码段(.text）：存储C等程序中的程序指令

### **Linux虚拟内存分配**

JVM等原生应用程序调用的malloc()、free()函数，实际是由基础C库libc提供的，而linux系统则提供了`brk()、mmap()`等系统调用来分配虚拟内存，所以libc的`malloc()、free()`函数实际是基于这些系统调用实现的。

### **Linux物理内存分配**

**缺页异常**

Linux在给进程建立VMA分配虚拟内存时，并没有将物理内存映射上去，只有当CPU通过MMU访问到那块虚拟地址了，发现该地址对应的页表项不存在，MMU会触发缺页异常，内核才会给对应的虚拟内存页分配物理内存页帧。

- **轻微缺页**：所需数据**已在物理内存中**（可能是文件页或匿名页），只需建立映射。
- **严重缺页**：所需数据**不在内存中**，需**分配一个空闲物理页帧**，**从磁盘读取数据填入**，再建立映射。

**内存回收**

若Linux系统**空闲内存不足**，可能会触发linux的**内存回收机制**，linux为空闲内存设置了high，low，min这三个水位，以确定内存回收的时机，

1. **high水位**：安全水位，直接分配内存
2. **low水位**：当空闲内存低于low时，说明内存开始不足了，分配内存后，会唤醒**kswapd**内核线程**异步**回收内存，直到内存回收到high水位。

通过**vm.watermark_scale_factor**内核参数，可调整内存水位之间的差值，通过**grep -E 'pageoutrun|allocstall'  /proc/vmstat**可观察`kswapd`和`direct reclaim`运行次数。

对于不同种类的物理内存页，回收方式是不同的：

- 对于匿名页：若开启了swap，会将数据swap到磁盘后，物理内存页放入到空闲链表。
- 对于干净的文件页：直接回收，将页放入空闲链表。
- 对于脏文件页：先将该页的数据同步到磁盘中，再将页放入空闲链表。

**受控领土（逻辑划分）：**

- **Java 堆** ≈ **Go 堆**（存对象）。
- **Thread Stack** ≈ **Goroutine Stack**（存调用栈）。注意：所有的 Goroutine 栈空间在物理上都是从 Go 的“堆（Heap）”中分配出来的匿名内存，而 M（系统线程）拥有的才是真正的原生栈。
- **MetaSpace** ≈ **Type Metadata**（存程序结构定义）。

**非受控/外部领土：**

- **JNI malloc / DirectBuffer** ≈ **Cgo malloc / mmap**。

### 先判断：**进程/内核哪个占用多？**

**内核内存的其他重要组成部分**

除了 Slab，内核态的内存占用还包括：

- **Page Tables（页表）**: 每个进程都需要页表来映射虚拟地址到物理地址。如果系统中进程数量巨大（比如成千上万个轻量级线程），页表会占用惊人的内核内存。
- **Kernel Stack（内核栈）**: 每个线程在内核态执行代码时都需要一个独立的内核栈（通常是 8KB 或 16KB）。当进程/线程数非常多时，这也是一笔巨大的固定开销。
- **Direct Mapping (Direct Kernel Map)**: Linux 内核通过内核虚拟地址空间直接映射所有的物理内存。虽然这不算“占用”，但内核维护这些映射表本身也需要空间。
- **DMA/HugeTLB**: 专门为 DMA 缓冲区或大页内存分配的区域，这些通常不在常规的 Slab 分配器中。
- **Vmalloc Area**: 用于内核分配大块连续虚拟内存的区域。

使用 `meminfo` 计算

Linux 将所有内存统计都记录在 `/proc/meminfo` 中。你可以通过以下命令大致计算出内核占用的份额：

```sh
cat /proc/meminfo
```

你可以关注这些关键指标来推算：

- **`Slab`**: 内核数据缓存。
- **`PageTables`**: 进程页表占用。
- **`KernelStack`**: 内核栈占用。
- **`VmallocUsed`**: 虚拟内存映射区域占用。

如top中未明显看到占用内存大的进程，也可通过ps命令测算进程内存占用总和，以进一步确认内存占用在进程，还是内核，如下：

```bash
ps h -eo rss | awk '{s+=$1}END{print s}' | numfmt --from=auto --to=iec
```

一般来说，内存问题不会是由内核导致的，除非内核或驱动出现bug，这可考虑使用bcc的**memleak**命令排查。

### glibc缓存的内存

### native分配的内存

通过pmap命令，就可以查看进程的整个虚拟内存空间，它也包含了native分配的内存块。一般我们分析进程虚拟内存空间中，物理内存占用比较大的内存块，如下：

```bash
$ pmap -x 763060 | sort -nrk3 | head # 按第3列数据的数值倒序排序
Address           Kbytes     RSS    Dirty  Mode  Mapping
0000000000400000      4       4       0    r-x-- your_go_program
000000c000000000   204800  198760   198760 rw--- [anon]  # 匿名内存（堆/栈）
00007f8a00000000    10240    8192    8192  rw--- [anon]
...
total kB           524288  498760   489200
```

<img src="2.%E5%86%85%E5%AD%98%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image-20260310170056576.png" alt="image-20260310170056576" style="zoom: 67%;" />

| **特征 (Mapping)** | **权限 (Mode)** | **身份推断**                                                 |
| ------------------ | --------------- | ------------------------------------------------------------ |
| `[ anon ]`         | `rw-p`          | **最可疑的区域**。这通常是堆 (Heap)、Goroutine 栈、或者是通过 `mmap` 分配的匿名内存。 |
| `[ stack ]`        | `rw-p`          | 这是 **M (原生线程) 的栈**。一个进程通常有几个线程，就会有几个这样的段。 |
| `[ heap ]`         | `rw-p`          | 在某些实现中会直接标注，但在 Go/Java 中，它经常被合并进 `[ anon ]`。 |
| `*.so` 或 `*.go`   | `r-x-p`         | 这是**代码段**（只读、可执行）。它是内存里的“指令集”，内存占用通常很稳定，不会泄露。 |
| `*.so`             | `rw-p`          | 这是**数据段**，存放库的全局变量。                           |

我们可以保存前后两个时间点的pmap数据，然后进行比对，看看哪些内存块是新增的或变大了，然后可以在**/proc/$pid/mem**中读取相应内存块数据，用**strings**检查，看有没有可疑的字符串。

### 内核参数

| **vm.zone_reclaim_mode**         | 内存区域内回收，值为1时线程去回收自己 zone 的 page cache 而不去使用其它 zone 的 free pages |
| **vm.watermark_scale_factor**    | 调整Linux空闲内存水位的差值                                  |

| **swapoff --all**命令            | 禁用swap                                                     |
| **vm.overcommit_memory**         | 是否允许Linux申请超过物理内存大小的虚拟内存                  |

3. 若想避免内存被swap，可使用**mlock(c函数)**来锁定内存，锁定文件缓存，可使用**vmtouch**命令。

### JVM

通过调优JVM内存与GC参数，也可以优化系统的整体性能，如下：

| **调优参数**                     | **作用**                                                     |
| -------------------------------- | ------------------------------------------------------------ |
| -XX:InitialRAMPercentage=65.0    | 按物理内存比例分配堆内存(初始值)                             |
| -XX:MinRAMPercentage=65.0-Xms10g | 按物理内存比例分配堆内存(最小值)-Xms是配置最小堆内存的绝对值 |
| -XX:MaxRAMPercentage=65.0-Xmx10g | 按物理内存比例分配堆内存(最大值)-Xmx是配置最大堆内存的绝对值 |
| -XX:MaxDirectMemorySize=128m     | 限制直接内存，避免直接内存占满内存                           |
| -XX:+AlwaysPreTouch              | 预touch堆内存，启动时就分配物理内存，而不是使用到才分配      |
| -XX:+HeapDumpOnOutOfMemoryError  | 发生OOM异常时，自动dump堆                                    |
| -XX:HeapDumpPath=/home/logs/     | dump文件路径，要保证目录存在                                 |

通过调优JVM内存与GC参数，也可以优化系统的整体性能，如下：

| **调优参数**                            | **作用**                                                     |
| --------------------------------------- | ------------------------------------------------------------ |
| -XX:+UseParallelGC-XX:+UseParallelOldGC | 新生代与老年代使用并行Parallel Scavenge收集器                |
| -XX:+UseParNewGC-XX:+UseConcMarkSweepGC | 新生代使用ParNew并行垃圾回收器老年代使用CMS垃圾回收器，堆内存4G以上且JDK9以下可考虑使用，以上可用G1 |
| -XX:+UseG1GC                            | 使用G1垃圾回收器，内存4G以上且JDK8以上可考虑使用。           |
| -XX:+UseZGC                             | 使用ZGC垃圾回收器，JDK17以上，需要低延时可考虑使用。         |

### 编码

优化进程的内存占用，可尽量避免产生大量对象。

1. **流式处理**，尽量使用类似InputStream的流式处理，而不要一次性读取后再处理。
2. **数量限制**，使用有界队列和限制最大数量的线程池。
3. **分页查询**，分多次分页查询处理数据，而不是一次性查询所有。
4. **避免大对象**，大对象对GC有很大挑战，必要时可避免创建大对象，如使用LinkedList代替ArrayList(内含数组，数量多时是大对象)，使用jackson流式序列化大对象等。
5. **缓存优化**，内存不足对系统危害极大，非性能要求极高的缓存场景，建议使用redis远程缓存替代本地缓存。

## 总结

1. linux物理内存划分为**node（节点），zone（区域），page（页面）**这三个层面。
2. linux虚拟内存划分为**栈，内存映射段，堆，数据段，代码段**等。
3. java内存划分为**java堆，非堆（metaspace，code cache，thread等），native分配**等。
4. linux 虚拟内存通过**brk/mmap**分配，**glibc**作为malloc函数与brk/mmap系统调用的桥梁，可能**会缓存一定量的内存块**。
5. linux通过**缺页中断**分配物理内存，当系统空闲内存不足时，会启动**内存回收**机制。
6. 通过**jcmd，arthas，NMT，pmap**等命令，可以观察java进程各内存区域的占用情况。
7. 若堆内存占用高，可使用**jmap+MAT**诊断，若metaspace占用高，可使用**arthas classloader+profiler**诊断，若native分配占用高，可使用**tcmalloc/mtrace+arthas profiler**诊断。
8. 可通过**dmesg**确认进程是否被OOM killer干掉了。
9. **内存调优**可以调整内核参数，用户态内存分配器或JVM参数。

# 故障定位：Go 进程内存占用高分析笔记

## 1. 内存组成架构对比 (Go vs Java)

Go 进程不像 Java 那样有明确的 Heap/MetaSpace 划分，它的内存主要由 **Go Runtime** 自行管理。

- **Go Heap (堆):** 存储所有动态分配的对象。Go 的 GC（三色标记法）负责回收。
- **Goroutine Stack (栈):** 每个协程初始约 2KB，随需求增长。几十万个 Goroutine 会消耗大量物理内存。
- **Runtime Metadata:** 存储 GC 位图、mspan 映射表、类型信息等。
- **Off-Heap / Cgo:** 通过 `C.malloc` 或 `mmap` 直接申请的内存，不受 Go GC 控制。

```
+--------------------------------------------------------------------------+
| Go 进程 (Go Process)                                                      |
|                                                                          |
| +----------------------------------------------------------------------+ |
| | Go 运行时内存 (Go Runtime Managed)                                    | |
| | +-----------+  +-----------+  +-----------+  +---------------------+ | |
| | | Go 堆     |  | 栈 (Stack)|  | 运行时元数据|  | Go 内存分配器       | | |
| | | (Heap)    |  | (Goroutine|  | (mspan,   |  | (mcache, mcentral)  | | |
| | |           |  |  Stacks)  |  |  mheap)   |  +---------------------+ | |
| | +-----------+  +-----------+  +-----------+                          | |
| +----------------------------------------------------------------------+ |
|                                                                          |
| +----------------------------------------------------------------------+ |
| | libc 内存分配器 (Cgo/System/Non-Go Memory)                            | |
| | +---------------------+  +-----------------------------------------+ | |
| | | Cgo 调用(Cgo Malloc) | | 映射内存(mmap/Large allocs)              | | |
| | +---------------------+  +-----------------------------------------+ | |
| +----------------------------------------------------------------------+ |
|                                                                          |
| +----------+  +-----------+  +-----------+  +-----------+  +-----------+ |
| |  代码段   |  |   数据段  |  | 堆 (Brk)  |  | mmap区域   | | 栈 (Thread)| |
| +----------+  +-----------+  +-----------+  +-----------+  +-----------+ |
+--------------------------------------------------------------------------+
       |                                       |
       v                                       v
+--------------------------------------------------------------------------+
| 操作系统内核 (Linux Kernel)                                               |
| +----------+ +---------------------------------------------------------+ |
| | 物理页面 | | 页面链表 (Page Lists: 空闲, 匿名 Anon, 文件 File Page)     | |
| | (DMA/    | +---------------------------------------------------------+ |
| | Normal)  | | 缓存 (Page Cache) / Slab 分配器                          | |
| +----------+ +---------------------------------------------------------+ |
+--------------------------------------------------------------------------+
```

概念澄清：什么是“堆外”？什么是“非堆”？

在 Java 中，很多人混淆了这两个概念，但在 Go 中，我们可以重新定义它们：

- **堆内存 (Heap Memory - Go 管理区)：** Go Runtime 分配器（`mheap` 等）管理的内存。`pprof` 能看得见的内存。
- **堆外内存 (Off-Heap - "账外内存")：** Go 代码通过 `Cgo` 调用 C 的 `malloc`，或者直接 `mmap` 分配的内存。**Go 的 GC 完全无法感知它们。**
- **为什么说 Native 是“堆外”？**
  - 因为 `Native` 代码运行在 Go 的 Runtime 调度器之外。当你调用 C 库时，内存是由 `libc` 的分配器管理的，它不在 Go 的 `mspan` 统计范围内。这就是为什么内存泄漏时，`pprof` 查不出原因，必须用 `pmap` 才能看到异常的 `anon` 区域。
- **非堆内存 (Non-Heap)：** 在 Java 中是指 `MetaSpace`、`CodeCache` 等。**在 Go 中，严格意义上没有“非堆”这个概念**。Go 的类型元数据（类比 Java 的 MetaSpace）直接存在 Go 的 Heap 区域中。

## 2. 核心分析工具链

在 Go 中，我们不使用 `jmap` 或 `jstat`，而是使用以下工具：

| **维度**         | **Go 工具**                 | **说明**                                |
| ---------------- | --------------------------- | --------------------------------------- |
| **实时监控**     | `top` / `free` / `ps`       | 查看进程 RSS 和 VIRT                    |
| **映射分析**     | `pmap -x <pid>`             | 分析进程内存映射段（同 Java）           |
| **深度剖析**     | **`pprof`**                 | Go 最核心工具，分析堆内存分配、采样对象 |
| **运行时状态**   | `runtime.ReadMemStats`      | 代码内打印详细内存计数器                |
| **系统调用追踪** | `strace -e mmap,brk,munmap` | 观察向内核申请内存的频率                |

### 极简的“排查工具组合拳”

在实际的运维或开发工作中，这套组合拳是这样打的：

1. **`top` / `free`**: 先看一眼全局和进程 RSS，确认**“有没有问题”**（这是体检）。
2. **`pmap -x`**: 查看进程内存分布，确认**“是哪种类型的内存（堆、栈、映射）变多了”**（这是 CT 扫描）。
3. **`pprof`**: 进入代码逻辑，确认**“到底是哪行代码引起的”**（这是手术切片）。
4. **`strace`**: 如果前三个都看不出，用它观察系统调用，确认**“是不是系统底层的分配策略（如内存对齐、碎片化）引起的”**（这是最后的外科手术）。

当你的 Go 程序 RSS 很高时，通过以下四个象限逐一排查，就能精准定位：

| **内存区域**        | **对应 Java 区域** | **排查工具**           | **排查逻辑**                                            |
| ------------------- | ------------------ | ---------------------- | ------------------------------------------------------- |
| **Go Heap**         | Java Heap          | `pprof` (heap)         | 最常见。是否存在 `inuse_space` 巨大的对象？             |
| **Goroutine Stack** | Thread Stack       | `pprof` (goroutine)    | 协程数是否失控？每个协程占 2KB+，10万协程 = 200MB+。    |
| **Runtime Data**    | MetaSpace          | `runtime.ReadMemStats` | Go 的内部数据结构（如大量的 map/channel 元数据）。      |
| **Native/Off-Heap** | Native / Direct    | `pmap` / `strace`      | **最危险的区域**。通过 Cgo 申请或系统直接 mmap 的内存。 |

## 3. 典型分析流程

### 第一步：确认内存类型 (RSS 异常 vs 堆异常)

- **现象：** `top` 显示 RSS 很高，但业务逻辑似乎没那么多数据。
- **动作：** 检查 `pprof` 的 `heap` 剖析。
  - 如果 `pprof` 显示 `InUse` 远小于 `RSS`：说明内存空闲但在 Go Runtime 手里，没还给系统（类似 Java 的 `malloc_trim` 场景）。
  - 如果 `pprof` 显示 `InUse` 很高：代码里有真正的内存泄漏（对象未释放）。

### 第二步：使用 pprof 定位代码行

```sh
# 导出堆内存剖析文件
curl -s http://localhost:6060/debug/pprof/heap > heap.out
# 进入交互式分析
go tool pprof -http=:8080 heap.out
```

- **关注指标：**
  - `alloc_space`: 程序累计申请过的内存（由于 GC，不代表当前占用）。
  - `inuse_space`: **当前**驻留在内存中的对象（排查泄漏的关键）。

### 第三步：排查“堆外”或“空闲”内存

如果 `pprof` 看不到异常，但 `pmap` 显示有大量巨大的 `anon` 段：

1. **MADV_FREE 问题：** Go 1.12 - 1.15 在 Linux 上默认使用 `MADV_FREE` 告知内核内存可回收，但内核并不立刻减少 RSS。
   - **解决：** 设置环境变量 `GODEBUG=madvdontneed=1` 强制立即归还物理内存。
2. **Goroutine 泄漏：** 开启了大量协程未关闭，每个占几 KB 栈空间。
   - **动作：** 访问 `/debug/pprof/goroutine?debug=1` 查看协程总数。

## 4. 案例模拟：Go 版的 "malloc_trim" 场景

**Java 案例回顾：** 调用 `malloc_trim` 强制 libc 归还空闲内存。

**Go 对应场景：** Go 的堆内存释放比较保守。如果流量激增后内存不下降：

- **原因：** Go 运行时认为未来可能还会用到这些内存，为了性能不频繁进行系统调用归还。

- **手动触发归还 (Go 代码内)：**

  ```go
  import "runtime/debug"
  
  // 强制进行一次 GC 并尝试将物理内存还给操作系统
  debug.FreeOSMemory() 
  ```
  
  *注：这相当于 Go 世界里的 `malloc_trim`。*

## 5. 常见故障点总结表

**排查地图：怎么判断是哪个区域导致？**

你可以根据 `pmap` 的现象与 `pprof` 的对比来“定案”：

### 情况 A：`pprof` Heap 占用巨大

- **出问题的区域：Go 堆 (Heap)**
- **对应关系：** 这是 Go 运行时**最正统、最受控**的内存区域。
- **为什么出问题：** 你的业务代码中，对象生命周期被无意间拉长了。比如全局 `map` 不断添加数据而不删除，或者大对象（如巨大的 slice）逃逸到了堆上无法被回收。
- **诊断特征：** `pmap` 显示 `anon` 段（堆区域）数值非常大，且 `pprof` 的 `inuse_space` 也同样非常大。两者数值高度吻合。
- **排查目标：** 业务逻辑（代码逻辑、缓存机制）。

### 情况 B：`pprof` Heap 很小，但 `pmap` 的 RSS 巨大

- **出问题的区域：Goroutine 栈 (Stack) 或 内存碎片 (Heap Idle)**
- **对应关系：** 这是 Go 的**“隐形内存区域”**。
- **为什么出问题：**
  - **栈膨胀：** 你开启了大量的 Goroutine，每个协程的栈（即使是 2KB）叠加起来，导致 RSS 飙升。但 `pprof` 的 Heap 是专门统计“堆对象”的，它**默认不会统计栈内存**。
  - **内存碎片 (Heap Idle)：** Go 的分配器（`mheap`）向内核申请了内存，分配给你的代码用，但你代码随后释放了。Go 运行时觉得“以后还用得到”，为了性能，**暂时没把这些内存还给操作系统**。
- **诊断特征：** `pmap` 显示巨大的 `anon` 段，但 `pprof` 的 `inuse` 指标却很小（比如 RSS 是 1GB，`inuse` 只有 50MB）。
- **排查目标：** 协程调度器（Goroutine 数量）、GC 回收策略 (`debug.FreeOSMemory`)。

### 情况 C：RSS 极大，且在逻辑上完全与 Go 运行时的统计脱节

- **出问题的区域：原生内存 (Native / Off-Heap)**
- **对应关系：** 这是 Go 的**“禁区”**。
- **为什么出问题：**
  - **Cgo 泄漏：** 你调用了 C 库，但在 C 层申请的内存（`malloc`）忘了调用 `free`。
  - **mmap 泄露：** 代码中显式调用了 `syscall.Mmap` 来分配大数据缓冲区，但对应的 `Munmap` 逻辑没走。
  - **Go 根本不知道这块内存的存在**，所以它无法监控，也无法 GC。
- **诊断特征：** `pprof` 查不到任何异常，`runtime.MemStats` 的数值也很健康，但 `top` 命令看到的 RSS 就是居高不下，且 `pmap` 能看到一块非常突兀的 `anon` 段。
- **排查目标：** C 语言接口调用处、第三方驱动库、底层系统调用。

## 总结：系统内存占用高该如何排查？

### **第一步：宏观定性（区分用户态 vs 内核态）**

**内核态占用高**：如果 `free -m` 显示已用内存很高，但 `top` 中所有进程的 `RES` 加起来却远小于总用量，那么内存可能被内核占用了。

1. **检查内存映射**：查看 `/proc/meminfo`。重点看 `Slab`、`VmallocUsed` 和 `PageTables`。

2. **观察 `Slab` 占用**：内核使用 Slab 机制管理小对象（如文件句柄、网络连接）。执行 `slabtop -s c` 按内存占用排序。

   如果 `dentry` 或 `inode_cache` 过高，说明系统打开了大量小文件。

**用户态占用高**：如果在 `top` 中看到多个进程的 `RES`（常驻内存）之和接近物理内存总量，或者某个特定进程的 `%MEM` 持续飙升，则判定为**用户态**问题。

### **第二步：用户态排查（以 Go 程序为例）**

如果确定是 Go 程序导致的内存占用过高，排查思路分为：**“看指标”**、**“抓快照”**、**“定代码”**。

**1. 确认表现形式**

- **RSS 持续上升**：可能是典型的内存泄漏。
- **RSS 很高但 CPU 也高**：可能是频繁 GC（垃圾回收）导致的，说明对象分配太快。

**2. 使用 pprof 工具进行深度诊断**

Go 语言内置了强大的 `net/http/pprof`。我会通过以下步骤定位：

- **查看堆内存分配 (Heap Profile)**：

  ```sh
  go tool pprof -http=:8080 http://<ip>:<port>/debug/pprof/heap
  ```

  - 在 Web 界面中查看 **Top** 视图，找出占用内存最大的函数。
  - 查看 **Graph**（火焰图），观察函数调用链路。

- **区分 `inuse_space` 和 `alloc_space`**：

  - `inuse_space`: 当前程序持有的内存（查泄漏看这个）。
  - `alloc_space`: 程序累计分配过的内存（查频繁分配导致的 GC 压力看这个）。

**3. 分析具体原因**

在 Go 中，用户态内存高通常由以下几个“坑”引起：

- **Goroutine 泄漏**：大量 Goroutine 阻塞导致其关联的栈内存（每个约 2KB+）无法释放。
- **Slice/Map 滥用**：例如在一个长生命周期的全局 Map 中不断插入数据，或截取了大数组的一小段导致原大数组无法被回收。
- **未关闭的资源**：`sql.Rows`、`http.Body` 或 `Ticker` 未 Close，导致底层缓冲区泄漏。

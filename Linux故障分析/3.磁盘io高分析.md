# 磁盘io高分析

## 高磁盘io占用分析

### 整体情况

高磁盘io占用，分析方法也是逐步**细分资源占用情况**，分3步：**找磁盘** -> **找进程或文件** -> **找调用栈**

`iostat -dxz 1`可以查看磁盘整体占用情况

```sh
# -d：只显示设备（磁盘）使用状态
# -x：在输出中包括扩展的磁盘指标
# -z：省略零活动设备的输出
```

`pidstat -d 1`可以查看哪个进程读写磁盘频繁。

可以发现是java进程占用高，主要是写操作！

通过bcc的**filetop**可以查看在读写哪个文件。

```sh
filetop -p $(pgrep java) # pgrep java用来找到进程名为java的进程的pid
```

### 找调用栈

通过arthas的profiler可以找到调用栈，如下：

<img src="3.%E7%A3%81%E7%9B%98io%E9%AB%98%E5%88%86%E6%9E%90.assets/image-20260312022759894.png" alt="image-20260312022759894" style="zoom: 50%;" />

如果是非Java程序，可以通过bcc的stackcount命令来采集使用`vfs_write()`的程序的调用栈，如下：

```sh
$ stackcount-bpfcc -f vfs_write
```

它的核心作用是：**统计“谁”在频繁调用内核的写入接口 `vfs_write()`**。

- **vfs_write**：这是 Linux 虚拟文件系统（VFS）层的通用写入函数。无论是写日志、写数据库文件，还是写 Socket，最终几乎都会经过这个内核函数。
- **-f**：表示输出格式为 **Folded**（折叠格式）。这种格式将每一层调用栈用分号 `;` 连接，行末跟随该堆栈出现的次数。这种格式是生成火焰图的**标准输入源**。

当你执行该命令时，它会进入“静默监听”状态。

1. **内核埋点**：它会在内核 `vfs_write` 函数的入口处插入一个探针。
2. **数据收集**：每当系统（任何进程）调用一次 `vfs_write`，BCC 就会抓取当前的完整调用栈，并在内核 BPF Map 中对该堆栈的计数器 +1。
3. **输出结果**：当你按下 `Ctrl+C` 停止采样时，它会将所有收集到的堆栈及其出现频率打印到终端。

**输出示例（折叠格式）：**

```java
java;libjvm.so;vfs_write 105
go-app;runtime.goexit;os.Write;syscall.Write;vfs_write 42
```

*这表示 `java` 进程通过某路径调用了 105 次写入，而 `go-app` 经过 `os.Write` 调用了 42 次。*

#### 如何生成火焰图

`stackcount -f` 产生的折叠堆栈正是为了配合 Brendan Gregg 的 `FlameGraph` 工具使用的。要生成火焰图，你需要执行以下“三部曲”：

**第一步：采样并保存数据**

```sh
# 采样 30 秒，并将折叠后的堆栈信息保存到 out.stacks
stackcount-bpfcc -f vfs_write > out.stacks
```

**第二步：利用脚本渲染成 SVG**

你需要下载 [FlameGraph](https://github.com/brendangregg/FlameGraph) 脚本库：

```sh
# 将折叠堆栈转换为火焰图 SVG
./flamegraph.pl out.stacks > io_flamegraph.svg
```

#### 如何通过火焰图定位问题？

看 IO 火焰图时，建议遵循 **“由下而上找根源，由上而下找逻辑”** 的原则：

**A. 寻找“平顶”（Plateaus）**

如果你看到火焰图顶部有一个非常宽的平面，这通常意味着该调用栈是 **IO 密集型操作的直接发起者**。

- **Go 场景：** 你可能会看到 `os.(*File).Write` 或者 `bufio.(*Writer).Flush`。
- **Java 场景：** 常见的是 `ch.qos.logback.core.OutputStreamAppender.writeOut`。

**B. 区分“同步”与“异步”**

- **同步 IO：** 调用栈会一直延伸到内核态（如 `ext4_file_write_iter`）。如果这一支很宽，说明业务逻辑在等待磁盘写入完成。
- **异步/缓冲 IO：** 如果看到大量 `Buffered` 字样的中间层，说明程序在内存中做了缓冲，但最终触发了刷新（Flush）。

可以看到，都是logback在写日志！

## 磁盘io调优

磁盘io相关的调优选项，如下：

| **调优参数**                          | **作用**                   |
| ------------------------------------- | -------------------------- |
| **ionice**命令                        | 调整进程的io优先级         |
| **/sys/block/\*/queue/scheduler**     | IO调度策略                 |
| **/sys/block/\*/queue/read_ahead_kb** | 文件系统请求的最大预读KB数 |

### 编码优化

由于大多数程序员都是crud开发，涉及到存储系统研发的很少，写的代码与磁盘最密切的就是写日志而已，因此在磁盘方面遇到的问题非常少。说几点通用优化策略，如下：数据缓存：将读写缓存起来，避免直接读写磁盘。增大缓冲：比如使用更大Buffer的BufferReader。尽量避免随机io：不管是HDD还是SDD，随机io的性能都比顺序io差得多，故应该尽量避免随机io，比如数据库中，随机io写缓存，同时在redo log中使用顺序io备份更新记录(避免断电)，然后使用异步线程同步缓存数据到磁盘。数据索引：不管是文件系统，还是数据库，都对数据做了索引，以避免全盘扫描数据。

## 总结

1. 通过**iostat -dxz 1**观测磁盘整体io情况。
2. 通过**pidstat -d 1**找磁盘占用高的进程，通过bcc的**filetop**找读写的文件。
3. 通过bcc的**stackcount**，采集对 **vfs_write()** 内核函数的调用栈，找到读写的代码位置。
4. 通过**ioping**可简单确认磁盘的性能情况。

# CPU占用高分析

## 资源占用高分析思路

比如说我们的cpu占用高，然后内存占用高，这样的一些场景，首先介绍一下分析思路

![image-20260121140814767](1.CPU%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image-20260121140814767.png)

资源分析视角是自底向上，在这个逐步自底向上的过程逐步细分资源占用的，找到问题根因，如cpu高问题,如下：

1.用户态还是内核态高？

2.什么进程占用cpu高?

3.什么线程占用cpu多？

4.什么调用栈占用cpu多？

5.什么请求占用cpu多？

比如我们cpu占用高的时候，我们会往上看，就是我们是操作系统的**内核态占用**比较高，还是操作系统的**用户态占用**比较高，第二个发现是用户态占用高的话，我们一定会继续去找，

是**什么进程占用的cpu比较多**，然后找到了进程之后，我们又继续去找是**什么线程占用的cpu比较高**，然后找到线程之后，我们可能就会去看一看这个线程当前正在执行什么操作，

是**什么调用栈占用的cpu比较多**，然后找到调用栈之后，我们可能需要关心一下，比如说是**什么请求cpu比较多**，比如说像mysql这样的程序的话，它的调用栈其实各种SQL的调用栈其实都是类似的，

其实具体的话，占用cpu比较多，就是个别的几个慢SQL导致的，所以我们最后要找到什么请求上

对于业务系统，一般找到了具体的调用栈，问题就排查出来了，但对于类似mysql，nginx这样的系统，由于各种请求的调用栈大致相同，因此还需要深入排查到是什么请求数据(SQL，URL）占用资源多。

也可以直接一步细分到调用栈，比如perf，bcc等内核级工具，它采集的调用栈，既包含用户进程的，也包含内核态的中断处理与内核线程的。

## CPU使用率解释

![image-20260121141133552](1.CPU%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image-20260121141133552.png)

| 字段                | 含义               | 说明                                                         |
| ------------------- | ------------------ | ------------------------------------------------------------ |
| us (`user`)         | 用户态 CPU 时间    | 执行普通用户进程（非内核、非 nice）所占的 CPU 百分比         |
| sy (`system`)       | 内核态 CPU 时间    | 执行内核代码（系统调用、中断处理上半部等）所占的 CPU 百分比  |
| ni (`nice`)         | 低优先级用户态时间 | 执行 nice 值 > 0 的用户进程所占 CPU（属于用户态，但单独统计） |
| id (`idle`)         | 空闲时间           | CPU 无事可做，处于 idle 状态（不包括 I/O 等待）              |
| wa (`iowait`)       | I/O 等待时间       | CPU 空闲，但有未完成的磁盘 I/O（严格说不算“使用”，但反映 I/O 瓶颈） |
| hi (`hardware irq`) | 硬中断处理时间     | CPU 花在处理硬件中断（如网卡、键盘）上半部的时间             |
| si (`software irq`) | 软中断处理时间     | CPU 花在处理软中断（如网络协议栈下半部、tasklet）的时间      |
| st (`steal time`)   | 虚拟机偷取时间     | 被 hypervisor 分配给其他虚拟机而“偷走”的时间（仅虚拟化环境） |

**举个例子（来自 `top` 的 CPU 行）：**

```
%Cpu(s): 10.0 us,  5.0 sy,  0.0 ni, 80.0 id,  2.0 wa,  2.0 hi,  1.0 si,  0.0 st
```

- 用户程序用了 10%
- 内核常规工作（如系统调用）用了 5%
- 硬中断用了 2%
- 软中断用了 1%
- 空闲 80%
- I/O 等待 2%

✅ 这些百分比加起来 ≈ 100%，且 **`hi` 和 `si` 不包含在 `sy` 中**。

### 用户态

用户态cpu使用率解释

```Batch
us： 非niced进程花费的cpu时间占比      就是没有调整过的进程优先级的花费的cpu时间占比
ni：   niced进程花费的cpu时间占比      就是调整过ni优先级的进程花费的cpu时间占比，其实ni这个优先级，现在已经应用的很少了

niced是谦和度的意思，进程的谦和度越低就越喜欢抢资源

# 弄清楚这两个概念之前要先知道linux的进程的优先级
```

**linux进程的优先级：**

- 进程谦和度NI列（Nice）：用户可设置的“优先级偏移量”，范围：-20 ~ +19，值越小优先级越高，可通过renice命令调整（普通用户只能把niced值设置为0~19，只有root用户可以将niced值设为负数）

- 进程优先级PR列（Priority）：内核实际用于调度的优先级值，默认PR=NI+20，但如果linux调度器觉得有必要，也可能会动态调整进程的当前优先级。
  - PR取值范围：
    - 普通进程：0 到 39
      - 计算公式：PR = 20 + NI
      - 因此当 NI = -20 时，PR = 0（最高优先级）
      - 当 NI = 19 时，PR = 39（最低优先级）
    - 实时进程（Real-Time）：显示为 RT 或 负数（如 -2）
      - 实时进程的优先级高于所有普通进程
      - 其 PR 值不由 NI 决定，而是由实时调度策略（如 SCHED_FIFO、SCHED_RR）和 rt_priority 决定

### 内核态

#### 系统调用

是操作系统提供给用户空间程序的一种接口，运行程序请求操作系统的服务，比如访问磁盘（open/read/write），网络（socket/recvfrom/sendto）等，内核收到系统调用请求后，会先切换到内核态，然后执行相应处理逻辑。

#### 中断

​	中断是指计算机系统在执行程序的过程中，由于某些紧急事件或外部设备的请求，暂时中止当前程序的执行，转而去处理更为紧急的任务。处理完这个紧急任务后，计算机系统会返回到被中断的地方，继续执行原来的程序，比如系统中断，网络中断。

​	在 linux 中，中断分为2个部分处理，硬中断和软中断。 

1.硬中断：由硬件直接触发，由于硬中断执行过程中一般需要禁用中断后再处理，因此硬中断需要能快速执行完以避免其它中断信号丢失。

2.软中断：为了尽可能快执行完硬中断，减少禁用中断时间，linux设计了出现了软中断，用于处理中断中可以延迟处理的部分。

**硬中断执行时的「铁律」：执行前，必须「全局关闭中断」**

​	CPU 在执行硬中断处理程序的那一刻，会立刻执行一条指令：cli（close interrupt） → 禁用当前 CPU 上的所有硬中断请求。意思是：在这个硬中断处理完之前，这个 CPU 再也接收不到任何硬件的中断信号了。

**为什么要「禁用中断」？**

​	硬中断是硬件的最高优先级请求，比如网卡的数据包、磁盘的 IO 完成信号，都是「晚处理一秒就可能丢数据」的紧急请求。如果 CPU 在处理一个网卡硬中断时，又接收并处理一个磁盘硬中断，两个中断的处理程序会「抢占、混乱」，大概率会导致数据错乱、硬件卡死。所以 Linux 内核的设计是：硬中断是「独占 CPU、独占硬件」的原子操作，绝不允许被其他中断打断。

**为什么硬中断「必须快速执行完」？**

​	因为硬中断执行时CPU 是关闭所有中断的！！！如果硬中断的处理逻辑很复杂、执行时间很长 → CPU 会在很长一段时间内「收不到任何硬件的中断信号」：

- 网卡新的数据包来了，CPU 收不到中断 → 网卡缓冲区满了 → 丢包；

- 磁盘写完数据了，CPU 收不到中断 → 磁盘一直等 → IO 超时；

- 鼠标点击了，CPU 收不到中断 → 鼠标卡死 → 无响应；

- 键盘按键了，CPU 收不到中断 → 键盘失灵。

**软中断（SoftIRQ）：承接硬中断的「所有后续工作」**，开启中断运行（开启中断时，cpu会正常响应其他中断信号），可延迟、可调度

​	软中断就是处理硬中断「不想干、没时间干、不能干」的所有剩余工作，这部分工作「重要，但不紧急」，可以延迟处理，也是中断里真正干活的主力。

比如：

​	网卡硬中断：只把数据包从网卡缓存拷贝到内核内存 → 软中断 负责：解析数据包的协议头、检查 IP 地址、检查端口号、把数据包交给对应的应用程序（比如 nginx、ssh）；

​	磁盘硬中断：只把磁盘数据拷贝到内核内存 → 软中断 负责：把数据刷到页缓存、更新文件的 inode 信息、通知对应的进程「你的 IO 完成了，可以继续运行了」；

**软中断的 3 个核心特性（完美解释「延迟处理」）**

✅ 软中断执行时，「开中断」运行软中断处理的时候，CPU 的中断是打开的！如果此时有新的硬中断信号过来，CPU 会立刻暂停软中断，优先处理硬中断，处理完硬中断后，再回来继续处理软中断。→ 这就彻底解决了「丢中断」的问题，也是软中断能「延迟处理」的核心底气。

✅ 软中断的优先级：「仅次于硬中断，高于所有进程」Linux 内核的调度优先级排序：硬中断 > 软中断 > 内核线程 > 用户态进程只要有软中断待处理，CPU 会优先处理软中断，不会被用户态进程抢占，保证「后续工作一定会被处理」，只是不用像硬中断那样「立刻马上」。

✅ 软中断有专门的「内核线程」处理，不抢占业务逻辑，Linux 为每个 CPU 核心，都创建了一个专门处理软中断的内核线程：ksoftirqd/n（n 是 CPU 核心号，比如 ksoftirqd/0、ksoftirqd/1），这个线程唯一的工作就是处理软中断。当硬中断标记了「有软中断要处理」，这个内核线程就会立刻被唤醒，执行软中断处理程序；处理完后，这个线程就会休眠，不占 CPU 资源。

**小结**

中断是硬件给 CPU 的「紧急求救信号」，CPU 必须优先处理；

硬中断：硬件触发、关中断运行、执行极快、只做「应答 + 拷贝 + 标记」，是「急诊抢救」；

软中断：内核触发、开中断运行、可延迟处理、做所有后续工作，是「专科治疗」；

拆分目的：让硬中断快到极致，避免丢中断，让系统的中断响应能力最大化；

优先级：硬中断 > 软中断 > 内核线程 > 用户进程；

#### 内核线程

linux内核管理着一批内核线程，用来执行一些特定的任务，如kswapd处理内存回收，ksoftirqd处理软中断等。

**其实可以将Linux内核看成一个服务器，这个服务器主要接收两种类型的请求，一个是系统调用，一个是中断，然后运行着一些异步任务，既内核线程。**

#### 中断和异常有什么区别？

| ----------------- | ---------------------------------- | ---------------------- | ---------------------------------- |
| 中断（Interrupt） | 外部设备（如键盘、网卡）           | 异步（与当前指令无关） | 硬件中断（IRQ）                    |

### 空闲

空闲cpu使用率解释：

```batch
id：空闲时花费的cpu时间占比（不包含wa）
wa：等待磁盘io完成花费的cpu时间占比

id与wa实际都是空闲cpu使用率，区别是当cpu空闲时，是否有正在等待磁盘io的线程存在，若存在，这部分时间单独记到wa中。
因此，linux设计wa指标，就是为了方便判断，当cpu空闲较多时，是否是磁盘阻塞导致的。
```

### java火焰图

通过arthas的profiler火焰图，也可以跳过找线程，一步到位到具体调用栈，它一般适合于做性能优化。

Profiler 会以固定的频率（例如每 10ms）向 JVM 发送信号，暂停并记录当前所有线程的调用栈。如果一个函数在采样中出现的次数越多，它在火焰图中的**横向宽度（Width）**就越宽。

```bash
[arthas]$ profiler  start  --alluser
Profiling  started

[arthas]$ profiler  stop
OK
profiler output  file:/home/meng/arthas-output/20240912-061532.html
```

#### **怎么看火焰图？**

- **横轴（Width）：** 代表该函数在采样周期内**消耗 CPU 时间的占比**。越宽，说明这个方法运行的时间越长，或者是被调用的频率越高，是性能优化的重点。
- **纵轴（Height）：** 代表**调用栈的深度**。最底部是入口（如 `Thread.run`），最顶部是当前正在执行的叶子函数。
- **颜色：** 通常绿色代表 Java 代码，黄色/红色可能代表内核态或 JVM 内部代码（不同工具颜色略有差异）。

**需要重点关注的调用栈**

1. “平顶山”模式（Plateau）—— 真正的性能杀手

如果火焰图顶部出现了一个非常宽的“平顶”，且没有更细分的子调用，这通常是**性能瓶颈**所在。

- **特征**：某个函数处于调用栈的顶端，且占据了很大的横向宽度。
- **含义**：这意味着 CPU 大部分时间都耗费在这个函数**自身的逻辑**上（比如复杂的计算、密集的循环、频繁的序列化/反序列化），而不是在等待子函数返回。
- **诊断**：优先优化这些“平顶”函数。

2. “宽基座”与“长细尖塔”

- **宽基座（Wide Base）**：如果底层逻辑（如 HTTP 框架、RPC 框架）很宽，但向上分叉很多，这通常是正常的。说明你的系统承载了大量并发请求。
- **长细尖塔（Deep & Narrow Spikes）**：如果调用栈非常深，但每一层都很窄，这通常代表**深度递归**或极其复杂的调用链路，虽然 CPU 占用不高，但可能存在栈溢出风险或逻辑过于复杂的问题。

3. 哪些“宽”通常是有问题的？

并不是所有的宽都是坏事，你需要对比业务逻辑：

| **现象**                        | **是否有问题** | **常见原因**                                                 |
| ------------------------------- | -------------- | ------------------------------------------------------------ |
| **序列化/反序列化过宽**         | ⚠️ 可能有误     | 过度使用 `json.Unmarshal`（反射耗时），建议换成 `easyjson` 或 `protobuf`。 |
| **垃圾回收 (GC) 相关过宽**      | ❌ 有问题       | 程序中产生了大量短生命周期的对象，导致 `runtime.gcWorker` 占用过高。 |
| **锁竞争 (`runtime.selectgo`)** | ❌ 有问题       | 多个协程在抢夺同一个 Channel 或 Mutex，导致 CPU 都在处理调度逻辑。 |
| **底层系统调用 (`syscall`)**    | ⚠️ 需关注       | 可能是频繁读写小文件或网络 IO 姿势不对，未开启带缓冲的 IO。  |
| **业务逻辑中的 `for` 循环**     | ✅ 正常/⚠️ 待定  | 如果是核心计算逻辑，那是正常的；如果是空转或低效算法，则需要优化。 |

arthas是用于java的，对于非java进程，像mysql这种非java程序可以使用perf  record或bcc中的profile命令绘制火焰图，以perf举例，如下：


## 系统态CPU占用高分析

top命令中显示`sy`字段的值很高，说明是内核态占用了大量CPU，那该怎么判断是系统调用还是内核线程导致的呢？

系统态cpu占用，大致由系统调用，中断，内核线程这3个部分组成。（中断被top命令单独区分开了）

### 系统调用

![image (8)](1.CPU%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image%20(8).png)

```sh
# 显示整个系统（或指定进程）在采样期间内，哪些系统调用被执行得最频繁。
syscount  # -P：将系统调用次数按进程名/PID进行聚合统计
```

系统调用是通过 bcc 的`syscount`命令触发的，可以通过bcc的`syscount`命令来检查系统调用情况，以及哪些进程的系统调用比较多。可以看到左边的`syscount`，他左边的系统调用最多是`recvfrom`

右边按进程统计系统调用，发现是mysql的系统调用最多

### 中断

中断占用cpu情况，可以通过top的`hi`与`si`确认。

具体是什么中断占用高，可以查看/proc/interrupts（硬中断）或/proc/softirqs（软中断）文件，用watch命令找出哪些中断次数增长最快。

```bash
# 每秒刷新一次，并高亮显示变化的地方
watch -n 1 -d cat /proc/softirqs

# 软中断和硬中断是以设备作为最小单位划分的
[root@server01 /proc]# cat softirqs 
                    CPU0       CPU1       
          HI:          1          0
       TIMER: 1165599548  894783953 # 定时器中断
      NET_TX:       2041       1542 # 网络发送
      NET_RX:  608705279   65806215 # 网络接收
       BLOCK:  175411472          0 # 磁盘中断
BLOCK_IOPOLL:          0          0
     TASKLET:      13820         69
       SCHED: 3361555763 3303366577 # 进程调度中断
     HRTIMER:          0          0
         RCU: 1344661313 1209592079 # 内存同步机制
```

或使用**irqtop**命令，它解析了上面两个文件数据，可看出，软中断CPU占用主要由磁盘与网络引起。

中断也可以通过bcc工具hardirqs（硬中断）和softirqs（软中断）来诊断。

![image (9)](1.CPU%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image%20(9).png)

可以看到软中断最多的也是`net_rx`网络相关的软中断，以及`block`磁盘相关的软中断。

### 内核线程

内核线程的 **CPU 使用率**，可以通过 **pidstat** 的 **%system** 来确认，内核线程一般以 **k** 开头。

```sh
$ pidstat -u 1 # -u：查看各进程的cpu使用率
08:05:10 AM   UID       PID    %usr  %system  %guest   %wait    %CPU   CPU  Command
08:05:11 AM     0    376232    0.00    62.00    0.00    9.00   62.00     1  kworker/u257:2+flush-8:0
08:05:11 AM     0    376606    1.00    62.00    0.00   28.00   63.00     0  stress
```

其中，**kworker/u257:0+flush-8:0** 就是一个内核线程，用于将文件系统脏页保存到磁盘。

![image (11)](1.CPU%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image%20(11).png)

其实 **pidstat** 的 **%system**，大多来自**系统调用**、**缺页异常**、**内核线程**这 3 个方面，而缺页中断通过 **-r** 选项可以看到。

```sh
$ pidstat -h -ur 1 # -h：在一行内显示所有统计信息
08:16:01 AM   UID      PID  %usr %system %guest %wait  %CPU  CPU  minflt/s  majflt/s      VSZ     RSS %MEM Command
08:16:01 AM     0       55  0.00   10.00   0.00  1.00 10.00    0      0.00      0.00        0       0 0.00 kswapd0
08:16:01 AM   110      944 17.00   30.00   0.00  0.00 47.00    1      4.00      3.00  1790444    7872 0.40 mysqld
08:16:01 AM     0   377098  1.00   40.00   0.00  5.00 41.00    0    142.00   1565.00  8408612  996224 50.67 python3
```

- 指向 `kswapd0` 的 `%system`：**内核线程占用%system**
- 指向 `mysqld` 的 `%system`：**系统调用占用%system**
- 指向 `python3` 的 `minflt/s` 和 `majflt/s`：**缺页异常占用%system**

### 火焰图

也可以用perf  record或bcc的profile，直接采集整个系统的调用栈，绘制一张oncpu火焰图，以查看系统态cpu占用在哪。

```bash
# 收集线程栈
profile-bpfcc   -adf  -F   99  > stack_fold.log

# 生成火焰图
cat  stack_fold.log  | sed 's/;::/:::/g' | ./FlameGraph/flamegraph.pl  >  flamegraph.svg
```

![image (12)](1.CPU%E5%8D%A0%E7%94%A8%E9%AB%98%E5%88%86%E6%9E%90.assets/image%20(12).png)

从这个火焰图可以看到有三个部分组成，第一个部分就是`entry_SYSCALL`这样的一个调用栈，它其实就是在做系统调用，再发送一个网络包

第二部分我们有一个kswapd0这样的一个内核线程，它在占用内核态的cpu使用率

然后第三部分就是handle_mm_fault，这一看就是一个缺页异常，处理相关的一个调用栈，所以它是缺页异常占用的内核态cpu使用率

## 空闲cpu使用率高

**情况1：**id%使用率高

这种是空闲cpu使用率，有两种可能：

**1.系统负载不大，**可能没有业务流量，或由于网络丢包导致流量未进系统，如tcp连接队列或socket接收缓存配置过小，导致丢包。

**2.线程都被阻塞住了，**无线程占用cpu资源，这时请求的耗时会明显增大，这种问题的诊断会在<耗时高分析>那一篇再讲。 

**情况2：**wa%使用率高

这种也是空闲cpu使用率，有两种可能：

1.线程阻塞在磁盘访问上，一般需要检查磁盘性能指标，可以用iostat或ioping命令，检查磁盘是否有明显的性能退化。

2.使用了nfs之类的网络存储，由于网络较慢，wa%高可能也是正常的。

## cpu调优

### 调优工具

CPU相关的Linux调优项，如下：

| **调优参数**                                                 | **作用**                                                     |
| ------------------------------------------------------------ | ------------------------------------------------------------ |
| **echo off > /sys/devices/system/cpu/smt/control**<br />**echo on > /sys/devices/system/cpu/smt/control** | 关闭或开启超线程查看超线程状态，**cat /sys/devices/system/cpu/smt/active，**1表示已开启 |
| **cpupower**                                                 | 调整CPU能耗状态                                              |
| **taskset -pc 1-2 13333**                                    | 进程绑核，这样可以提升CPU缓存的命中率，进而提升IPC(每周期指令数)，进而提升性能。 |
| **renice**                                                   | 调整进程的优先级                                             |
| **irqbalance**                                               | 将中断均衡到各CPU上。                                        |

### JVM、JIT

JVM JIT将Java字节码即时编译成可直接执行的二进制指令，以加快代码执行，因此可通过调优JIT JVM参数，实现CPU优化，如下：

| **调优参数**                                                 | **作用**                                                     |
| ------------------------------------------------------------ | ------------------------------------------------------------ |
| **-XX:+TieredCompilation**                                   | 启用分层编译(JDK8+默认开启)，启动时用C1编译器，热点代码用C2编译器。 |
| **-XX:InitialCodeCacheSize**<br/>**-XX:ReservedCodeCacheSize** | JIT编译的代码放在code cache中，满时会关闭JIT编译，故可视情况调整大小。 |
| **-XX:+UseCodeCacheFlushing**                                | code cache满关闭JIT编译前，是否回收code cache                |
| **-XX:CICompilerCount**                                      | 编译线程数，CPU核充足时，可考虑增大                          |
| **-XX:+PreserveFramePointer**                                | 保留帧指针（frame pointer），以便perf、bcc可遍历调用栈。     |

### 代码优化

优化进程的CPU占用，本质上还是需要调整代码，使用更低时间复杂度的算法。

算法优化，不一定非要手动创建新算法，比如：

1. **合适数据结构**，将List.contains优化为HashMap.containsKey，实际就从O(n)优化到了O(1)，指定List初始大小等。
2. **使用缓存**，缓存计算结果，避免重复计算。
3. **正则优化**，如**`id:.*,name:.*`**优化为**`id:[^,]*,name:[^,]*`**就可以减少正则的回溯次数。
4. **计算优化**，如long替代BigDecimal，使用高性能序列化库，使用零拷贝，使用SIMD指令等。
5. **SQL优化**，将全表扫描优化为索引扫描，本质上就是从穷举算法优化成了树搜索算法。
6. **提升CPU缓存命中率**，使用数组或ArrayList，相比LinkedList，对CPU缓存更友好。

## 总结

1.资源占用高，适合使用自下而上的资源分析视角，逐步细化资源使用。

2.高cpu占用分析，用户态还是内核态？可通过top命令确认。

3.若是用户态，可进一步通过top查看进程及线程的cpu占用，对于java程序：

- **可以通过`jstack ${pid}`的方式输出占用CPU最高的进程的详细信息，然后再将占用CPU最高的线程通过 TID 过滤出来，最后即可得到该线程的调用栈信息**；
- 也可以通过`arthas`的`thread -n 4` 直接找到**当前java进程**中前占用CPU最高的调用栈；
- 或通过profiler直接绘制出**当前java进程**中所有线程调用栈的火焰图，哪个调用栈最宽就说明它占用的CPU时间最长。

对于Go程序，由于协程在线程间频繁切换，**`top -H` 看到的 LWP ID 可能在下一秒就换了任务**。因此，在 Go 里通过 CPU 线程 ID 倒查堆栈的效率通常不如直接通过`pprof`工具分析 **CPU Profile**。

若有需要，可通过`bpftrace`进一步细化到请求数据（如SQL)

4.若是内核态，可进一步细化为是系统调用、中断（单独看hi和si）还是内核线程占用导致

- 系统调用：可以通过bcc的`syscount -P`看哪个进程使用的系统调用最多
- 中断：可以通过`watch -n 1 -d cat /proc/softirqs或interrupts`查看哪个设备的中断次数增长最快，也可以通过`irqtop`观察
- 内核线程：可以通过`pidstat -u 1`判断CPU占用高的是不是内核线程（一般以k开头）、是哪个内核线程

也可通过bcc的profile直接绘制一张整体系统的火焰图，以查看到底是什么导致的内核态CPU占用率高。

5.若是空闲，则一般是系统流量过小（可能是本身流量小，也有可能是网络丢包导致流量没有进入服务器），或线程被长时间阻塞了导致的。

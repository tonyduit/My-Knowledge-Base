### 4. 你提到处理流式响应时需要避免阻塞，具体做了什么？

SSE 本质上确实还是基于 HTTP 协议，它没有彻底摆脱阻塞。传统 HTTP 请求是一次性返回完整结果，而 SSE 通过 Chunked Transfer-Encoding 实现持续推送。

在实现时，我们需要避免的是在流式处理过程中出现额外阻塞。具体做了以下几点：

1. 单独 goroutine 消费避免阻塞主流程 ：在初始化时，我们用 go RMQMessage.Consume(MQMessage) 启动一个单独的 goroutine 来消费消息队列，避免了消费逻辑阻塞 main 函数或 HTTP 服务的启动，以及在每次流式响应将用户问题通过Rabbitmq异步写入到数据库，避免了流式响应过程中的阻塞。
2. SSE 请求使用独立处理流程 ：在 CreateStreamSessionAndSendMessage 和 ChatStreamSend 中，我们设置了 SSE 响应头（ Content-Type: text/event-stream 、 Cache-Control: no-cache 、 Connection: keep-alive ），并通过 http.Flusher 接口实现数据的及时推送。
3. 每次推送后立即 Flush ：在流式回调函数中，每次调用 writer.Write() 后，都会紧接着调用 flusher.Flush() ，避免数据缓冲在服务端，让前端能实时看到打字机效果。
4. 避免在流式回调中做耗时操作 ：回调函数只做数据发送和 Flush 操作，AI 模型生成和消息存储是在另外的流程中完成的，不会阻塞流式推送。

从客户端角度看，这条连接在整个推送过程中确实是保持等待的，直到后端发送 [DONE] 标记后关闭连接才真正结束。

在代码中，通过StreamResponse函数不断刷新对应数据给到前端

```go
func (o *OpenAIModel) StreamResponse(ctx context.Context, messages []*schema.Message, cb StreamCallback) (string, error) {
    stream, err := o.llm.Stream(ctx, messages)
    if err != nil {
        return "", fmt.Errorf("openai stream failed: %v", err)
    }
    defer stream.Close()

    var fullResp strings.Builder

    for {
        msg, err := stream.Recv()
        if err == io.EOF {
            break
        }
        if err != nil {
            return "", fmt.Errorf("openai stream recv failed: %v", err)
        }
        if len(msg.Content) > 0 {
            fullResp.WriteString(msg.Content) // 聚合

            cb(msg.Content) // 实时调用cb函数，方便主动发送给前端
        }
    }

    return fullResp.String(), nil //返回完整内容，方便后续存储
}
```

**面试时的陈述性语句**

SSE 的实现我主要做了这几点：

1.首先设置正确的响应头，包括 Content-Type: text/event-stream ，告诉浏览器这是 SSE 响应；然后是 Cache-Control: no-cache ，禁用缓存确保数据实时； Connection: keep-alive 保持 TCP 连接不关闭，用于持续推送； Access-Control-Allow-Origin: * 处理跨域问题；最后是 X-Accel-Buffering: no ，防止 Nginx 代理缓冲数据，保证数据能立即推送给前端。

2.然后通过类型断言获取 http.Flusher 接口；每次向 response writer 写入数据后，立即调用 Flush() 方法，避免数据缓冲在服务端；同时避免在流式回调中执行耗时操作，保证数据能实时推送给前端。这样就实现了打字机效果，提升了用户体验。"

3.在流式响应时，需要将用户当前的问题存储到数据库，项目中通过Rabbitmq异步写入数据库的方式避免了响应过程中的阻塞，提高了响应速度。

###  5. 如果现在高并发请求聊天接口，模型调用耗时较长，你会如何进行超时控制和取消？使用 `context` 时有什么注意点？

**1. 超时控制：使用 context.WithTimeout 修改 Controller 层 ( controller/session/session.go )**

```go
import "time"  // 记得导入 time 包

func CreateSessionAndSendMessage(c *gin.Context) {
    req := new(CreateSessionAndSendMessageRequest)
    res := new(CreateSessionAndSendMessageResponse)
    userName := c.GetString("userName")
    if err := c.ShouldBindJSON(req); err != nil {
        c.JSON(http.StatusOK, res.CodeOf(code.CodeInvalidParams))
        return
    }

    // ==================== 关键代码开始 ====================
    // 1. 创建带超时的 context（例如 30 秒）
    timeoutCtx, cancel := context.WithTimeout(c.Request.Context(), 30*time.Second)
    defer cancel()  // 确保退出时取消，释放资源
    // ==================== 关键代码结束 ====================

    // 传递带超时的 context 给下游
    session_id, aiInformation, code_ := session.CreateSessionAndSendMessage(timeoutCtx, userName, req.UserQuestion, req.ModelType)

    if code_ != code.CodeSuccess {
        c.JSON(http.StatusOK, res.CodeOf(code_))
        return
    }

    res.Success()
    res.AiInformation = aiInformation
    res.SessionID = session_id
    c.JSON(http.StatusOK, res)
}
```

**2. 取消机制：利用请求上下文实现客户端断开时自动取消**

Gin 的 c.Request.Context() 会在客户端断开连接时自动取消！

Controller 层已经用了 c.Request.Context() 作为父 context，所以：

- 如果用户关闭浏览器或取消请求，context 会自动取消
- 下游的模型调用会收到取消信号，提前退出

示例：

controller层：

```go
func ChatStreamSend(c *gin.Context) {
    req := new(ChatSendRequest)
    userName := c.GetString("userName")
    if err := c.ShouldBindJSON(req); err != nil {
        c.JSON(http.StatusOK, gin.H{"error": "Invalid parameters"})
        return
    }

    // 设置 SSE 头
    c.Header("Content-Type", "text/event-stream")
    c.Header("Cache-Control", "no-cache")
    c.Header("Connection", "keep-alive")
    c.Header("Access-Control-Allow-Origin", "*")
    c.Header("X-Accel-Buffering", "no")

    // ==================== 直接传递 Gin 的 context ====================
    // c.Request.Context() 会在客户端断开时自动取消！
    code_ := session.ChatStreamSend(userName, req.SessionID, req.UserQuestion, req.ModelType, c.Request.Context(), http.ResponseWriter(c.Writer))
    // =================================================================

    if code_ != code.CodeSuccess {
        c.SSEvent("error", gin.H{"message": "Failed to send message"})
        return
    }

    c.Writer.Write([]byte("data: [DONE]\n\n"))
    c.Writer.Flush()
}
```

**使用 context 的注意点**

1. **传递原则**：context 必须从请求入口传递到最底层，确保整个调用链都能响应取消。
2. **资源清理**：使用 `defer cancel()` 确保 context 被正确取消，释放资源。
3. **错误处理**：检查 `context.Canceled` 或 `context.DeadlineExceeded` 错误，区分超时和主动取消。
4. **并发安全**：context 是线程安全的，可以在 goroutine 中安全使用。
5. **性能考虑**：超时时间需平衡用户体验和资源利用，避免过短导致频繁失败或过长占用资源。

**面试时的陈述性语句**

超时控制和取消我是这样做的：

首先在 Controller 层用 context.WithTimeout 创建一个带 30 秒超时的 context，用 defer cancel() 确保资源释放；

父 context 用 Gin 的 c.Request.Context() ，这样客户端断开时会自动取消；然后把这个 context 层层传递到最底层的模型调用；

在流式响应时，我还会通过 select 检查 ctx.Done() ，避免客户端断开后继续发送数据；

错误处理时区分 DeadlineExceeded 和 Canceled ，分别记录超时和客户端取消的日志。

### 6.Gin 框架内部路由查找机制是什么？为什么它比 net/http 更快？ 

Gin 框架的路由查找机制基于 **Radix Tree（压缩前缀树）** 实现，而标准库 `net/http` 使用的是一个 **线性遍历的路由表**。

在 Gin 中，每个 HTTP 方法（GET、POST 等）都有一棵独立的 Radix Tree，用于存储和查找路径节点。

当请求到来时，Gin 会：

1. 根据请求方法定位对应的 Radix Tree；
2. 从根节点开始按路径层级匹配；
3. 对参数路径（如 `/user/:id`）使用动态节点匹配；
4. 对通配符路径（如 `/static/*filepath`）使用通配节点匹配；
5. 最终直接拿到绑定的 handler。

这种树状结构可以在路径共享前缀较多的情况下，大幅减少匹配次数。

相比之下，`net/http` 的默认 `ServeMux` 是 **线性匹配**：

每次请求都会依次遍历所有注册的路由规则，找到最长前缀匹配的那一条，时间复杂度近似 O(n)，**n是路由规则数量**。

因此：

- Gin 路由查找是 **基于树的前缀匹配**，查找效率更高；
- `net/http` 是 **顺序遍历匹配**，在路由数量增多时性能会明显下降；
- 同时 Gin 在路由构建阶段会预处理路径参数、缓存节点结构，减少运行时开销。

简单来说：

**Gin 快的原因在于使用了 Radix Tree + 路由预编译 + 减少运行时字符串匹配。**

**补充：那么为什么不使用哈希表呢？**

理论上哈希表查找是 O(1)，但是在路由匹配这种场景下，**路径不是简单的固定字符串键值对**，而是有层级、参数、通配符等语义的结构。

**举个例子：**

- `/user/:id`
- `/user/profile`
- `/static/filepath`

**这些路径显然没法直接作为哈希表的 key 去匹配，因为：**

1. **存在动态路径参数（`:id`）：**
   **`/user/1`**、**`/user/2` **都要匹配同一个 handler。
   如果用哈希表，就得为所有可能的 id 生成 key，不现实。
2. **存在通配符匹配（`filepath`）：**
   **`/static/css/a.css`**、**`/static/js/b.js` **都走同一逻辑，哈希没法表达“前缀匹配”或“部分通配”。
3. **需要最长前缀匹配逻辑：**
   比如 **`/user/info`** 和 **`/user`**都存在时，Gin 要找到最“具体”的那条规则。
   哈希表没法表达“层级和优先级”关系。

所以 Gin 选择使用 **Radix Tree**（压缩前缀树）：

- **它既能快速匹配共享前缀（节省空间），**
- 又能灵活支持 **`:param`**、**`wildcard`**、**前缀优先**等复杂逻辑。

从性能上看，Radix Tree 查找路径的复杂度是 O(k)，其中 **k 是路径层数**（比如 **`/a/b/c` ** 就是 3 层），实际上在路由匹配场景下比哈希表更合适也更稳定。

### 7. 你是否自定义过中间件？实现了什么？中间件执行顺序如何控制？

Gin 的中间件执行顺序遵循 **洋葱模型**（Onion Model），按添加顺序从外到内执行：

1. **全局中间件**：在 `gin.Default()` 或 `r.Use()` 中添加，首先执行。
2. **分组中间件**：如 `AIGroup.Use(jwt.Auth())`，在路由分组级别添加，作用于该分组下的所有路由。
3. **路由级中间件**：在单个路由上添加，具有最高优先级。

- **请求进入**：中间件按添加顺序执行（正向）。
- **处理器执行**：所有中间件执行完毕后，调用路由处理器。
- **响应返回**：处理器完成后，中间件按逆序执行（反向），用于后处理（如日志记录）。

在项目中，有用到JWT 中间件，主要是应用于 `/AI`、`/image`  分组，确保这些接口需要认证，而 `/user` 分组无需认证。

### 8.项目中如何优雅地处理全局错误与日志追踪？如果要接入链路追踪（如 OpenTelemetry），你会怎么做？

首先我们来了解一下链路追踪是什么意思：

**以聊天接口为例：**

- 用户请求 `/api/v1/AI/chat/send`。
- 中间件创建 Trace，记录请求开始。
- JWT 验证、会话创建、AI 模型调用等各步骤生成子 Span。
- 如果模型调用超时或失败，可以快速定位问题点。

```

                    │                      Trace (整个请求的完整链路)                     │
                    │  trace_id: abc-123-xyz (唯一标识，贯穿整个请求)                     │
                    ├───────────────────────────────────────────────────────────────────┤
                    │                                                                   │
                    │  ┌──────────────────┐  ┌──────────────────┐  ┌─────────────────┐  │
                    │  │   Span 1         │  │   Span 2         │  │   Span 3        │  │
                    │  │  (JWT 验证)      │  │  (会话创建)       │  │  (AI 模型调用)   │  │
                    │  │  span_id: 111    │  │  span_id: 222    │  │  span_id: 333   │  │

                    └───────────────────────────────────────────────────────────────────┘
```

**作用**

1. **性能监控**：测量每个步骤的耗时，识别瓶颈（如 AI 模型响应慢）。
2. **错误调试**：关联错误日志，查看请求上下文，避免在日志中“海底捞针”。
3. **系统理解**：可视化服务依赖关系，帮助架构优化。
4. **故障排查**：在高并发时，追踪异常请求的完整路径。
5. **业务洞察**：统计接口调用频率、成功率等指标。

项目中全局错误与日志追踪的处理较为基础，没有使用专门的日志框架或全局错误处理机制。以下是基于代码分析的总结：

**当前错误处理方式**

1. **错误返回**：各层（controller、service）通过自定义错误码（如 `code.CodeServerBusy`）和消息返回错误。controller 使用 `res.CodeOf(code)` 统一响应格式。
2. **局部错误处理**：在 service 和 controller 中使用 `if err != nil` 进行检查，记录日志并返回错误码。没有全局 panic recover，导致未捕获的 panic 会导致程序崩溃。
3. **缺乏统一处理**：没有全局中间件捕获和处理错误，如 Gin 的 `Recovery()` 中间件未显式使用（`gin.Default()` 默认包含）。

## 第三阶段：认证与会话管理（JWT）

### 9. 你使用 JWT 做登录态维持，那为什么不使用 session？

在单体架构中，Session 通常存储在服务器内存中即可，因为所有请求都由同一台服务器处理。
但在微服务或分布式架构下，请求可能会被不同节点处理，如果每个节点各自维护 Session，就会导致**会话不一致**问题（例如用户在 A 节点登录，在 B 节点访问却变成未登录）。

因此，通常需要引入一个**集中式 Session 存储中间件**，如 **Redis、Memcached 或数据库**，来统一存储和共享 Session。
这样无论请求落在哪个服务节点，都能从同一数据源中读取 Session，实现**登录状态一致**。

这也是为什么在分布式场景下，很多系统更倾向使用 **JWT 等无状态认证方案**，因为它**不依赖集中存储**，天然适合水平扩展。

下面是区别表格：

| 特性         | **JWT（JSON Web Token）**                                    | **Session**                                             |
| ------------ | ------------------------------------------------------------ | ------------------------------------------------------- |
| **存储位置** | 客户端（LocalStorage、Cookie 或 Header）                     | 服务器端（内存、Redis、数据库）                         |
| **状态管理** | 无状态（Stateless），服务器不保存用户状态                    | 有状态（Stateful），服务器维护会话数据                  |
| **安全性**   | Token 自包含，支持签名校验；若被窃取可重放，需配合 HTTPS 使用 | Session ID 随机生成，依赖服务器安全；需防止会话固定攻击 |
| **扩展性**   | 适合分布式架构，无需共享状态或集中存储                       | 需在多节点间共享 Session（常用 Redis Cluster）          |
| **性能**     | 无需查询服务器存储，只需验证签名，解析速度快                 | 每次请求需查 Session 存储，存在额外 I/O 开销            |
| **过期控制** | Token 内含过期时间（exp），自动失效                          | 服务器维护过期机制，可灵活调整                          |
| **注销机制** | 主动失效较难（需黑名单机制），适合短期 Token                 | 可立即销毁 Session，支持主动注销                        |
| **数据体积** | Token 含 Payload，体积较大，传输开销略高                     | 仅传 Session ID，轻量高效                               |

###  10. JWT 如何防止被窃取后继续使用？你实现了 Token 过期/刷新策略吗？

针对窃取问题：

JWT（JSON Web Token）本身无法完全防止被窃取后继续使用，但可以通过多种安全措施和策略来降低风险。

**针对第一个问题**

1. **HTTPS 传输**：强制使用 HTTPS，确保 Token 在传输过程中不被中间人窃取。项目未显式配置 HTTPS，但生产环境应启用。
2. **签名验证**：JWT 使用 HMAC-SHA256 签名，服务器用密钥验证完整性。若 Token 被篡改，验证失败。
3. **短过期时间**：设置较短过期时间（如 1-24 小时），减少被窃取后的利用窗口。
4. **黑名单机制**（未实现）：存储失效 Token，在 Redis 中检查。若用户登出，可将 Token 加入黑名单。
5. **Token 版本控制**：在 Payload 中添加版本号，用户重新登录时更新版本，旧 Token 失效。
6. **IP/设备绑定**：在 Token 中包含客户端 IP 或设备指纹，请求时验证（需权衡便利性）。

**针对Token刷新策略：项目中并未实现，我们先来了解以下什么是Token刷新以及如何实现**

**Token 刷新（Token Refresh）** 就是指：当用户的登录凭证（Access Token）快要过期时，不让用户重新登录，而是用一个“**刷新凭证（Refresh Token）**”去申请一个新的 Token。

换句话说：

- **Access Token**：短期有效的通行证。
- **Refresh Token**：长期有效的备用钥匙。

这样就能在保证安全的同时，避免频繁让用户重新登录。

**典型流程如下**（例如在 JWT 或 OAuth2 中）：

1.用户登录后，服务器返回：

- 一个 **Access Token**（有效期短，比如 30 分钟）
- 一个 **Refresh Token**（有效期长，比如 7 天或 30 天）

2.当 Access Token 过期时，前端不会让用户重新输入账号密码，
而是携带 **Refresh Token** 调用接口：

```plain
POST /auth/refresh
Authorization: Bearer <refresh_token>
```

3.服务器验证 Refresh Token 合法后，签发一个新的 Access Token 返回。

4.新 Token 生效，用户无感继续使用。

###  11. 如果 JWT 被盗，服务器如何主动让它失效？（考验黑名单 / TTL / Redis 标记策略）

JWT 是无状态的，一旦签发后，服务器本身不会保存它的状态，所以服务器无法像 Session 一样主动让某个 JWT 立即失效。

但在实际系统中，我们通常会结合 黑名单机制 或 短 TTL + 刷新策略 来实现“可控失效”，主要有三种常见做法：

**方案一：黑名单（Blacklist）**

**思路：**

- 当发现 Token 被盗、用户登出、管理员强制下线等场景时，将该 JWT 的唯一标识（如 `jti` 字段或 Token 本身）存入 **Redis 黑名单**。
- 每次请求验证 JWT 时，除了验签，还要检查它是否在黑名单中。

```
┌──────────────────────────────────────────────────────────────────┐
│                        黑名单机制完整流程                         │
└──────────────────────────────────────────────────────────────────┘

【场景1：正常请求】
  客户端 ──→ 携带 Token ──→ 服务端
                              │
                              ├→ 验证签名 ✓
                              ├→ 检查过期 ✓
                              ├→ 查 Redis 黑名单 → 不存在 ✓
                              └→ 允许访问

【场景2：用户登出后再次请求】
  用户点击登出 ──→ Token jti 存入 Redis 黑名单
                              │
  客户端 ──→ 携带同一 Token ──→ 服务端
                              │
                              ├→ 验证签名 ✓
                              ├→ 检查过期 ✓
                              ├→ 查 Redis 黑名单 → 存在！❌
                              └→ 拒绝访问（401）

【场景3：黑名单自动清理】
  Redis 中的黑名单项 ──→ 设置 TTL = Token 剩余有效期
                              │
                        Token 自然过期后
                              │
                        Redis 自动删除该项 ✓
                        （无需手动清理）
```

**方案二：短 TTL + Refresh Token**

**思路：**

- Access Token 设置较短有效期（如 30 分钟）。
- 当快过期时，用 Refresh Token 重新获取新的 Access Token。
- 如果发现盗用，可以直接**废弃 Refresh Token**，让新 Token 无法再刷新。

**优点：**

- 不需要存储黑名单，Access Token仍保持无状态。（但Refresh Token依然需要存储在服务端）

**缺点：**

- Access Token 被盗后，在过期前仍可被使用一段时间。

| Token 类型    | 客户端存储 | 服务端存储           | 无状态？ |
| ------------- | ---------- | -------------------- | -------- |
| Access Token  | ✅ 是       | ❌ 否                 | ✅ 无状态 |
| Refresh Token | ✅ 是       | ✅ 是（数据库/Redis） | ❌ 有状态 |

```
┌─────────────────────────────────────────────────────────────────┐
│                    Refresh Token 完整流程                        │
└─────────────────────────────────────────────────────────────────┘

【签发阶段】
  用户登录 ──→ 服务端生成 Refresh Token ──→ 存入数据库/Redis
                      │
                      └──→ 同时返回给客户端存储

【刷新阶段】
  客户端 ──→ 携带 Refresh Token ──→ 服务端
                                      │
                                      ├→ 查数据库/Redis 验证是否存在
                                      ├→ 检查是否被标记为失效
                                      └→ 有效则签发新 Access Token

【废弃阶段】
  发现盗用/用户登出 ──→ 服务端更新数据库/Redis
                          │
                          ├→ 标记该 Refresh Token 为失效
                          └→ 或删除该记录
                          │
                          下次客户端尝试刷新 ──→ ❌ 拒绝
```

**方案三：Token 版本号（Version 或 TokenVersion）**

**思路：**

- 在用户表中维护一个 `token_version` 字段。
- 签发 JWT 时把当前版本号写入 Token。
- 如果发现异常登录、盗号、登出，就把数据库中的版本号加 1。
- 校验时若 Token 的版本号 ≠ 用户当前版本号，则认为失效。

**优点：**

- 只需一次数据库比对，逻辑简单高效。

**缺点：**

- 需每次验证时查询数据库（可缓存）。

```
┌─────────────────────────────────────────────────────────────────────────────┐
│                           JWT + Refresh Token 完整流程                       │
└─────────────────────────────────────────────────────────────────────────────┘

【登录】
  客户端 ──→ POST /login ──→ 服务端
                              │
                              ├→ 验证密码 ✓
                              ├→ 生成 Access Token（无状态，30 分钟）
                              ├→ 生成 Refresh Token（有状态，7 天）
                              ├→ 存储 Refresh Token 到 Redis ✓
                              └→ 返回两个 Token 给客户端

【正常请求】
  客户端 ──→ 携带 Access Token ──→ 服务端
                                    │
                                    ├→ 验证签名 ✓
                                    ├→ 检查黑名单 ✓
                                    └→ 允许访问

【Access Token 过期后刷新】
  客户端 ──→ POST /refresh + Refresh Token ──→ 服务端
                                                │
                                                ├→ 查 Redis 验证 Refresh Token 存在 ✓
                                                ├→ 检查是否被废弃 ✓
                                                ├→ 生成新 Access Token
                                                └→ 返回新 Access Token

【发现盗用/用户登出】
  客户端/管理员 ──→ POST /logout ──→ 服务端
                                      │
                                      ├→ Access Token jti 加入 Redis 黑名单
                                      ├→ Refresh Token 标记为 Revoked=true
                                      └→ 下次请求/刷新 ──→ ❌ 拒绝

【管理员强制下线】
  管理员 ──→ POST /revoke-all/{userID} ──→ 服务端
                                            │
                                            ├→ 方案 A：废弃该用户所有 Refresh Token
                                            ├→ 方案 B：用户 token_version +1
                                            └→ 所有旧 Token 立即失效
```

**三种方案对比**

| 方案          | 服务端存储        | 废弃速度       | 性能             | 适用场景       |
| ------------- | ----------------- | -------------- | ---------------- | -------------- |
| 黑名单        | Redis 存 jti      | 立即生效       | 高（Redis O(1)） | 高安全要求     |
| Refresh Token | Redis/DB 存 Token | 下次刷新时生效 | 中（需查存储）   | 平衡安全与性能 |
| 版本号        | DB 存 version     | 下次验证时生效 | 低（每次查 DB）  | 用户少或可缓存 |

## 第四阶段：数据库与缓存优化（MySQL + Redis）

### 12. Go 中如何管理数据库连接池？你设置了哪些参数？为什么？

Go 中数据库连接池通过 `database/sql` 包管理，项目使用 GORM（基于 `database/sql` 的 ORM）连接 MySQL。连接池自动处理连接的创建、复用和关闭，无需手动管理。

**连接池管理方式**

1. 底层机制：`database/sql` 维护一个连接池，包含空闲和活跃连接。执行查询时，从池中获取连接，用完后归还。
2. GORM 集成：项目在 `common/mysql/mysql.go` 中通过 `gorm.Open()` 初始化，获取底层 `*sql.DB` 实例进行池配置。

**项目设置了以下连接池参数（在 `InitMysql()` 中）：**

```go
sqlDB, _ := db.DB()
sqlDB.SetMaxIdleConns(10)          // 最大空闲连接数
sqlDB.SetMaxOpenConns(100)         // 最大打开连接数
sqlDB.SetConnMaxLifetime(time.Hour) // 连接最大生命周期
```

1.**SetMaxIdleConns(10)**：

- **作用**：池中保持的最大空闲连接数。超过此数，空闲连接被关闭。
- **为什么**：避免连接过多占用资源。10 个足够处理中等并发，减少连接创建开销。太少会导致频繁创建/销毁，太多浪费内存。

2.**SetMaxOpenConns(100)**：

- **作用**：允许的最大打开连接数（包括活跃和空闲）。超出时，新请求排队等待。
- **为什么**：防止数据库过载。100 适合高并发场景（如聊天接口），基于数据库服务器能力调整。太高可能导致 DB 拒绝连接，太低限制吞吐量。

3.**SetConnMaxLifetime(time.Hour)**：

- **作用**：单个连接的最大存活时间，过期后强制关闭并重建。
- **为什么**：避免长时间连接导致的网络问题（如防火墙断开）或状态不一致。1 小时平衡了稳定性和资源刷新。太短增加开销，太长风险积累（**长时间复用同一连接，会让隐性的网络、状态、资源问题不断叠加**）。

## 第五阶段：异步消息处理（RabbitMQ）

### 15. 你为什么选择 RabbitMQ 而不是 Kafka？

在这个项目中，我选择 RabbitMQ 而不是 Kafka，主要基于以下几个原因：

首先， 消息量和功能需求匹配 。项目中的消息主要是聊天记录的异步存储，消息量不大，也不需要复杂的流处理。RabbitMQ 对中小规模消息队列的支持非常成熟，而 Kafka 更适合大规模的日志流或事件驱动场景，用在这个项目里有点过重。

其次， 路由和可靠性 。虽然项目中只用了简单的 Work Queue 模式，但 RabbitMQ 提供了消息持久化、ACK 确认机制，能保证消息不丢失。这对聊天记录存储很重要，我们不希望用户的聊天记录因为服务重启而丢失。

然后是 学习和运维成本 。RabbitMQ 单节点就能跑，部署和运维简单，还有内置的 Web 管理界面方便监控。Kafka 需要依赖 ZooKeeper，集群配置也复杂很多，对于这个项目来说，初期用 RabbitMQ 更快速落地。

最后是 生态和社区 。RabbitMQ 在 Go 语言中的客户端支持很好，我们用的 github.com/streadway/amqp 库非常成熟，集成成本低。

当然，如果未来消息量激增到百万级以上，我也会考虑切换到 Kafka 或者 RabbitMQ 集群，但就当前项目阶段来说，RabbitMQ 是更合适的选择。

**补充：如果你希望消息队列尽可能地轻，怎么不用redis的list来实现消息队列呢？redis不是也支持RDB和AOF持久化吗？它也能保证数据不会丢失啊。**

确实，Redis List 也可以做轻量级消息队列，而且我也考虑过这个方案。但最终选择 RabbitMQ 主要是基于可靠性的考虑。

Redis List 的消息消费是基于 RPOP 的，一取出消息就从队列中移除了，如果处理失败或服务重启，消息容易丢失。虽然可以自己实现 ACK 和重试机制，但这相当于重新造轮子。

而 RabbitMQ 原生就支持这些功能，包括消息持久化、ACK 确认、死信队列等，对聊天记录这种不能丢的数据来说，可靠性更重要。当然，如果只是做简单的任务队列，Redis List 是没问题的，但这个项目中我更看重消息的可靠性。

### 17. 消费者并发消费如何做？如何避免消息乱序或重复消费？ 

**理论上如何确保高并发消费的可靠性**

如果要进一步确保高并发消费的可靠性，通常会从以下几个方面考虑：

 a) 消息持久化

将队列和消息都设置为持久化，这样 RabbitMQ 重启后消息不会丢失。

 b) 手动确认（Ack）

不用自动确认，而是等业务处理成功后手动发送 Ack，这样即使消费者崩溃了，消息也会重新入队。

 c) 死信队列（DLQ）

如果消息处理失败多次，就把它放到死信队列，后续人工介入处理，避免无限重试。

 d) 消费者数量控制

根据服务器性能合理控制消费者数量，避免过度并发导致资源耗尽。

 e) 连接和 Channel 管理

保持连接复用，每个线程/协程用自己的 Channel，避免 Channel 并发安全问题。

 f) 消息幂等性

在消费端做幂等处理，即使同一条消息被消费多次，也不会重复写入数据库。

**针对消息乱序**

RabbitMQ 默认是“尽力顺序”的，并**不保证严格顺序**，原因是：

- 多个消费者并行时，消费速度不同；
- 网络抖动或 ACK 延迟都会打乱顺序。

🔸 常见解决策略：

| 场景             | 解决方案                                                     |
| ---------------- | ------------------------------------------------------------ |
| **需要全局顺序** | 只能使用 **单队列 + 单消费者**，串行消费（吞吐量低）         |
| **需要局部顺序** | 按业务 Key（如订单 ID、用户 ID）哈希路由到**不同队列**，每个队列一个消费者，保证局部顺序 |

项目当前没有做完整的顺序保证，RabbitMQ 消费失败会 panic，消息会丢失。如果要保证顺序，我考虑过几种方案：

1. 禁止 NACK 重试 ：最简单，但失败消息会丢失
2. 死信队列 ：失败消息进入 DLQ，不会重试也不会丢失，推荐
3. 消息带序列号 ：消费端缓存并排序，复杂但能保证顺序
4. 消息带时间戳，消费端按时间戳排序后再插入数据库，这样不需要多个队列，实现也更简单。
5. 按 sessionID 哈希分队列 ：保证局部有序，实现稍复杂

**针对重复消费**

1. 使用手动确认（Manual ACK）

只有当业务逻辑真正处理成功后再 ACK，否则 MQ 会重新投递。

```go
ch.Consume(queue, "", false, false, false, false, msgs)
for msg := range msgs {
    if handle(msg.Body) {
        msg.Ack(false)   // 确认成功
    } else {
        msg.Nack(false, true) // 失败，要求重投
    }
}
```

2. 幂等消费

利用消息 ID 去重，防止同一消息重复执行。

```go
if redis.SetNX("msg:"+msg.MessageId, 1, 1*time.Hour) {
    // 首次消费
    process()
    msg.Ack(false)
} else {
    // 重复消费，直接确认跳过
    msg.Ack(false)
}
```

## 第六阶段：AI 模型调用与架构设计

### 18. 你提到支持 OpenAI 和 Ollama，多模型切换的具体设计是怎样的？

- 工厂模式
- 接口抽象

项目支持 OpenAI、Ollama 等多模型切换，设计采用了**接口抽象**和**工厂模式**的组合，确保灵活性和可扩展性。

**接口抽象**

1.**AIModel 接口**：定义统一契约，所有模型实现该接口。

```go
type AIModel interface {
    GenerateResponse(ctx context.Context, messages []*schema.Message) (*schema.Message, error)
    StreamResponse(ctx context.Context, messages []*schema.Message, cb StreamCallback) (string, error)
    GetModelType() string
}
```

- **好处**：抽象差异，调用方无需关心具体实现。支持同步/流式响应。

2.**具体实现**：

- `OpenAIModel`：封装 OpenAI API 调用。
- `OllamaModel`：封装 Ollama 本地模型。

**工厂模式**

1.**AIModelFactory**：负责模型创建，使用注册机制。

```go
type AIModelFactory struct {
    creators map[string]ModelCreator // modelType -> 创建函数
}
```

- **注册**：`registerCreators()` 预注册模型类型（如 "1" 为 OpenAI，"2" 为 Ollama）。
- **创建**：`CreateAIModel(ctx, modelType, config)` 根据类型动态创建实例。
- **扩展性**：`RegisterModel()` 允许运行时注册新模型。

2.**AIHelper 封装**：工厂创建模型后，包装为 `AIHelper`，管理会话的历史消息。

切换机制

- **运行时切换**：前端传递 `modelType`（如 "1"），`AIHelperManager.GetOrCreateAIHelper()` 调用工厂创建对应模型。
- **会话隔离**：每个用户会话绑定一个 `AIHelper`，模型切换不影响其他会话。

#### 设计思路

**第一步：为什么要用策略模式 + 接口抽象？**

这本质上就是策略模式的场景！

**策略模式解决的问题是：有一组算法（这里就是不同的 AI 模型），它们可以互相替换，让具体的策略/代码实现独立于调用它的客户端。**

如果不用策略模式，代码会写成这样：

```go
        // OpenAI 的流式逻辑
        stream, err := m.openaiLLM.Stream(ctx, messages)

        var fullResp strings.Builder
        for {
            msg, err := stream.Recv()
            if err == io.EOF {

            }
            if err != nil {

            }
            if len(msg.Content) > 0 {
                fullResp.WriteString(msg.Content)
                cb(msg.Content)
            }
        }
        return fullResp.String(), nil
    } else if m.modelType == "2" {
        // Ollama 的流式逻辑（和 OpenAI 几乎一样，但要重复写一遍）

        for {
            msg, err := stream.Recv()
            if err == io.EOF {
                break
            }

            }
        }
```

这个反例的问题：

1. 代码重复：OpenAI 和 Ollama 的逻辑几乎一样，但要写两遍
2. 耦合度高：所有模型逻辑混在一起
3. 难扩展：加新模型（如 Claude）要改所有 if-else 的地方
4. 难测试：没法单独测试某个模型

所以我们需要一个统一的接口，让所有模型都实现这个接口，调用方只依赖接口，不依赖具体实现。这就是接口抽象的价值。

**第二步：为什么要用工厂模式？**

有了接口还不够，谁来创建具体的模型对象？

如果每次调用都自己写：

1. 创建逻辑重复：OpenAI 和 Ollama 的创建逻辑散落在各处
2. 违反开闭原则：加新模型要改 GetOrCreateAIHelper 函数
3. 难以维护：创建逻辑不在一个地方，改一个地方要改多处

所以我们用工厂模式，把所有模型的创建逻辑集中到一个地方，用一个 map 注册表，模型类型对应创建函数。这样加新模型只需要在工厂里注册一下，不用改调用方的代码。

**第三步：为什么要有 AIHelper？**

有了模型还不够，每个会话还需要：

- 保存聊天记录
- 管理消息的存储
- 统一调用模型的入口

**如果这些逻辑散落在 controller 里，代码会很乱。**

所以我们设计 AIHelper，一个会话对应一个 AIHelper，它负责：

1. 持有 AIModel 接口
2. 保存该会话的消息历史
3. 提供统一的 GenerateResponse 和 StreamResponse 方法
4. 处理消息的存储逻辑

**第四步：为什么要有 AIHelperManager？**

现在有了 AIHelper，但谁来管理所有用户的所有会话？

我们需要：

- 一个用户可以有多个会话
- 同一个会话多次请求，应该复用同一个 AIHelper
- 线程安全的管理

所以我们设计 AIHelperManager，用双层 map：map[用户]map[会话ID]AIHelper，来管理所有的 AIHelper。

### 19. 流式响应如何与前端 Server-Sent Events (SSE) 结合？

流式响应与 SSE 结合

1.**SSE 设置**：

- **头部配置**：`Content-Type: text/event-stream`，`Cache-Control: no-cache`，`Connection: keep-alive`，`X-Accel-Buffering: no`（禁用代理缓冲，确保实时性）。
- **数据格式**：`data: {content}\n\n`，前端通过 `EventSource` 监听。

2.**流式生成**：

- `AIHelper.StreamResponse()` 调用模型流式 API，返回回调函数 `cb`。
- `cb` 在 `StreamMessageToExistingSession` 中实现，实时发送数据：

```go
	cb := func(msg string) {
		// 直接发送数据，不转义
		// SSE 格式：data: <content>\n\n
		log.Printf("[SSE] Sending chunk: %s (len=%d)\n", msg, len(msg))
		_, err := writer.Write([]byte("data: " + msg + "\n\n"))
		if err != nil {
			log.Println("[SSE] Write error:", err)
			return
		}
		flusher.Flush() //  每次必须 flush
		log.Println("[SSE] Flushed")
	}
```

- 结束时发送 `data: [DONE]\n\n`。

3.**前端集成**：

- 前端使用 `EventSource` 连接 SSE 端点，逐块显示 AI 响应。
- 支持会话 ID 先发送，确保前端及时绑定会话。

**面试时可以说的陈述性语句**

1.首先设置正确的响应头，包括 Content-Type: text/event-stream ，告诉浏览器这是 SSE 响应；然后是 Cache-Control: no-cache ，禁用缓存确保数据实时； Connection: keep-alive 保持 TCP 连接不关闭，用于持续推送； Access-Control-Allow-Origin: * 处理跨域问题；最后是 X-Accel-Buffering: no ，防止 Nginx 代理缓冲数据，保证数据能立即推送给前端。

2.然后通过类型断言获取 http.Flusher 接口；回调函数内部：每次Eino框架的model.ToolCallingChatModel.Stream()一返回字符就向 ResponseWriter 写入数据，然后立即调用 Flush() 方法，避免数据缓冲在服务端；同时避免在流式回调中执行耗时操作，保证数据能实时推送给前端。这样就实现了打字机效果，提升了用户体验。"

3.在流式响应时，需要将用户当前的问题存储到数据库，项目中通过Rabbitmq异步写入数据库的方式避免了响应过程中的阻塞，提高了响应速度。

### 20. 模型上下文由谁来维护？

项目中模型上下文（对话历史）由多个组件协同维护，确保内存效率和持久化。

1. **AIHelper（内存维护）**：

- `common/aihelper/aihelper.go` 中的 `AIHelper` 结构体维护 `messages []*model.Message`，存储当前会话的对话历史。
- 每次调用 `GenerateResponse` 或 `StreamResponse` 时，添加用户消息和 AI 回复到内存列表。
- 上下文传递给 Eino 框架：`utils.ConvertToSchemaMessages(a.messages)` 转换为 `[]*schema.Message`，供模型推理使用。

1. **Eino 框架（推理时使用）**：

- Eino 处理消息转换和模型调用，上下文作为消息列表传递给底层 LLM（如 OpenAI/Ollama）。
- 支持角色区分（User/Assistant），确保对话连贯。

1. **Message 表（持久化存储）**：

- `dao/message/message.go` 和 `model/message.go` 定义消息结构。
- 每次消息生成后，通过 RabbitMQ 异步插入数据库，确保历史可查询和恢复。
- 字段：`SessionID`、`UserName`、`Content`、`IsUser`、`CreatedAt`。

### 为什么选 SSE 做流式响应？

1. SSE 基于 HTTP 协议，不用额外配置端口，兼容性比 WebSocket 更好；
2. SSE 自带自动重连机制，前端不用自己写重连逻辑，开发成本低；
3. AI 响应是 “服务器单向推给前端”，SSE 刚好适配这种单向流式场景，没必要用双向的 WebSocket。

| 维度       | SSE（服务器发送事件）            | WebSocket                                |
| ---------- | -------------------------------- | ---------------------------------------- |
| 通信方向   | 单向（仅服务器 → 客户端）        | 双向（服务器↔客户端）                    |
| 底层协议   | 基于 HTTP 协议（特殊用法）       | 独立的 WebSocket 协议（握手阶段用 HTTP） |
| 连接特点   | HTTP 长连接，文本流传输          | TCP 长连接，支持二进制 / 文本传输        |
| 自动重连   | 自带（客户端原生支持）           | 无原生重连，需自己写逻辑                 |
| 兼容性     | 所有现代浏览器支持，低版本也兼容 | 大部分浏览器支持，但需处理兼容降级       |
| 开发复杂度 | 低（只需处理服务器推数据）       | 高（需处理双向通信、重连、心跳）         |
| 适用场景   | 单向流式推送（AI 回答、通知）    | 双向实时交互（聊天、协作、游戏）         |

**面试时可以说的陈述性语句**

“AI 流式响应是服务器单向给前端推数据，SSE 刚好适配这种场景，而且它基于 HTTP 协议，开发成本低、自带自动重连，不用像 WebSocket 那样自己处理双向通信和重连逻辑，能更快落地；如果需要前端中途暂停 AI 回答这种双向交互，再考虑用 WebSocket 更合适。”

### 如何确保AIHelper不会越堆越多最终导致 OOM ？

用Redis缓存AIHelper元数据，每次获取AIHelper的时候先去AIHelperManager大map里通过全局唯一`sessionID`获取AIHelper，

若获取到了就返回并更新Redis中该键的TTL，

若获取不到，说明该键已经过期了，需要从数据库中读取该AIHelper，

若能读取到该AIHelper，则加载这个AIHelper到AIHelperManager，并将该AIHelper的标识记录到Redis中，

若读取不到，则创建新AIHelper并将该AIHelper的标识记录到Redis中，并设置TTL。

#### 数据流向图

```
用户请求 → 查内存缓存 → 命中 → 返回 AIHelper → 同时刷新Redis元数据TTL
                    ↓ 未命中
                    查数据库会话表 → 存在 → 重建元数据 → 重建 AIHelper → 设置Redis元数据（用于过期标记）→ 返回
                                 ↓ 不存在  
                                创建新会话 → 保存元数据到 Redis → 返回
```

Redis 只用于过期标记，不用于会话重建

```go

import (
	"context"
	"encoding/json"
	"fmt"
	"log"
	"sync"
	"time"
	
	"GopherAI/common/redis"

// SessionTombstone Redis中的会话墓碑标记
type SessionTombstone struct {
	SessionID  string    `json:"session_id"`
	UserName   string    `json:"user_name"` 
	CreateTime time.Time `json:"create_time"`
}

// AIHelperManager 修正版本：Redis只用于标记
type AIHelperManager struct {
	helpers map[string]*AIHelper
	mu      sync.RWMutex
	
	// Redis用于分布式协调
	redisClient *redis.Client
	
	// 配置
	sessionTimeout  time.Duration
	cleanupInterval time.Duration
	stopCleanup     chan struct{}
}

// GetOrCreateAIHelper 修正逻辑
func (m *AIHelperManager) GetOrCreateAIHelper(userName, sessionID, modelType string, config map[string]interface{}) (*AIHelper, error) {
	m.mu.Lock()
	defer m.mu.Unlock()

	// 1. 查内存（唯一缓存层）
	if helper, exists := m.helpers[sessionID]; exists {
		helper.lastAccess = time.Now()
		return helper, nil
	}

	// 2. 直接查数据库（跳过Redis查询！）
	sessionExists, err := session.SessionExists(sessionID)
	if err != nil {
		return nil, err
	}

	if sessionExists {
		// 3. 从数据库重建AIHelper
		helper, err := m.rebuildFromDB(userName, sessionID, modelType, config)
		if err != nil {
			return nil, err
		}

		// 4. 设置Redis墓碑标记（用于分布式清理协调）
		m.setTombstone(sessionID, userName)
		
		log.Printf("[AIHelperManager] Rebuilt from DB and set tombstone: %s", sessionID)
		return helper, nil
	}

	// 5. 创建新会话
	helper, err := m.createNewHelper(userName, sessionID, modelType, config)
	if err != nil {
		return nil, err
	}

	// 6. 新会话也要设置墓碑标记
	m.setTombstone(sessionID, userName)
	
	return helper, nil
}

// setTombstone 设置Redis墓碑标记
func (m *AIHelperManager) setTombstone(sessionID, userName string) error {
	tombstone := &SessionTombstone{
		SessionID:  sessionID,
		UserName:   userName,
		CreateTime: time.Now(),
	}
	
	data, err := json.Marshal(tombstone)
	if err != nil {
		return err
	}
	
	key := fmt.Sprintf("ai:session:tombstone:%s", sessionID)
	// 设置TTL，比sessionTimeout稍长，确保清理时能检测到
	return m.redisClient.SetEx(context.Background(), key, data, m.sessionTimeout + 1*time.Minute).Err()
}

// cleanupExpiredHelpers 修正的清理逻辑
func (m *AIHelperManager) cleanupExpiredHelpers() {
	m.mu.Lock()
	defer m.mu.Unlock()

	now := time.Now()
	cleanedCount := 0

	for sessionID, helper := range m.helpers {
		// 方法1：检查内存中的访问时间
		if now.Sub(helper.lastAccess) > m.sessionTimeout {
			delete(m.helpers, sessionID)
			cleanedCount++
			log.Printf("[cleanup] Removed by memory timeout: %s", sessionID)
			continue
		}

		// 方法2：检查Redis墓碑标记是否还存在
		// 如果Redis标记已过期，说明其他实例认为这个会话该清理了
		key := fmt.Sprintf("ai:session:tombstone:%s", sessionID)
		exists, err := m.redisClient.Exists(context.Background(), key).Result()
		if err != nil {
			log.Printf("[cleanup] Redis error for %s: %v", sessionID, err)
			continue
		}

		if exists == 0 {
			// Redis标记已过期，清理内存中的会话
			delete(m.helpers, sessionID)
			cleanedCount++
			log.Printf("[cleanup] Removed by Redis tombstone expiration: %s", sessionID)
		}
	}

	if cleanedCount > 0 {
		log.Printf("[cleanup] Cleaned %d sessions", cleanedCount)
	}
}
```

**TTL 工作机制**

1. 每次访问刷新 Redis TTL （30 分钟）
2. Redis 自动删除过期元数据
3. `AIHelper回收协程`轮询检测过期的AIHelper对象，当检测到 Redis 元数据消失后，清理对应 AIHelper
4. MySQL 中的消息记录永久保存

### 2：你在实现AI流式响应时遇到了哪些挑战？

- **并发管理和资源竞争**：在多用户并发访问AI助手时，确保goroutine安全访问共享资源（如消息历史）是一个主要挑战。通过读写锁（sync.RWMutex）保护消息切片，避免数据竞争，同时优化锁粒度以提升性能。
- **流式数据实时输出**：保证AI模型流式响应实时推送到前端，避免阻塞主线程。使用回调函数（StreamCallback）在SSE（Server-Sent Events）中即时发送数据块，减少用户感知延迟。
- **异步存储防止阻塞**：在流式响应过程中，消息存储采用RabbitMQ异步队列，避免同步写数据库导致的阻塞，提升高并发下的响应速度。
- **模型切换与扩展性**：支持多种AI模型动态切换，需要工厂模式管理模型创建，确保新模型易于集成而不影响现有功能。
- **性能调优**：在高负载下，优化goroutine数量和内存使用，避免资源泄漏。使用连接池管理数据库和缓存连接，减少开销。
- **资源管理**：在并发场景下，管理AI助手实例和会话映射，使用单例管理器防止重复创建，同时实现清理机制释放闲置资源。

### 3：你在实现基于Gin框架的高性能HTTP服务器时遇到了哪些挑战？

- **多线程并发处理**：确保多goroutine环境下的线程安全是一个主要挑战。需要仔细设计锁机制，以避免竞争条件和死锁，同时最大化并发性能。

### 如果用户在请求的时候狂点几下，后端怎么做能防止这种情况导致的bug？

**一、当前代码的实际情况**

如果用户狂点发送，会发生什么：

2. 多个 AI 模型调用同时进行 - 浪费 API 额度，增加成本
3. 消息历史可能混乱 - 多个请求同时调用 AddMessage() ，消息顺序可能不对
4. 前端收到多个混乱的流式响应 - 用户体验差

**1. AIHelper 没有会话级别的互斥锁**

看 aihelper/aihelper.go:12-19 ：

当前项目后端没有针对用户重复点击的情况做专门处理，但可以通过以下几种方式改进：

### 怎么防止MQ消息积压？

**问题 1：增加消费者**

直接从同一个队列多开几个消费者 goroutine 就行

思路：RabbitMQ 的 Work Queue 模式本身就支持 多个消费者从同一个队列拿消息 ，RabbitMQ 会自动做负载均衡（轮询或公平分发）。

```go
msgs, err := r.channel.Consume(...)  // msgs 是 Go 原生 channel，安全！

// 可以启动多个 goroutine 同时从 msgs 读！
go func() {
    for msg := range msgs {
        handle(msg)
    }
}()

go func() {
    for msg := range msgs {
        handle(msg)
    }
}()

// ... 更多 goroutine
```

项目里的做法：

- 现在只有 1 个 goroutine 跑 RMQMessage.Consume(MQMessage)
- 要增加消费者，只需要多 go 几次！

**问题 2：怎么在单个消费者内部开多个 goroutine 提高处理能力？**

思路：从 channel 拿到消息后，不直接处理，扔给 goroutine 池去处理！

思路概述：

1. 从 msgs channel 拿消息 （这个还是单 goroutine 拿，因为 msgs 本身是并发安全的）
2. 拿到消息后，不直接调用 MQMessage(msg) ，而是启动一个 goroutine 去处理，或者用 worker pool
3. 注意 ACK 时机 ：等 goroutine 处理完了，再手动 ACK（如果改成手动确认模式的话）

简单说：

```go
// 原流程：
for msg := range msgs {
    MQMessage(&msg)  // 单 goroutine 处理，慢
}

// 优化后：
for msg := range msgs {
    go func() {  // 扔给新 goroutine 处理
        MQMessage(&msg)
    }()
}
```

或者用 worker pool（更可控）：

- 启动固定数量的 worker goroutine
- 从 msgs 拿消息，发送给 worker channel
- worker 从 channel 拿消息处理

```go
func (r *RabbitMQ) Consume(handle func(msg *amqp.Delivery) error) {
    // ... 前置代码 ...
    msgs, err := r.channel.Consume(...)
    
    // 启动 worker pool（比如 4 个 worker）
    workerCh := make(chan *amqp.Delivery, 100)
    for i := 0; i < 4; i++ {
        go func() {
            for msg := range workerCh {  // worker 从这里拿消息
                handle(&msg)
            }
        }()
    }
    
    // 主 goroutine 只负责从 RabbitMQ 拿消息，扔给 worker
    for msg := range msgs {
        workerCh <- &msg  // 扔给 worker pool，不阻塞！
    }
}
```

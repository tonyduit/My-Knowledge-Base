# Go内存管理

> 导语：现代高级编程语言管理内存的方式分自动和手动两种。手动管理内存的典型代表是C和C++，编写代码过程中需要主动申请或者释放内存；而Java 和Go等语言使用自动的内存管理系统，由内存分配器和垃圾收集器来代为分配和回收内存，开发者只需关注业务代码而无需关注底层内存分配和回收，虽然语言帮我们处理了这部分但是还是有必要去了解一下底层的架构设计和执行逻辑，这样可以更好的掌握一门语言，本文主要以go内存管理为切入点再到go垃圾回收，系统的讲解一下go自动内存管理系统的设计和原理，由于篇幅有限略去了go垃圾回收三色标记屏障技术这一块，有兴趣的推荐去看下《go语言设计和实现》。此文目的是抛砖引玉，欢迎各位交流探讨。

## 一、TCMalloc

go内存管理是借鉴了TCMalloc的设计思想，TCMalloc 全称 Thead-Caching Malloc，是google开发的内存分配器，为了方便理解下面的go内存管理，有必要要先熟悉一下TCMalloc。

![image-20260401205056494](Go%E5%86%85%E5%AD%98%E7%AE%A1%E7%90%86.assets/image-20260401205056494.png)

### 1.1 Page
操作系统对内存管理以页为单位，TCMalloc也是这样，只不过TCMalloc里的Page大小与操作系统里的大小并不一定相等，而是倍数关系。

### 1.2 Span

一组连续的Page被称为Span，比如可以有4个页大小的Span，也可以有8个页大小的Span，Span比Page高一个层级，是为了方便管理一定大小的内存区域，Span是TCMalloc中内存管理的基本单位。

### 1.3  ThreadCache
每个线程各自的Cache，一个Cache包含多个空闲内存块链表，每个链表连接的都是内存块，同一个链表上内存块的大小是相同的，也可以说按内存块大小，给内存块分了个类，这样可以根据申请的内存大小，快速从合适的链表选择空闲内存块。由于每个线程有自己的ThreadCache，所以ThreadCache访问是无锁的。

### 1.4 CentralCache
是所有线程共享的缓存，也是保存的空闲内存块链表，链表的数量与ThreadCache中链表数量相同，当ThreadCache内存块不足时，可以从CentralCache取，当ThreadCache内存块多时，可以放回CentralCache。由于CentralCache是共享的，所以它的访问是要加锁的。

### 1.5 PageHeap

PageHeap是堆内存的抽象，PageHeap存的也是若干链表，但链表保存的是Span，当CentralCache没有内存的时，会从PageHeap取，把1个Span拆成若干内存块，添加到对应大小的链表中，当CentralCache内存多的时候，会放回PageHeap

### 1.6  TCMalloc对象分配
小对象直接从ThreadCache分配，若ThreadCache不够则从CentralCache中获取内存，CentralCache内存不够时会再从PageHeap获取内存，大对象在PageHeap中选择合适的页组成span用于存储数据。

### 2.1 Page

和TCMalloc中page相同，上图中最下方浅蓝色长方形代表一个page
### 2.2 Span

与TCMalloc中的Span相同，Span是go内存管理的基本单位，代码中为`mspan`，一组连续的Page组成1个Span，所以上图一组连续的浅蓝色长方形代表的是一组Page组成的1个Span，另外，1个淡紫色长方形为1个Span.
### 2.3 mcache

mcache与TCMalloc中的ThreadCache类似，mcache保存的是各种大小的Span，并按Span class分类，小对象直接从mcache分配内存，它起到了缓存的作用，并且可以无锁访问。但mcache与ThreadCache也有不同点，TCMalloc中是每个线程1个ThreadCache，Go中是每个P拥有1个mcache，因为在Go程序中，当前最多有GOMAXPROCS个线程在运行，所以最多需要GOMAXPROCS个mcache就可以保证各线程对mcache的无锁访问，下图是G，P，M三者之间的关系

![image-20260401220326366](Go%E5%86%85%E5%AD%98%E7%AE%A1%E7%90%86.assets/image-20260401220326366.png)

### 2.4 mcentral
mcentral与TCMalloc中的CentralCache类似，是所有线程共享的缓存，需要加锁访问，它按Span class对Span分类，串联成链表，当mcache的某个级别Span的内存被分配光时，它会向mcentral申请1个当前级别的Span。 但mcentral与CentralCache也有不同点，CentralCache是每个级别的Span有1个链表，mcentral是每个级别的Span有2个链表。
### 2.5 mheap
mheap与TCMalloc中的PageHeap类似，它是堆内存的抽象，把从OS(系统)申请出的内存页组织成Span，并保存起来。当mcentral的Span不够用时会向mheap申请，mheap的Span不够用时会向OS申请，向OS的内存申请是按页来的，然后把申请来的内存页生成Span组织起来，同样也是需要加锁访问的。 但mheap与PageHeap也有不同点：mheap把Span组织成了树结构，而不是链表，并且还是2棵树，然后把Span分配到heapArena进行管理，它包含地址映射和span是否包含指针等位图，这样做的主要原因是为了更高效的利用内存（分配、回收和再利用）。

为对象寻找span 寻找span的流程如下

1. 计算对象所需内存大小size
2. 根据size到size class映射，计算出所需的size class
3. 根据size class和对象是否包含指针计算出span class
4. 获取该span class指向的span

以分配一个包含指针大小为20Byte的对象为例，根据映射表：

```go
// class  bytes/obj  bytes/span  objects  tail waste  max waste
//     1          8        8192     1024          0     87.50%
//     2         16        8192      512          0     43.75%
//     3         32        8192      256          0     46.88%
```

size class 3，它的对象大小范围是(16, 32]Byte，20Byte刚好在此区间，所以此对象的size class为3，Size class到span class的计算如下:

```go
// noscan为false代表对象包含指针
func makeSpanClass(sizeclass uint8, noscan bool)spanclass {
    return spanClass(sizeclass<<1) | spanClass(bool2int(noscan))
}
```

所以，对应的span class为：

```go
span class = 3 << 1 | 0 = 6
```

所以该对象需要的是span class 6指向的span，自此，小对象内存分配完成。

```go
// from runtime.gomalloc.go

var sizeclass uint8
// step1: 确定规格sizeClass
if size <= smallSizeMax-8 {
    sizeclass = size_to_class8[divRoundUp(size, smallSizeDiv)]
} else {
    sizeclass = size_to_class128[divRoundUp(size-smallSizeMax, largeSizeDiv)]
}
size = uintptr(class_to_size[sizeclass])
// size class到span class
spc := makeSpanClass(sizeclass, noscan)
// step2: 分配对应spanClass 的span
span = c.alloc[spc]
v := nextFreeFast(span)
if v == 0 {
    v, span, shouldhelpgc = c.nextFree(spc)
}
x = unsafe.Pointer(v)
if needzero && span.needzero != 0 {
    memclrNoHeapPointers(unsafe.Pointer(v), size)
}
```

大对象(>32KB)的分配则简单多了，直接在 mheap 上进行分配，首先计算出需要的内存页数和span class级别，然后优先从 `free` 中搜索可用的span，如果没有找到，会从 `scav` 中搜索可用的span，如果还没有找到，则向OS申请内存，再重新搜索2棵树，必然能找到span。如果找到的span比需求的span大，则把span进行分割成2个span，其中1个刚好是需求大小，把剩下的span再加入到 `free` 中去。

## Go是如何分配内存的？（堆对象）

Go 的内存分配借鉴了 Google 的 TCMalloc 分配算法，其核心思想是内存池 + 多级对象管理。内存池主要是预先分配内存，减少向系统申请的频率；多级对象有：mheap、mspan、arenas、mcentral、mcache。它们以 mspan 作为基本分配单位。

（1）Page，类似操作系统里的页；

（2）Span，go 内存管理的基本单位，一组连续的 Page 组成个Span；

（3）mcache，拥有各种大小的Span，每个P拥有1个mcache，无锁访问；

（4）mcentral，所有线程共享的缓存，需要加锁访问；

（5）mheap，堆内存的抽象把从 OS(系统)申请出的内存页组织成 Span，并保存起来，也是加锁访问；

具体的分级策略回顾内存模型图：

```go
操作系统（物理内存）
       ↓ mmap()（Go 唯一用的系统调用）
+--------------------------------+
|           mheap                |  全局大总管，负责向 OS 申请内存
+--------------------------------+
       ↓ 切成一页一页（8KB），拼成 span
+--------------------------------+
|           mcentral             |  全局中央缓存，按大小分级
+--------------------------------+
       ↓ 每个 P 拿一批
+--------------------------------+
|           mcache               |  每个 P 一个，无锁分配
+--------------------------------+
       ↓ 最终给对象使用
+--------------------------------+
|       程序里的变量/对象         |
+--------------------------------+
```

### 触发点：你写了一行代码

```go
obj := new(int) // 或 make，或任何需要堆分配的对象
```

这行代码会触发 Go 内存分配器**完整链路**。

下面是**真正的执行步骤**（完全按源码顺序）：

### 1.判断对象大小（决定走哪种分配路径）

Go 会先计算**对象大小**，然后分 3 种情况：

1. **微对象 (0 ~ 16B)**
2. **小对象 (16B ~ 32KB)**
3. **大对象 (> 32KB)**

**99% 的对象都是小对象，我们重点讲这个。**

### 2.获取当前 G 绑定的 P → 拿到 P 自带的 mcache

```plaintext
当前 goroutine (G)
   ↓
绑定到 逻辑处理器 (P)
   ↓
P 内部自带一个 **mcache**
```

**mcache 是每 P 一个，线程本地，无锁！**

这是**最快的分配路径**，完全无锁。

### 3.根据对象大小 → 找到对应的 size class

比如分配 24B 的对象：

```plaintext
size class = 6
对应的 mspan 里切好的块 = 24B
```

mcache 有一个数组：

```go
alloc [67]*mspan  // 按 size class 存着可用的 mspan
```

直接定位：

```plaintext
mcache.alloc[sizeclass]
```

### 4.查看 mcache 里当前 span 有没有空闲块

情况 A：有空闲块 → **直接分配，结束！**

```plaintext
从 mcache 的 span 里拿一个空闲块
返回指针
```

✅ **这是最快路径，无锁、无系统调用、10ns 完成。**

情况 B：mcache 这个 size class 没有空闲块了 → **必须 refill**

进入**扩容流程**：

```plaintext
mcache 不够
   ↓
mcache 向 mcentral 申请 1 个完整的 span
```

### 5.mcache 向 mcentral 获取新 span

**mcentral 是全局的，所有 P 共享，必须加锁。**

mcentral 内部有两个链表：

```plaintext
partial ：有空闲对象的 span
full    ：满的 span
```

流程：

1. 加锁
2. 从 **partial 链表**取一个**有空闲块的 span**
3. 取到后，把这个 span 给 mcache
4. 解锁

如果 mcentral 也没有可用 span → 继续向上找 mheap

```plaintext
mcentral 没有可用 span
   ↓
向 mheap 申请一个新 span
```

### 6.mcentral 向 mheap 申请新 span

mheap 是全局唯一的内存总管。

它做：

1. 从**空闲页列表**找一段**连续的 page**
2. 把连续 page 封装成 **mspan**
3. 按 size class 切分成小内存块
4. 返回给 mcentral

如果 mheap 也没有空闲页 → **必须向 OS 申请内存**

```plaintext
mheap 没有空闲页
   ↓
调用 **mmap** 向操作系统申请内存
```

### 7.Go 调用 mmap 从操作系统获取内存

这是**唯一接触系统内核**的地方。

```plaintext
mmap(匿名内存)
   ↓
操作系统分配物理内存 → 映射到进程虚拟空间
   ↓
返回给 mheap
```

**Go 永远不用 brk ()，只用 mmap ()！**

### 8.内存一路返回

```plaintext
OS → mheap → mcentral → mcache
```

mcache 拿到新 span 后：

```plaintext
把新 span 放到 mcache.alloc[sizeclass] 位置
```

### 9.最终分配内存给对象

```plaintext
从 mcache 的新 span 中取一个块
返回指针给用户代码
```

✅ **分配完成！**

```
用户代码 new/make
       ↓
计算对象大小 → 确定 size class
       ↓
获取 P → 获取 P 自带的 mcache
       ↓
查看 mcache[size class] 的 span 是否有空闲块
       ↓
┌─────────────┴─────────────┐
有空闲块                  无空闲块
    ↓                        ↓
直接分配（结束）         mcache 向 mcentral 申请 span
                            ↓
                    mcentral 查看 partial 链表
                            ↓
                    ┌────────┴────────┐
                    有span           无span
                        ↓               ↓
                    返回span       mcentral 向 mheap 申请
                                        ↓
                                mheap 从空闲页分配 span
                                        ↓
                                ┌───────┴───────┐
                                有空闲页        无空闲页
                                    ↓               ↓
                            组装成span       mheap 调用 mmap 向OS申请
                                                    ↓
                                            OS分配物理内存 & 映射
```

**Go 完全不用系统原生堆（brk），全程用 mmap 向操作系统拿内存 → 交给 mheap 管理 → 切成 span → 分给 mcentral → 再给 mcache → 最后给对象使用。**

go语言对象的分配根据对象大小的不同申请策略也不同：

- 当要分配大于 32K 的对象时，从 mheap 分配。
- 当要分配的对象小于等于 32K 大于 16B 时，从P上的 mcache 分配，如果 mcache 没有内存，则从 mcentral 获取，如果 mcentral 也没有，则向 mheap 申请，如果 mheap 也没有，则从操作系统申请内存。
- 当要分配的对象小于等于 16B 时(微小对象)，从 mcache 上的微型分配器上分配。

## 栈对象的内存分配是怎么做的？

栈上分配内存，根本不经过 Go 内存分配器，

只做一件事：移动栈指针 rsp。

没有 mcache、没有锁、没有链表、没有 span、没有 mmap，

**纯汇编级别的指针加减**。

栈的结构是什么样？

每个 goroutine 有一块连续内存当作栈：

```plaintext
高地址 ← stack.top
        |
        | 已使用
        |
        v
        当前 rsp (栈顶指针)
        |
        | 空闲
        |
低地址 ← stack.bottom
```

栈是**一块连续、预先申请好的内存**（Go 会用 mmap 申请，但分配时不再管来源）。

比如函数里：

```go
func f() {
    var x int64  // 8 字节
    var y int    // 机器字长，比如 8 字节
}
```

编译器在编译时就知道：

- 需要为 `x` 分配 **8 字节**
- 需要为 `y` 分配 **8 字节**
- 一共需要 **16 字节**

所以编译后，函数序言会生成一条指令：

```asm
sub rsp, 16    ; 栈指针向下移动 16 字节
```

这就**分配完成了**。

- `x` 就在 `rsp+0` 位置
- `y` 就在 `rsp+8` 位置

**没有任何运行时逻辑，没有任何查找，没有任何 GC 参与。**

栈 “释放” 变量怎么做？

函数返回时：

```asm
add rsp, 16    ; 栈指针恢复原位
ret
```

内存并没有被 “清空”，只是**栈指针回去了**。

### 总结

下次分配直接覆盖。

1. 编译器在编译时计算当前函数栈帧大小
2. 进入函数时：`sub rsp, 大小`
3. 变量通过 `rsp+偏移量` 访问
4. 函数返回时：`add rsp, 大小`
5. 结束

**全程：**

- 无系统调用
- 无运行时参与
- 无锁
- 无链表
- 无 span
- 无 mcache/mcentral/mheap
- 无 GC

### go语言的栈是怎么用的？

下面分原理、内存布局、两种栈（用户栈 / 系统栈）展开说明。

一、Go 为什么不用原生栈段

传统进程内存布局（Linux/macOS）：

```plaintext
高地址
+------------------+
| 栈 (Stack)       |  ← 固定大小（通常 2MB）、由内核管理
|                  |  ← 向下增长
+------------------+
| 内存映射段 (mmap) |  ← Go 堆、Go 栈、动态库都在这里
+------------------+
| 堆 (Heap)        |  ← 传统 brk/sbrk 堆（Go 基本不用）
+------------------+
| BSS/Data/代码等  |
低地址
```

Go 运行时**完全弃用**进程默认的 Stack 段：

- 传统栈**固定大小**（2MB），无法动态扩缩，不适合百万级 goroutine
- Go 需要**用户态管理、动态扩容**的栈（初始 2KB，可扩到 1GB）
- 所以 Go 自己用 `mmap(MAP_ANON|MAP_PRIVATE)` 申请虚拟内存，**把栈和堆都放在 mmap 段**Go

二、两种栈：都在 mmap，但用途不同

Go 里有两类栈，**全部来自 mmap**：

1. Goroutine 用户栈（G stack）

- 每个 G 有一个：执行 **用户 Go 代码** 的栈

- 初始 **2KB**（Go 1.21+ 共享池优化）

- 动态扩容 / 缩容：不够时 `morestack` 分配更大 mmap 块、拷贝数据

- 分配路径：

  ```plaintext
  stackalloc → 池不够 → sysAlloc → mmap
  ```

  直接从 mmap 区拿虚拟内存

2. 系统栈（g0 stack /gsignal stack）

- 每个 OS 线程 M 绑定两个：
  - **g0 栈**：运行 **Go 运行时代码**（调度、GC、栈扩容、cgo）
  - **gsignal 栈**：处理信号（Unix）
- **固定大小**（不扩容）：纯 Go 下约 8KB，cgo 下更大
- 同样由 `sysAlloc → mmap` 分配，**也在 mmap 段**Go

> 只有主线程 m0 的 g0 栈**最初**可能在进程传统 Stack 段，但运行时启动后会**切换到自己 mmap 分配的 g0 栈**，之后所有栈都在 mmap。

三、内存布局（Go 视角）

Go 进程虚拟内存简化：

```plaintext
高地址
+---------------------+
| 内核空间            |
+---------------------+
| 【mmap 段】         | ← 整块由 mmap 来的匿名内存
|   ├─ Go 堆 arena    | ← mheap 管理（64MB/块）
|   ├─ Goroutine 栈   | ← 每个 G 独立 mmap 块
|   ├─ g0/gsignal 栈  | ← 每个 M 两个固定栈
|   └─ 运行时元数据   |
+---------------------+
| 空洞（保护）        |
+---------------------+
| 传统 brk 堆         | ← Go 几乎不用
+---------------------+
| Data/BSS/代码段     |
低地址
```

**关键点**：

- **堆、goroutine 栈、g0 栈、gsignal 栈 全都在 mmap 段**
- 它们只是**用途不同、管理方式不同**的虚拟内存块，物理上都来自操作系统匿名页
- 传统 Stack 段只在启动瞬间短暂用一下，很快废弃

四、多线程下：M、G、栈的关系

- 一个 M（OS 线程）同一时间只跑一个 G
- 执行用户代码：用 **G 的用户栈**（mmap）
- 进入运行时 / 调度 / GC：自动切到 **M 的 g0 栈**（mmap）
- 所有栈都在 mmap，**没有任何栈在进程默认 Stack 段**

五、一句话总结

**Go 不使用进程原生栈段，所有栈（goroutine 用户栈、g0 系统栈、gsignal 信号栈）都通过 mmap 分配，和堆同属内存映射段，由运行时全权管理。**

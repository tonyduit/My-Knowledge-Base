# Go并发

## 进程、线程、协程

进程、线程和协程都是并发编程的概念

进程是操作系统分配资源的基本单位，每个进程都有自己的独立内存空间，不同进程之间的数据不能直接共享, 通常通过进程间通信（IPC）来进行数据交换，例如管道、消息队列等。

线程是操作系统调度的最小执行单位，同一进程的不同线程共享相同的内存空间，可以直接访问共享数据。

协程是轻量级的用户态线程，由Go调度器进行管理，协程的创建和销毁比线程更为轻量，可以很容易地创建大量的协程。协程之间通过通信来共享数据，而不是通过共享内存。这通过使用通道（channel）等机制来实现。

## 进程、线程的区别

- 调度:进程是资源管理的基本单位，线程是程序执行的基本单位。
- 切换:线程上下文切换比进程上下文切换要快得多。
- 拥有资源: 进程是拥有资源的一个独立单位，线程不拥有系统资源，但是可以访问隶属于进程的资源。
- 系统开销: 创建或撤销进程时，系统都要为之分配或回收系统资源，如内存空间，I/O 设备等，OS 所付出的开销显著大于在创建或撤销线程时的开 销，进程切换的开销也远大于线程切换的开销。

## 协程和线程的区别

- 线程和进程都是同步机制，而协程是异步机制。
- 线程是抢占式，而协程是非抢占式的。需要用户释放使用权切换到其他协程，因此同一时间其实只有一个协程拥有运行权，相当于单线程的能力。
- 一个线程可以有多个协程，一个进程也可以有多个协程。
- 协程不被操作系统内核管理，而完全是由程序控制。线程是被分割的CPU资源，协程是组织好的代码流程，线程是协程的资源。但协程不会直接使用线程，协程直接利用的是执行器关联任意线程或线程池。
- 协程能保留上一次调用时的状态。

## 并行和并发的区别

- 并发就是在一段时间内，多个任务都会被处理;但在某一时刻，只有一个任务 在执行。单核处理器可以做到并发。比如有两个进程 A 和 B，A 运行一个时间片之后，切换到 B，B 运行一个时间片之后又切换到 A。因为切换速度足够快，所以宏观上表现为在一段时间内能同时运行多个程序。
- 并行就是在同一时刻，有多个任务在执行。这个需要多核处理器才能完成，在微观上就能同时执行多条指令，不同的程序被放到不同的处理器上运行，这个是物理上的多个进程同时进行。

## CSP并发模型

Go语言的并发模型建立在goroutine和channel之上。其设计理念是**共享数据通过通信而不是通过共享内存来实现**

- Goroutines 是Go中的轻量级线程，由Go运行时（runtime）管理。与传统线程相比，goroutines的创建和销毁开销很小。程序可以同时运行多个goroutines，它们共享相同的地址空间。
- Goroutines之间的通信通过channel（通道）实现。通道提供了一种安全、同步的方式，用于在goroutines之间传递数据。使用通道可以避免多个goroutines同时访问共享数据而导致竞态条件的问题。
- 多路复用：`select` 语句允许在多个通道操作中选择一个执行。这种方式可以有效地处理多个通道的并发操作，避免了阻塞。
- 互斥锁和条件变量
  - Go提供了`sync`包，其中包括 `Mutex`（互斥锁）等同步原语，用于在多个goroutines之间进行互斥访问共享资源。
  - `sync` 包还提供了 `Cond`（条件变量），用于在goroutines之间建立更复杂的同步。
- 原子操作： Go提供了`sync/atomic`包，其中包括一系列原子性操作，用于在不使用锁的情况下进行安全的并发操作。

## CSP模型的三大特性

- **解耦：** 发送者不需要知道接收者是谁，它们只需要关注 Channel 这一媒介。
- **阻塞特性（天然的同步）：**
  - 当 Channel 满了，发送者会阻塞。
  - 当 Channel 空了，接收者会阻塞。 这让你省去了写 `wait()` 和 `notify()` 的繁琐逻辑。
- **安全性：** 由于数据是在 Channel 之间“流动”的，同一时间只有一个 Goroutine 能拥有数据的所有权，从根源上避免了**数据竞争（Data Race）**。

另外：**Go 并不是只有 CSP**

虽然 Go 极力推崇 CSP，但它依然保留了传统的 `sync` 包（锁、原子操作）。

- **什么时候用 CSP (Channel)？** 涉及到数据分发、任务编排、异步处理时。
- **什么时候用锁 (Mutex)？** 仅仅是为了保护一个简单的全局变量，且对性能要求极高时。

## 什么是go routine

goroutine（协程）是一种轻量级的线程，由Go运行时（runtime）管理，一个典型的 Go 程序可能会同时运行成千上万个 goroutine，Goroutines 使得程序可以并发执行，而无需显式地创建和管理线程。通过关键字 `go` 可以启动一个新的 goroutine，例如：`go someFunction()`。

每个 goroutine 都有自己的独立栈空间，这使得它们之间的数据不容易互相干扰。与传统的多线程编程相比，使用 goroutines 不需要开发者显式地进行线程的创建、销毁和同步。Go 运行时会自动处理这些事务。

```
┌─────────────────────────────────────────────────┐
│                    进程内存空间                  │
├─────────────────────────────────────────────────┤
│  ┌─────────────┐  ┌─────────────┐               │
│  │  线程1栈     │  │  线程2栈    │   ...         │  ← 操作系统管理
│  │  (8MB固定)  │  │  (8MB固定)   │               │
│  └─────────────┘  └─────────────┘               │
│                                                 │
│  ┌─────────────────────────────────────────┐    │
│  │              堆 (Heap)                  │    │
│  │  ┌─────────┐ ┌─────────┐ ┌─────────┐    │    │
│  │  │Goroutine│ │Goroutine│ │Goroutine│    │    │  ← Go运行时管理
│  │  │ 栈(2KB) │ │ 栈(2KB) │ │ 栈(2KB) │     │    │
│  │  └─────────┘ └─────────┘ └─────────┘    │    │
│  └─────────────────────────────────────────┘    │
└─────────────────────────────────────────────────┘
```

**重要结论：Goroutine栈是从堆上分配的，不是从各个线程的栈段上划分的！**

## 那么 Goroutine 相比线程有什么优势？

Goroutine 不是操作系统线程，而是 Go 运行时管理的用户级线程。它在设计上针对并发编程进行了优化，主要优势包括：

1.**轻量级资源占用**：

- 线程通常占用 1-2 MB 的栈空间，而 Goroutine 的初始栈空间仅为 2 KB（可动态增长到 GB 级别，但通常很小）。
- 创建和销毁 Goroutine 的开销远低于线程（Goroutine 创建只需几纳秒，线程可能需要微秒级）。

2.**高效的启动和切换**：

- Goroutine 可以在用户空间快速启动，无需系统调用。
- 切换成本低：Goroutine 切换是用户态操作，而线程切换涉及内核态，成本更高。

3.**可扩展性**：

- 一个 Go 程序可以轻松运行数万个 Goroutine，而线程数量受操作系统限制。
- Go 的调度器优化了 CPU 利用率，尤其在 I/O 密集型任务中，对于用户态的阻塞，只会阻塞当前 Goroutine 而不会阻塞当前线程。

| 阻塞类型   | Go (Goroutine + M)                                           | 纯线程模型（Java/Python 等）                                 |
| ---------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 内核态阻塞 | G 绑定 M 阻塞，但**仅阻塞当前 M**（线程），Go 调度器会快速分配新 M 接管 P，其他 G 继续执行 | 线程直接阻塞，且无 “自动补充执行载体” 的机制，阻塞期间该线程完全闲置 |
| 用户态阻塞 | 仅 G 挂起，**M 完全不阻塞**，立刻执行其他 G（用户态切换，无内核开销） | 线程阻塞（哪怕是用户态锁 / 等待），操作系统需通过内核态切换到其他线程，开销高 |

Go 的**调度补偿机制**：虽然内核态阻塞会卡住当前 M，但 Go 会立刻补一个新 M 来干活，所以整体并发不受影响；而纯线程模型中，线程阻塞后只能等操作系统内核调度，期间这个线程对应的资源就闲置了，且线程创建成本高，没法像 Go 这样 “快速补位”。

4.**垃圾回收友好**：

- Goroutine 与 Go 的垃圾回收器紧密集成，减少了内存泄漏风险。

## 如何控制 goroutine 的生命周期

1.启动

使用关键字 `go` 可以启动一个新的 goroutine。

```go
go func() {
    // goroutine 的代码逻辑
}()
```

2.等待结束

希望主程序等待某个 goroutine 执行完毕后再继续执行。可以使用 `sync.WaitGroup` 来实现等待。

```go
package main

import (
    "fmt"
    "sync"
)

func main() {
    var wg sync.WaitGroup

    wg.Add(1) // 添加一个等待的 goroutine

    go func() {
        defer wg.Done() // goroutine 完成时调用 Done 减少计数
        // goroutine 的代码逻辑
        fmt.Println("Goroutine executing...")
    }()

    // 等待所有 goroutine 完成
    wg.Wait()

    fmt.Println("Main goroutine exiting.")
}
```

3.使用通道（channel）来通知 goroutine 退出

```go
package main

import (
    "fmt"
    "time"
)

func main() {
    quit := make(chan bool)

    go func() {
        defer fmt.Println("Goroutine exiting...")
        // goroutine 的代码逻辑
        time.Sleep(time.Second * 2)
        quit <- true // 发送退出通知
    }()

    // 主 goroutine 等待退出通知
    <-quit // 阻塞等待，直到有数据
    fmt.Println("Main goroutine exiting.")
}
```

4.使用context包

Go 标准库中的 `context` 可以实现超时控制、取消、传递参数等功能。

## Go语言中的Channel是什么，有哪些用途，如何处理阻塞

Channel（通道）是用于在goroutines之间进行通信的一种机制。通道提供了一种并发安全的方式来进行goroutines之间的通信。通过通道，可以避免在多个goroutines之间共享内存而引发的竞态条件问题，因为通道的读写是原子性的，不会被其他goroutine中断。

### **用途**

- **数据传递：** 主要用于在goroutines之间传递数据，确保数据的安全传递和同步。
- **同步执行：** 通过Channel可以实现在不同goroutines之间的同步执行，确保某个goroutine在另一个goroutine完成某个操作之前等待。
- **消息传递：** 适用于实现发布-订阅模型或通过消息进行事件通知的场景。
- **多路复用：** 使用`select`语句，可以让**一个goroutine同时监听多个Channel，哪个Channel准备好了就处理哪个**，而不需要为每个Channel单独创建一个goroutine来等待。

### **如何处理阻塞**

1. 缓冲通道，在创建通道时指定缓冲区大小，即创建一个缓冲通道。当缓冲区未满时，发送数据不会阻塞。当缓冲区未空时，接收数据不会阻塞。
2. `select`语句用于处理多个通道操作，可以用于避免阻塞。
3. 使用`time.After`创建一个定时器，可以在超时后执行特定的操作，避免永久阻塞。
4. `select`语句中使用`default`分支，可以在所有通道都阻塞的情况下执行非阻塞的操作。

## 什么是互斥锁（mutex）？在什么情况下会用到它们？

互斥锁是一种用于控制对共享资源访问的同步机制。它确保在任意时刻只有一个线程能够访问共享资源，从而避免了多个线程同时对资源进行写操作导致的数据竞争和不一致性。

在并发编程中，多个线程（或者Goroutines）可能同时访问共享的数据，如果不进行同步控制，可能导致以下问题：

- **竞态条件（Race Condition）：** 多个线程同时修改共享资源，导致最终结果依赖于执行时机，可能引发不确定的行为。
- **数据不一致性：** 多个线程同时读写共享资源，可能导致数据不一致，破坏了程序的正确性。

互斥锁通过在临界区（对共享资源的访问区域）中使用锁来解决这些问题。基本上，当一个线程获得了互斥锁时，其他线程需要等待该线程释放锁后才能获得锁。这确保了在任一时刻只有一个线程能够进入临界区。

在Go语言中，互斥锁通常使用`sync`包中的`Mutex`类型来实现。以下是一个简单的示例：

```go
package main

import (
	"fmt"
	"sync"
)

var counter int
var mutex sync.Mutex

func increment(wg *sync.WaitGroup) {
	defer wg.Done()
	
	// 互斥锁加锁
	mutex.Lock()
	counter++
	// 互斥锁解锁
	mutex.Unlock()
}

func main() {
	var wg sync.WaitGroup
	for i := 0; i < 1000; i++ {
		wg.Add(1)
		go increment(&wg)
	}
	wg.Wait()

	fmt.Println("Counter:", counter)
}
```

`mutex.Lock()`用于加锁，`mutex.Unlock()`用于解锁。这确保了`counter`的并发访问是安全的，避免了竞态条件。

需要注意的是，在使用互斥锁时，要确保在临界区内的代码执行时间较短，以减小锁的持有时间，从而提高程序的并发性能。过长的锁持有时间可能导致其他线程被阻塞，降低并发性。

## Mutex有几种模式

mutex有两种模式：**normal** 和 **starvation**

1.普通模式

在普通模式中，锁的获取是非公平的，即等待锁的 Goroutine 不保证按照先来先服务（FIFO）的顺序获得锁。新到来的 Goroutine 有可能在等待时间较长的 Goroutine 之前获得锁。

2.饥饿模式：

在饥饿模式中，系统保证等待锁的 Goroutine 按照一定的公平原则获得锁，避免某些 Goroutine 长时间无法获取锁的情况。

## Mutex有几种状态

| 标志位          | 含义                                          |
| --------------- | --------------------------------------------- |
| `mutexLocked`   | 锁是否被某个 goroutine 持有                   |
| `mutexWoken`    | 是否有等待的 goroutine 被唤醒（避免重复唤醒） |
| `mutexStarving` | 是否进入饥饿模式                              |
| `waiters`       | 等待锁的 goroutine 数量（高29位存储）         |

### 总结

| 概念     | 正确理解                                   |
| -------- | ------------------------------------------ |
| 工作模式 | 2种：正常模式、饥饿模式                    |
| 状态标志 | 3个位标志：locked、woken、starving         |
| waiters  | 是等待者计数，不是状态                     |
| 设计目的 | 平衡吞吐量（正常模式）和公平性（饥饿模式） |

## 无缓冲的 channel 和有缓冲的 channel 的区别？

对于无缓冲区channel：

发送的数据如果没有被接收方接收，那么**发送方阻塞；**如果一直接收不到发送方的数据，**接收方阻塞**；

有缓冲的channel：

发送方在缓冲区满的时候阻塞，接收方不阻塞；接收方在缓冲区为空的时候阻塞，发送方不阻塞。

```go
	recvq    waitq  // 接收者的等待队列（双向链表），用于存储被阻塞的接收协程
	sendq    waitq  // 发送者的等待队列（双向链表），用于存储被阻塞的发送协程

	lock mutex  // 数据保护锁
}
```

### **关于channel的收发流程**

当一个 goroutine 因 channel 操作被阻塞时，runtime 会：

1. 从 `sudog` 池中分配一个 `sudog` 对象；
2. 将当前 goroutine (`g`) 和相关数据（如要发送的值地址）填入；
3. 把这个 `sudog` 加入 `sendq` 或 `recvq`；
4. 调用 `gopark()` 让该 goroutine 进入等待状态。

简而言之，就是一个发送协程（接收协程），进入到channel中发数据（取数据）时，如果`recvq`（`sendq`）中没有阻塞中的`sudog`（`sudog`就是对被阻塞的go协程的一个封装），那么就会将该协程封装为一个`sudog`然后加入`sendq`（`recvq`）进行等待，直到有接收协程（发送协程）来channel中取数据（发数据）。**这两个队列就是用于缓存与channel交互的多个goroutine**

### **为什么buf用数组，sendq/recvq用双向链表？**

​	对于`buf`，在我们创建有缓冲的channel的时候就已经定义好了缓冲区的大小了，所以`buf`没有动态扩缩容的需求，而数组的各个元素的内存是连续的，cpu缓存命中率高，环形数组实现的队列在出队时的时间复杂度也不逊于链表，都是O(1)，而且数组在频繁入队出队时只需要覆盖原来的数据就好了，而链表需要频繁修改指针，不被引用的节点会给GC造成压力。

​	而`sendq`和`recvq`的大小是不确定的，所以需要用到链表可以灵活扩容的特性。

## goroutine调度（GPM模型）

操作系统内核在调度时会挂起当前正在执行的线程并将寄存器中的内容保存到**该线程的TCB**中，然后选出接下来要执行的线程并从**该线程的TCB**中恢复该线程的寄存器信息，然后从它上次被中断的地方继续执行。从一个线程切换到另一个线程需要完整的上下文切换。因为可能需要多次内存访问，索引这个切换上下文的操作开销较大，会增加cpu运行的周期。

区别于操作系统内核调度操作系统线程，goroutine 的调度是Go语言运行时（runtime）层面的实现，是完全由 Go 语言本身实现的一套调度系统——go scheduler。它的作用是按照一定的规则将所有的 goroutine 调度到操作系统线程上执行。

在经历数个版本的迭代之后，目前 Go 语言的调度器采用的是 `GPM` 调度模型。

其中：

- G：表示 goroutine，每执行一次`go func()`就创建一个 G，包含要执行的函数和上下文信息。
- 全局队列（Global Queue）：是一个**基于 Mutex 保护的链表**，存放等待运行的 G。
- P：**P 是 Go 调度器中的“逻辑处理器”（Logical Processor），代表一个可执行 goroutine 的资源上下文。它是 G（goroutine）和 M（machine/thread）之间的调度桥梁。**，最多有 GOMAXPROCS 个。
- P 的本地队列（基于环形数组实现的队列）：同全局队列类似，存放的也是等待运行的G，存的数量有限，不超过256个。新建 G 时，G 优先加入到 P 的本地队列，如果本地队列满了会批量移动部分 G 到全局队列。
- M：线程想运行任务就得获取 P，从 P 的本地队列获取 G，当 P 的本地队列为空时，M 也会尝试从全局队列或其他 P 的本地队列获取 G。M 运行 G，G 执行之后，M 会从 P 获取下一个 G，不断重复下去。
- Goroutine 调度器和操作系统调度器是通过 M 结合起来的，每个 M 都代表了1个内核线程，操作系统调度器负责把内核线程分配到 CPU 的核上执行。

### **GPM 模型的工作流程**

1.Goroutine 创建:当创建一个新的 Goroutine 时，运行时会将其封装为一个 G 对象，并尝试将其添加到当前 P 的本地队列中。如果本地队列已满，则会将部分 G（当前 G和本地队列中一半的G）转移到全局队列中。

2.任务调度:M 从其绑定的 P的本地队列中获取可运行的 G 并执行。如果本地队列为空，P 会尝试从全局队列获取，如果全局也为空，则会尝试从其他P的本地队列中窃取任务（称为work stealing）。

3.阻塞处理:如果 M 在执行过程中发生阻塞（例如系统调用），运行时会将该 M 与 P 分离，并将P分配给其他空闲的M，以继续执行其他 Goroutine。当阻塞的 M 恢复时，它会尝试获取一个空闲的 P 将阻塞恢复的 G 放入其中继续执行，如果没有空闲的 P，那么从阻塞恢复的 G 会被放回全局队列，然后 M 进入休眠状态。

单从线程调度讲，Go语言相比起其他语言的优势在于OS线程是由OS内核来调度的， goroutine 则是由Go运行时（runtime）自己的调度器调度的，完全是在用户态下完成的， 不涉及内核态与用户态之间的频繁切换，包括内存的分配与释放，都是在用户态维护着一块大的内存池， 不直接调用系统的malloc函数（除非内存池需要改变），成本比调度OS线程低很多。 另一方面充分利用了多核的硬件资源，近似的把若干goroutine均分在物理线程上， 再加上本身 goroutine 的超轻量级，以上种种特性保证了 goroutine 调度方面的性能。

### **为什么本地队列要基于环形数组而不是链表实现？**

**前提：**Go 的本地队列在单个 P 上由唯一的 M 访问（大部分时间非并发），所以可以**无锁操作**；只有在工作窃取时才需要加锁（并发）。

**场景 1️⃣：正常执行（非并发，占 99%+ 时间）**

- 每个 P 被一个 M（OS 线程）独占。
- 只有这个 M 能操作 P 的本地队列：
  - **入队**：当前 Goroutine 启动新 Goroutine（`go func()`）时，由当前 M 放入本地队列。
  - **出队**：当前 M 从本地队列取下一个 G 执行。
- ✅ **这是严格的“单生产者 + 单消费者”模型** → **完全无锁**，用环形数组性能极高。

**场景 2️⃣：工作窃取（并发，偶发事件）**

- 当某个 M 发现自己的本地队列空了，它会尝试从**其他 P 的本地队列**偷一半 Goroutine。
- 此时：
  - **被偷的 P 的本地队列**：可能正在被它的 owner M 访问（出队/入队）。
  - **偷窃的 M**：试图读取并修改这个队列。
- ⚠️ **这就变成了多线程并发访问！**

| 维度                               | 环形数组（Go 本地队列）                               | 链表                                                     |
| :--------------------------------- | :---------------------------------------------------- | :------------------------------------------------------- |
| **1. 内存分配**                    | 启动时一次性分配 256 个 slot（零运行时分配）          | 每次入队都要 `malloc(node)`，出队要 `free(node)`         |
| **2. GC 压力**                     | **零 GC**（数组是 P 的一部分，P 是全局对象）          | **高 GC**（每个 node 都是堆对象，频繁创建销毁）          |
| **3. 缓存局部性 (Cache Locality)** | ✅ **极佳**：所有 Goroutine 指针连续存放，CPU 预取高效 | ❌ **极差**：node 分散在堆各处，每次访问都可能 Cache Miss |
| **4. 操作开销**                    | 入队/出队 = 移动索引 + 数组赋值（几条 CPU 指令）      | 入队 = 分配内存 + 设置指针；出队 = 读指针 + 释放内存     |

**总结**

​	本地队列用环形数组，全局队列用双向链表，这是一种分工的体现（**用简单、固定、无锁的结构处理 99% 的情况，用稍微重一点的全局结构处理 1% 的溢出**），对于常用的本地队列的环形数组的内存连续，可以用到cpu缓存，速度快。对于不常用的全局队列，本地队列装不下的goroutine会放到全局队列的链表里面，双向链表可以动态扩缩容，用于缓存从本地队列溢出的goroutine，全局队列虽然访问稍慢（需加锁），但不会丢失，也不会阻塞创建。

### **GOMAXPROCS**

​	Go运行时的调度器使用`GOMAXPROCS`参数来确定需要使用多少个 OS 线程来同时执行 Go 代码。默认值是机器上的 CPU 核心数。例如在一个 8 核心的机器上，GOMAXPROCS 默认为 8。Go语言中可以通过`runtime.GOMAXPROCS`函数设置当前程序并发时占用的 CPU逻辑核心数。（Go1.5版本之前，默认使用的是单核心执行。Go1.5 版本之后，默认使用全部的CPU 逻辑核心数。）

### P 的数量会影响什么？

p的数量（通过 `runtime.GOMAXPROCS()` 设置，默认等于 CPU 核心数）直接影响调度器的性能和程序行为：

**并发度**：

- P 数量决定同时可以运行的 Goroutine 数量上限（每个 P 可绑定一个 M 执行一个 G）。
- 增加 P 可以提高 CPU 利用率，尤其在多核系统上，但过度增加可能导致上下文切换开销增大。

**调度效率**：

- 更多 P 意味着更多本地队列，减少全局队列竞争，但也增加 work-stealing 的复杂度。
- 在 I/O 密集型任务中，P 数量影响阻塞 G 的处理速度（更多 P 可以更快地调度新 G）。

**内存和资源**：

- 每个 P 占用少量内存，但过多 P 会增加调度开销。
- 在单核 CPU 上，设置 P > 1 不会提高性能，因为只有一个 M 可用。

**性能调优**：

- 默认值通常最佳，但对于 CPU 密集型任务，可适当增加；对于 I/O 密集型，可减少以节省资源。
- 示例：`runtime.GOMAXPROCS(4)` 在 8 核机器上限制并发度为 4。

**1. P 数量过多导致上下文切换增加的原因**

首先要明确：**上下文切换分两种**——

- 「Goroutine 切换」：用户态切换，成本极低（纳秒级）；
- 「操作系统线程（M）切换」：内核态切换，成本极高（微秒级，是 Goroutine 切换的 100-1000 倍）。

GPM的逻辑是：**只要有空闲 P 且有可执行的 G，就会创建新 M 来绑定 P**（直到达到 `SetMaxThreads` 上限）

所以一般M的数量 ≈ P的数量（M通常会比P多 0~几个），P 数量过多的核心问题，是会触发**更多内核态的 M 切换**，而非 Goroutine 切换：

- 8 核 CPU 的**整个系统中**，同一时刻最多只能并行执行 8 个线程（不管这些线程属于哪个进程）；
- 操作系统会通过**时间片轮转**，让多个进程的多个线程 “轮流占用” 这 8 个核心，宏观上看起来像是 “同时执行”，但微观上还是串行切换的。
- 若 P 数量远超 CPU 核心数（比如 8 核 CPU 设 `GOMAXPROCS(32)`），操作系统需要在 32 个 M（线程）之间切换，才能让每个 M 都有机会执行；
- 这些 M 都绑定到有限的 CPU 核心上，操作系统内核不得不频繁切换线程上下文（保存 / 恢复寄存器、页表等），最终导致整体开销上升。

总结：P 数量过多导致上下文切换增加的本质是因为P增多时M也会增多，M增多了，操作系统就增加了调度成本。**本质还是M数量增多导致的**

**2. 增加 P 提升 work-stealing 复杂度的原因**

- work-stealing 的核心是 “空闲 P 找其他 P 要任务”，P 数量越多，空闲 P 需要遍历的 “目标 P” 就越多（比如 2 个 P 只需互偷，8 个 P 则要在 7 个 P 中找有任务的）；
- 每个 P 的本地队列都有自己的状态（如任务数量、指针位置），P 数量增加会导致窃取时的 “判断成本” 和 “协调成本” 上升（比如要避免多个 P 同时偷同一个 P 的队列）；
- 简单说：P 少的时候，窃取逻辑是 “一对一”，简单高效；P 多的时候，窃取逻辑是 “一对多”，需要更多的检查和判断，复杂度自然上升。

## Go什么时候发生阻塞？阻塞时调度器会怎么做。

- 用于**互斥或通道**操作导致goroutine阻塞，调度器将把当前阻塞的goroutine从本地运行队列**LRQ换出**，并重新调度其它goroutine；
- 由于**网络请求**和**IO**导致的阻塞，Go提供了网络轮询器（Netpoller）来处理，后台用epoll等技术实现IO多路复用。

其它回答：

### **用户态阻塞（Channel、Mutex等）**

当goroutine读写channel发生阻塞时，会调用gopark函数，该G脱离当前的M和P，调度器将新的G放入当前M。

```
┌─────────────────────────────────────────────────────────────────┐
│                    用户态阻塞处理流程                             │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  G执行 ──→ 遇到阻塞 ──→ 挂起G ──→ P继续调度其他G                   │
│   │           │           │           │                         │
│   │           │           │           └──→ 从本地/全局队列取G    │
│   │           │           └──→ G状态: running→waiting           │
│   │           └──→ runtime接管，无需分离M/P                      │
│   └──→ 阻塞操作（如ch<-value，无接收者）                          │
│                                                                 │
│  恢复时: G被唤醒 ──→ 放入P本地队列 ──→ 等待调度                    │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

代码示例

```go
ch := make(chan int)

go func() {
    ch <- 42  // 用户态阻塞，如果没有接收者
    // G被挂起，P继续调度其他G
}()

// 另一个goroutine
go func() {
    time.Sleep(1 * time.Second)
    <-ch  // 唤醒等待的G
}()
```

> **关键点：**
>
> - M和P**不分离**
> - P继续调度其他G
> - 阻塞的G进入等待队列

### **系统调用**

**系统调用阻塞处理完整流程：**

当某个G由于系统调用陷入内核态时：

1. **阻塞时**：M与G绑定进入阻塞状态，P的状态更新为**Psyscall**

2. Handoff检测：

   sysmon线程定期检测，若P处于Psyscall状态超过一定时间（约10ms），则执行Handoff：

   - P与当前M分离
   - P状态从Psyscall变为**Prunning**
   - P被分配给其他空闲M，继续调度其他G

3. 系统调用返回后：

   - **若P仍为Psyscall**（快速返回，未被Handoff）：M直接关联原P，恢复执行G
   - 若P已变为Prunning（慢速返回，已被Handoff）：M尝试获取空闲P
     - 有空闲P → 获取P，继续执行G
     - 无空闲P → G放入全局队列，M进入休眠等待下次调度

```
┌─────────────────────────────────────────────────────────────────┐
│                   系统调用阻塞处理流程 (Handoff机制)              │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  阻塞前:                                                         │
│  ┌─────┐    ┌─────┐    ┌─────┐                                  │
│  │  G  │───→│  P  │───→│  M  │  (正常执行)                       │
│  └─────┘    └─────┘    └─────┘                                  │
│                                                                 │
│  阻塞时:                                                         │
│  ┌─────┐    ┌───────────┐    ┌─────┐                            │
│  │  G  │───→│  P (分离)  │    │  M  │───→ 系统调用 (阻塞)        │
│  │等待 │    │  状态:     │    │绑定G│                            │
│  └─────┘    │  Psyscall │    └─────┘                            │
│             └─────┬─────┘                                       │
│                   │                                             │
│                   ↓                                             │
│             ┌─────┐    ┌─────┐                                  │
│             │  P  │───→│  M2 │  (空闲M接管P，继续调度其他G)       │
│             └─────┘    └─────┘                                  │
│                                                                 │
│  恢复时:                                                         │
│  M完成系统调用 ──→ 尝试获取P ┬─→ 有P则继续执行G                    │
│                            └──→ 无P则G放全局队列，M休眠           │
│                                                                 │
└─────────────────────────────────────────────────────────────────┘
```

代码示例：

```go
go func() {
    // 系统调用，会导致M阻塞
    data, _ := os.ReadFile("/large/file")  // 内核态阻塞
    fmt.Println(len(data))
}()

// 其他goroutine不受影响，P被其他M接管继续执行
```

>**关键点：**
>
>- **P与M分离**（Handoff机制）
>- P被其他空闲M接管
>- 阻塞的M和G绑定
>- 恢复时M尝试重新获取P

### 其他

- **系统监控**：当某个G在P上运行的时间超过10ms时候，或者P处于Psyscall状态过长等情况就会调用retake函数，触发新的调度。
- **主动让出**：由于是协作式调度，该G会主动让出当前的P（通过GoSched），更新状态为Grunnable，该P会调度队列中的G运行。

## goroutine什么情况会发生内存泄漏？如何避免。

**⚡️ Goroutine 内存泄漏的核心本质**

在 Go 中，Goroutine 虽轻量（初始约 **2KB** 栈空间），但如果它因为某种原因**永远无法结束**，它所占用的栈内存及其引用的所有堆对象（变量、Map、Slice 等）将永远无法被 GC 回收。

**判定标准：** 如果一个 Goroutine 启动后，既没有完成任务退出，也没有因为 panic 崩溃，而是永久停留在某个阻塞状态，这就是**内存泄漏**。

### **🔍 场景一：Channel 引起的永久阻塞**

这是最常见的泄露点。Channel 的读写必须成对出现，否则任何一方都可能“长眠”。

**1.1 发送者阻塞（无人接收）**

当主逻辑提前退出或不再需要数据，但后台协程仍在尝试发送时发生。

```go
func leakBySender() {
    ch := make(chan int) // 无缓冲 channel
    go func() {
        ch <- 1 // 如果没有人读这个 ch，这行将永远阻塞，协程无法退出
        fmt.Println("Sent") 
    }()
    // 主逻辑直接 return，没读 ch，子协程就此泄露
}
```

**避坑指南：** 使用 `select` 配合 `default`（直接丢弃）或 `timeout`（限时尝试）。

- **错误写法：** `ch <- 1` 没接收者时永久死等。
- **修正方案：**

```go
// 修正：如果 500ms 内发不出，说明下游堵塞，直接放弃防止泄露
select {
case ch <- data:
    fmt.Println("发送成功")
case <-time.After(500 * time.Millisecond):
    fmt.Println("发送超时，丢弃任务保护协程")
    return // 退出当前 goroutine，防止积压
}
```

**1.2 接收者阻塞（无人发送且未关闭）**

接收方在等信号，但发送方因为异常崩溃或逻辑漏写，既没发数据也没关通道。

```go
func leakByReceiver() {
    ch := make(chan int)
    go func() {
        data := <-ch // 如果发送方不发数据也不 close(ch)，这里永久阻塞
        fmt.Println(data)
    }()
    // 假设此处发生了某个 error 直接返回了，没有通知子协程
    return 
}
```

**避坑指南：** 必须由发送方负责 `close` 通道，或使用 `Context` 强制干预。

- **错误写法：** `<-ch` 在发送方崩溃后永久等待。
- **修正方案：**

```go
// 修正：使用 context 外部控制，一旦主逻辑取消，子协程立即撤退
select {
case data := <-ch:
    fmt.Println("收到:", data)
case <-ctx.Done(): 
    return // 即使 ch 永远没数据，ctx 取消时也能释放内存
}
```

### **🔍 场景二：nil Channel 的“静默死亡”**

对一个未初始化的 `chan`（其值为 `nil`）进行读写，既不会报错也不会 panic，而是会让当前协程**永久挂起**。

```go
func leakByNil() {
    var ch chan int // 仅仅声明，未 make
    go func() {
        ch <- 1 // 永久阻塞，不报错，不可恢复
    }()
}
```

**避坑指南：** 始终确保 `chan` 已被 `make` 初始化，或者在 `select` 中利用其阻塞特性（谨慎使用）。

- **错误写法：** 直接操作 `var ch chan int`。
- **修正方案：**

```go
// 修正：1. 始终 make 初始化；2. 读写前做非空判断
if ch == nil {
    log.Println("通道未初始化，拒绝处理")
    return
}
ch <- 1
```

### **🔍 场景三：生产者/消费者速率不匹配（无退出机制）**

如果生产者产生 Goroutine 的速度远快于消费者的处理速度，且没有限流或统一的退出信号，Goroutine 数量会线性膨胀。

**避坑指南：** 引入 **Worker Pool（工作池）** 模式，固定协程数量，不随任务量无限开启。

- **错误写法：** `for { go func(){...}() }` 来一个任务开一个协程。
- **修正方案：**

```go
// 修正：预先开启固定数量(如3个)的工作协程，任务排队处理
for i := 0; i < 3; i++ {
    go func() {
        for task := range taskCh { // 只有 taskCh 关闭时，协程才结束
            process(task)
        }
    }()
}
// 即使进来 100w 个任务，也只有 3 个 goroutine 在跑，内存极其稳定
```

**🛠️ 如何排查泄露？**

如果你的程序运行几天后内存居高不下，可以通过以下工具“捉鬼”：

1. **`runtime.NumGoroutine()`**：在日志中定期打印。如果数值只增不减，说明有泄露。
2. **`net/http/pprof`**：Go 官方自带的性能分析神器。
   - 访问 `/debug/pprof/goroutine?debug=1` 可以查看所有协程的调用栈。
   - 通过堆栈信息，你可以一眼看到成千上万个协程都卡在了哪一行代码。

## CAP 理论，为什么不能同时满足

CAP 理论是分布式系统设计中的三个基本属性，它们分别是一致性（Consistency）、可用性（Availability）、和分区容错性（Partition Tolerance）。CAP 理论由计算机科学家 Eric Brewer 在2000年提出。

1.一致性（Consistency）：

- 一致性要求系统在所有节点上的数据是一致的。即，如果在一个节点上修改了数据，那么其他节点应该立即看到这个修改。这意味着在任何时刻，不同节点上的数据应该保持一致。

2.可用性（Availability）：

- 可用性要求系统能够对用户的请求做出响应，即使在出现节点故障的情况下仍然保持可用。可用性意味着系统在出现故障时仍然能够提供服务，尽管可能是部分服务。

3.分区容错性（Partition Tolerance）：

- 分区容错性是指系统在面对网络分区的情况下仍能够正常工作。即当节点之间的网络出现故障或无法通信时，系统仍能够保持一致性和可用性。

CAP 理论提出的是在分布式系统中这三个属性不能同时被满足。这是由于在分布式系统中，网络的不确定性和延迟会导致无法同时满足一致性、可用性和分区容错性。

## 切片类型Slice是并发安全的吗？ （考点：并发下的Slice）【简单】

**go语言中的切片并不是并发安全的**

- 共享底层数组：多个切片可以共享同一个底层数组，一个goroutine对数组更改，会影响其他引用数组的切片
- 并发读写：多个goroutine对同一个切片读写，可能会造成竞态条件
- 扩容操作：切片的扩容操作并不是原子性的，多个goroutine同时对一个切片进行append操作，可能会造成数据丢失或覆盖

**解决方法**

- **使用同步原语**：比如使用`sync.Mutex`或`sync.RWMutex`来保护切片操作。
- **拷贝切片**：每个goroutine操作自己的切片拷贝，避免直接操作共享的切片。
- **通道传递**：通过通道传递切片的拷贝，而不是直接传递切片本身。

## go⾥⾯的map是并发安全的吗？如何并发安全。（考点：并发下的map）【简单】

Go里面，**原生的map类型并不是并发安全的**。一旦有多个goroutine同时读写同一个map，就可能遇到**数据竞争和不一致**的问题。

**要让map在并发环境下安全使用，可以这么操作**：

- **使用Mutex**：可以结合sync.Mutex或者sync.RWMutex来手动管理对map的访问。读写锁RWMutex更适合读多写少的场景。
- **使用sync.Map**：Go标准库提供了一个sync.Map类型。它是为并发设计的。它提供了安全的Load、Store和Delete等方法来操作映射。
- **避免共享**：如果可能，尽量让每个goroutine使用自己的map拷贝，然后通过通道传递数据。避免直接共享同一个map。

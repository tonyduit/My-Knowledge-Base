# MySQL八股文

# 架构

## sql语句的执行过程

1.连接器：连接器负责跟客户端建⽴连接、获取权限、维持和管理连接。

2.查询缓存：MySQL拿到⼀个查询请求后，会先到查询缓存看看，之前是不是执行过这条语句。之前执行过的语句及其结果可能会以key-value对的形式，被直接缓存在内存中。

3.分析器：你输入的是由多个字符串和空格组成的⼀条SQL语句，MySQL需要识别出里面的字符串分别是什么，代表什么。

4.优化器：优化器是在表里面有多个索引的时候，决定使用哪个索引；或者在⼀个语句有多表关联(join)的时候，决定各个表的连接顺序。

5.执行器：MySQL通过分析器知道了你要做什么，通过优化器知道了该怎么做，于是就进⼊了执行器阶段，开始执行语句。

# 引擎

## InnoDB和MyISAM有什么区别？


​	这俩引擎设计目标就不一样。MyISAM 是 MySQL 早期的引擎，那会儿互联网还没爆发，大部分场景就是读多写少的静态页面，表锁够用了。InnoDB 是后来 Oracle 收购的，从一开始就奔着企业级事务去的，行锁、MVCC、redolog、undo log这套东西都是为了保证 ACID。

​	从存储结构看，MYISAM 的索引和数据是分开存的，.MYI文件存索引，.MYD 文件存数据，查询时先查索引拿到数据行的物理地址，再去数据文件里捞。InnoDB 用的是聚簇索引，数据直接挂在 B+ 树叶子节点上，主键査询一次 B+ 树就能拿到数据，不用二次寻址。

​	锁机制差别更大。MyISAM 只有表锁，一个写操作会锁住整张表，并发写性能很差。InnoDB 支持行锁，通过 MVCC 实现了读写不阻塞，1000 个并发改同一张表的不同行，互不干扰。

# 索引

## MySQL InnoDB 引擎中的聚簇索引和非聚簇索引有什么区别？

​	聚簇索引的叶子节点存的是完整的行数据，数据和索引绑定在一起。InnoDB 表的数据文件本身就是按主键组织的 B+ 树，所以主键查询只需要一次索引查找就能拿到数据。

​	非聚簇索引的叶子节点只存索引列的值和主键值（非叶子节点也会存储索引列的值，以及其他节点的指针）。比如在 name 列上建索引，叶子节点存的是(name,id)这样的组合。查的时候先在 name 索引里找到对应的 id，再拿着 id 去聚簇索引里査完整数据，这就是回表。

比如执行 `SELECT * FROM user WHERE name ='Alice'`，流程是这样的：

![image-20260120144927212](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120144927212.png)

**和 MyISAM 的对比**

MyISAM 没有聚簇索引，它的主键索引和普通索引结构一样，叶子节点都是只存数据行的物理地址。数据文件和索引文件是分开存储的，查询时先在索引里找到地址，再去数据文件里取数据。

![image-20260120143836390](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120143836390.png)

InnoDB 选择聚簇索引的好处是：主键査询效率高，范围査询时数据物理上连续，能利用磁盘预读。坏处是二级索引查询多一次回表，插入时维护数据有序有开销。

## MySQL索引类型有哪些？

MySQL 索引可以从三个维度来分类：数据结构、存储方式、索引性质。面试时一般先从数据结构角度切入，重点讲 B+ 树素引，然后再展开聊聚簇索引和非聚簇索引的区别。

从数据结构角度看，MySQL支持这几种索引：

1）B+ 树索引:最常用的，InnoDB 和 MVISAM 默认都用它。多层平衡树结构，叶子节点用链表串起来，既能快速定位单条记录，又能高效做范围扫描，时间复杂度O(logdN)（d是每个节点的分支数）。

2）哈希索引:通过哈希函数直接算出数据位置，等值査询 O(1)级别，但不支持范围査询和排序。Memory 引擎默认用哈希索引，InnoDB 有个自适应哈希索引会自动建，不用手动管。

3）全文索引:把文本分词后建倒排索引，类似搜索引擎的原理。适合对 TEXT 类型字段做关键字搜索，比如文章内容检索

4）空间索引:基于R 树实现，专门处理地理坐标这种多维数据，支持区域查询、距离计算。

从 InnoDB 存储方式看，分两类:

1）聚簇索引:主键索引就是聚簇索引，叶子节点直接存完整的行数据，数据按主键顺序物理存储。一张表只能有一个聚簇索
引。

2）非聚簇索引:也叫二级索引，叶子节点只存索引字段值和主键值。査完二级索引还得拿着主键去聚簇索引里再查一遍，这个过程叫回表。

从索引性质看，有这几种:

1）主键索引:唯一且非空，每张表只能有一个。InnoDB 里主键索引就是聚簇索引。

2）唯一索引:保证列值不重复，但允许有 NULL，可以有多个 NULL。

3）普通索引:没有唯一约束，纯粹为了加速查询。

4）联合索引:多列组合成一个索引，遵循最左前缀原则，列顺序很重要。

5）全文索引:文本搜索用。

6）空间索引:GIS 数据用。

### 为什么要用B+树做索引？

​	数据库查询有两大类操作：等值査询和范围查询。哈希索引等值査询快，但范围查询搞不定。B+ 树两个都能扛，而且叶子节点用双向链表连起来，范围扫描的时候顺着链表走就行，不用回溯。

​	B+ 树还有个特点是树高很矮。一个3层的 B+ 树，能存 2000 万左右的数据。査任何一条数据最多3次磁盘 IO，这个性能在机械硬盘时代非常重要。

![image-20260120151931434](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120151931434.png)

## MySQL索引的最左前缀匹配原则是什么？

MySQL 索引的最左前缀匹配原则是指使用联合索引时，查询条件必须从索引的最左列开始匹配。联合索引包含多个列，查询时必须先有第一个列的条件，然后是第二个列，以此类推。

这是因为联合索引在 B+ 树中的排列方式是“从左到右”的顺序。比如联合索引`(first_name，last_name，age)`会先按 first name 排序，first name 相同再按 last name 排序，last name 相同再按 age 排序。

MySQL查找时会优先用 first name 作为匹配依据，然后依次用 last name 和 age。跳过最左侧字段，后面的列在 B+ 树中是无序的，压根没法利用索引快速定位。

<img src="MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120152530010.png" alt="image-20260120152530010" style="zoom:50%;" />

**为什么范围查询的字段会终止后续的字段使用索引？**

联合索引 `idx_a_b_c (a, b, c)` 的排序规则是：

✅ **先按 a 排序 → a 相同则按 b 排序 → b 相同则按 c 排序**（层级嵌套排序）

```sh
# 示例
A: 1 B: 1 C: 1
A: 1 B: 1 C: 2

A: 1 B: 2 C: 1
A: 1 B: 2 C: 2

A: 2 B: 1 C: 1
A: 2 B: 1 C: 2

A: 2 B: 2 C: 1
A: 2 B: 2 C: 2
```

❌ 不是 a、b、c 各自独立排好序再拼接

这种排序下，`a=1 AND b>2` 的数据里，`c` 是混乱的，完全无法利用索引快速查找，这也是为什么数据库不会这么设计。

### 实例讲解

假设当前表有一个联合索引`(a，b，c)`。

符合最左匹配原则的查询条件：

```sql
where a = 1;
where a = 1 and b = 2;
where a = 1 and b = 2 and c = 3;
```

不符合最左匹配原则的查询条件：

```sql
where b = 2;
where c = 3;
where b = 2 and c = 3;
```

部分命中的查询条件：

```sql
where a = 1 and c = 3;
```

这个查询可以用上联合索引`(a，b，c)`，但只能利用 a=1 这个条件过滤。但是在 MySQL 5.6 版本引入了索引下推优化，可以在引擎层查到 a=1 的数据后，直接用c过滤掉不符合的数据，减少回表次数。

<img src="MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120152043396.png" alt="image-20260120152043396" style="zoom:50%;" />

**等值查询（`=`）可以让联合索引继续向右匹配；而范围查询（`>`, `<`, `BETWEEN` 等）会“终止”后续列的索引查找能力，但当前列及之前的列仍然可以高效使用索引。**

| 查询语句                          | 能否用索引？      | 说明                                                         |
| --------------------------------- | ----------------- | ------------------------------------------------------------ |
| `WHERE a = 1 AND b = 2 AND c = 3` | ✅ 完全使用        | 三列都用于索引查找                                           |
| `WHERE a = 1 AND b > 2 AND c = 3` | ✅ 部分使用        | `a` 和 `b` 用于索引（`b` 是范围），`c` 不能用于查找，但可能通过 ICP 过滤 |
| `WHERE a > 1 AND b = 2`           | ⚠️ 仅 `a` 用于索引 | `a` 是范围，所以 `b` 无法用于索引查找（即使 `b=2`）          |
| `WHERE a = 1 AND b LIKE 'abc%'`   | ✅ `a` 和 `b` 可用 | `LIKE '前缀%'` 是范围查询，但能用索引                        |
| `WHERE a = 1 AND b LIKE '%abc'`   | ❌ `b` 无法用索引  | 后模糊匹配，索引失效                                         |

**✅ 情况一：SELECT 的字段都在索引中（覆盖索引）**

比如：

```sql
SELECT a, b, c FROM t WHERE a = 1 AND b > 2 AND c = 3;
-- 或者
SELECT c FROM t WHERE a = 1 AND b > 2 AND c = 3;
```

✅ **此时：**

- 联合索引 `(a, b, c)` 包含了所有需要的数据；
- MySQL 执行过程：
  1. 利用 `a = 1` 定位到索引起始位置；
  2. 在 `a=1` 的范围内，扫描 `b > 2` 的记录；
  3. 在扫描过程中，**直接检查 `c = 3` 是否成立**（因为 `c` 在索引里）；
  4. 满足条件的记录，**直接从索引返回，无需回表**。

🔍 此时 `EXPLAIN` 会显示：

```sql
type: range
key: idx_a_b_c
key_len: ...（覆盖 a+b，因为 b 是范围）
Extra: Using where; Using index   ← 注意！是 "Using index"，不是 "Using index condition"
```

> 💡 **“Using index” 表示使用了覆盖索引，完全不需要回表。**

📌 **结论：在这种情况下，`c = 3` 虽然不能用于索引 Seek（因为 `b` 是范围），但由于索引覆盖 + 索引内过滤，效果等同于“高效使用了索引”，且不回表。**

**⚠️ 情况二：SELECT 了索引外的字段（需要回表）**

比如：

```sql
SELECT name FROM t WHERE a = 1 AND b > 2 AND c = 3;
-- 假设 name 不在 (a,b,c) 索引中
```

✅ **此时：**

- `a = 1` → 用于 Seek；
- `b > 2` → 范围扫描；
- `c = 3` → **无法用于 Seek，但可通过 ICP 在索引层过滤**；
- 对于满足 `a=1 AND b>2 AND c=3` 的每一条索引记录，**仍需回表**去聚簇索引中取 `name` 字段。

🔍 `EXPLAIN` 会显示：

```
Extra: Using index condition   ← 注意！是 "index condition"，不是 "index"
```

> 💡 **“Using index condition” 表示用了 ICP：在存储引擎层用 `c=3` 过滤，避免不必要的回表，但最终仍需回表取数据。**

📌 **结论：`c = 3` 通过 ICP 减少了回表次数（只回表符合条件的行），但并没有“不用回表”。**

## 什么是回表

回表是指用二级索引查询时，因为二级索引的叶子节点只存索引列的值和主键值，拿不到其他字段的数据。如果查询需要其他字段，就得拿着主键再去聚簇索引查一遍完整的数据行，这个过程就叫回表。

![image-20260120154643595](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120154643595.png)

### 实例讲解

举个例子：`select * from user where age = 28;`，user 表有 id、name、age 三个字段，age 上有索引。
1）先走 age 二级索引，找到 age = 20 的记录，拿到主键值：

<img src="MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120154747702.png" alt="image-20260120154747702" style="zoom:50%;" />

2）因为用了`select *`需要 name、age、id 三个字段，但 age 索引里没有 name，只有age和id（age在叶子节点和非叶子节点都有，id只存在于叶子节点），得拿着主键去聚簇索引查完整数据：

<img src="MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120155030883.png" alt="image-20260120155030883" style="zoom:50%;" />

最终拿到`id=2, name='小鱼’, age=20`这条完整记录

**回表的性能代价**

​	回表不只是多查一次那么简单，还会带来大量随机 I/O。

​	因为通过二级索引拿到的主键id 不是连续的。比如 age = 20 的人很多，在 age 索引里按年龄排序，但对应的 id 是无序的，可能是 2、58、199、1024 这种散落分布。拿这些 id 去聚簇索引查，每次都要定位到不同的数据页，产生大量不连续的 I/O。

​	顺序 I/O 可以利用磁盘预读，一次读一大块连续数据，非常快。随机 I/O 每次都要重新寻址，磁盘得来回转，慢得多。所以如果查询返回几万行数据，每行都要回表，性能会急剧下降。

**如何避免/减少回表**

1）覆盖索引

​	如果查询需要的列都在索引里，就不用回表了。比如索引是(age，name)查询索select name from user where age=20，引叶子节点存了 age、name、主键，直接返回就行。

EXPLAIN 的 Extra 列显示 using index 就说明走了覆盖索引，没有回表。

2）索引下推

​	MySQL5.6 引入的优化。假设索引是(age，name)，查询 `where age=20 and name like'%张'`，以前的做法是先通过 age=20 拿到所有主键，全部回表拿完整数据，再在 Server 层用 name 过滤。有了索引下推，在引擎层就能用`name like '%张'`先过滤一遍，不符合条件的直接跳过不回表，大大减少回表次数。

3）减少 `select *` 的使用

​	不要图方便什么都用 `select *`。如果只需要索引里的字段，显式指定列名，能避免不必要的回表。

**什么时候 MySQL 会放弃索引直接全表扫描**

​	如果回表次数太多，MySQL优化器可能认为还不如直接全表扫描划算。

​	经验值大概是：如果查询返回的数据量超过表的 15%-30%，优化器可能放弃二级索引。因为与其回表几十万次产生随机I/O，不如全表顺序扫描一遍，虽然扫的数据多，但都是顺序 I/O，整体可能更快。

​	这也是为什么有时候明明建了索引，EXPLAIN 却显示全表扫描。不是索引没用，是优化器算了一笔账，觉得不走索引更快。

**怎么判断一个查询有没有回表?**

​	看 EXPLAIN 的 Extra 列。如果显示 `using index` ，说明走了覆盖索引，没有回表。如果没有这个提示，或者显示
`using index condition` ，说明有回表。另外如果 type 是 index，表示全索引扫描，也可能有回表。

## 什么是索引下推？

​	索引下推是 MySQL 5.6 引入的优化技术，能减少回表次数，提升查询效率，核心思路是把部分查询条件从 Server 层下推到存储引警层，在引擎层就把不符合条件的数据过滤掉，不用再回表查完整数据。

- 以前的流程是：引擎层用索引定位数据 → 返回**主键**给 Server 层 → Server 层拿着主键回表取完整数据 → Server 层再用剩余条件过滤。
- 有了索引下推（ICP）：**引擎层先在索引上完成过滤** → 只对过滤后符合条件的索引记录做回表 → 再把回表后的完整数据返回给 Server 层。不符合条件的压根不回表，大大减少 I/O。

索引下推主要用在联合索引上。

**ICP 生效的前提：**

- 查询使用了**二级索引（非聚簇索引）**；
- WHERE 条件中包含**无法用于“查找（lookup）”但存在于索引中的列**，
  - 例如：索引为：(a, b)，SELECT * FROM t WHERE a = 1 AND b LIKE '%xyz%';；
  - `a = 1` 用于定位；
  - `b LIKE '%xyz%'` 无法用于索引查找（因为不是前缀匹配），但 `b` 在索引中；
  - 存储引擎可以在遍历 `a=1` 的所有索引项时，**直接检查 `b` 是否包含 `'xyz'`**，而不回表 → **这就是 ICP**。
- 查询**需要回表**（即不是覆盖索引）。

<img src="MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120184227271.png" alt="image-20260120184227271" style="zoom:50%;" />

### 实例讲解

假设 people 表有联合索引`INDEX(zipcode，lastname，firstname)`，执行以下查询:

```sql
SELECT * FROM people
  WHERE zipcode='95054'
  AND lastname LIKE '%etrunia%'
  AND address LIKE '%Main Street%';
```

**没有索引下推的情况：**

​	联合索引只能用上`zipcode='95054'`这个条件，`lastname LIKE '%etrunia%'`虽然 lastname 在索引里，但因为是左模糊匹配，走不了索引查找，只能在 Server 层过滤。引擎层把所有`zipcode='95054'`的记录全部返回，每条都要回表拿完整数据，Server 层再用 lastname 和 address 过滤。

**有了素引下推：**

引擎层定位到`zipcode='95054'`的数据后，address 过滤，虽然 lastname 用不了索引查找，但索引里存了 lastname 的值。引擎层可以直接用`lastname LIKE '%etrunia%'`过滤，不符合条件的直接跳过不回表，只有符合条件的才回表取完整数据，再由 server 层用 address 过滤。

<img src="MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120185400179.png" alt="image-20260120185400179"  />

假设`zipcode='95054'`有 10000 条记录，符合 lastname 条件的只有 100 条。没有索引下推要回表 10000 次，有了索引下推只回表 100 次，差距巨大。

**如何判断是否生效**

看EXPLAIN的Extra列，如果显示 using index condition，说明用上了索引下推。

```sql
EXPLAIN SELECT * FROM people
  WHERE zipcode='95054'
  AND lastname LIKE '%etrunia%';
```

Extra 显示`Using index condition`就表示 lastname 条件被下推到引擎层了

**索引下推的限制**

1）MySQL 5.6 及以后版本才支持，InnoDB 和 MyISAM 都能用

2）子查询可能导致索引下推失效，具体得看 EXPLAIN

3）条件中用了函数或表达式，索引下推也不生效。比如 WHEREEAR(create_time)=2024，这种写法索引本身就用不上，更别说下推了

4）主键查询不需要索引下推。主键索引的叶子节点直接存完整数据，压根不存在回表，下推没有意义

5）覆盖索引也不需要索引下推。都不用回表了，过滤早晚没区别

**索引下推和覆盖索引的区别**

这两个优化都能减少 I/O，但原理不同：

| 特性        | 索引下推                  | 覆盖索引              |
| ----------- | ------------------------- | --------------------- |
| 解决的问题  | 减少回表次数              | 完全避免回表          |
| 是否回表    | 需要回表，但是次数少      | 不需要                |
| EXPLAIN标识 | Using index condition     | Using index           |
| 使用场景    | select * 且有额外过滤条件 | select 的列都在索引里 |

两者可以同时存在吗？

不能。如果走了覆盖索引，压根不回表，索引下推就没有用武之地了

## 如何排查是否用到了索引？

​	索引不一定有效。建了索引不代表查询就会用，用了索引也不代表查询就快。

​	MySQL最终是否走索引，靠的是优化器的成本计算。优化器会评估走索引和全表扫描各自的 I/O 成本和 CPU 成本，哪个便宜选哪个。有时候全表扫描确实成本低，比如表就几百行数据，走索引还不如直接扫；有时候是统计信息不准，导致优化器算错账，明明该走索引却选了全表扫描。

​	排査索引效果最直接的办法就是用 EXPLAIN 命令。在 SQL 前面加上 EXPLAIN，就能看到 MySQL 选择的执行计划。重点看这几个字段：

1）type:访问类型，ALL 是全表扫描，index 是全索引扫描，range 是范围扫描，ref 是等值匹配。ALL 基本就是没走索引，ref和 range 才是真正利用了索引的快速查找能力。

2）key:实际用的索引名称，NULL就是没用上索引。

3）rows:预估扫描的行数，这个数字越大说明查询代价越高。

## 如何使用EXPLAIN语句进行查询分析？

​	EXPLAIN 是 MySQL分析 SQL 执行计划的核心工具，在 SELECT 语句前加上 EXPLAIN 就能看到优化器打算怎么执行这条查
询。重点关注这几个字段：

select type 常见类型

- SIMPLE：简单查询，没子查询没 UNION。

- PRIMARY：最外层的查询

- SUBQUERY：SELECT或 WHERE 里的子查询

- DERIVED：FROM 子句里的子查询，MySQL会把它物化成临时表

- UNION：UNION 里第二个及之后的 SELECT

- UNION RESULT：UNION 的结果集

1）type 访问类型，直接决定了査询效率。性能从高到低排列：`const > eq_ref > ref > range > index > ALL`。看到 ALL就意味着全表扫描，数据量一大，性能就崩

2）key 实际用到的索引。possible keys 只是候选，key 才是优化器最终选的。如果显示 NULL 就说明压根没走索引

3）rows 预估要扫描的行数。这个值越小越好，几百行和几十万行的差距可能是毫秒和几秒的差别

4）Extra 额外信息藏着很多细节。

### **Extra的常见关键字**

**一、高效 / 正常关键字（优先关注）**

| 关键字                                  | 含义                                                   | 典型场景                                                     |
| --------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------ |
| `Using index`                           | 覆盖索引（仅用索引就能返回结果，无需回表）             | 查询字段都在索引里，如 `SELECT a,b FROM t WHERE a=1`（索引包含 a,b） |
| `Using where`                           | 用 WHERE 条件过滤数据（过滤在存储引擎 / 服务器层完成） | 有 WHERE 条件且条件能命中索引，如 `SELECT * FROM t WHERE a=1` |
| `Using index condition`                 | 索引下推（ICP）：存储引擎层先过滤索引数据，减少回表    | 联合索引范围查询后过滤后续字段，如 `SELECT * FROM t WHERE a=1 AND b>2 AND c=3` |
| `Using MRR`                             | 多范围读优化：批量处理索引扫描结果，减少磁盘 I/O       | 大范围索引查询（如 `a IN (1,2,3...)`）                       |
| `Using join buffer (Block Nested Loop)` | 用连接缓冲区优化关联查询（轻量版，无性能问题）         | 小表关联大表，且关联字段有索引                               |
| `Not exists`                            | 子查询优化为反连接，避免重复扫描                       | `WHERE NOT EXISTS (SELECT 1 FROM t2 WHERE t1.id=t2.id)`      |

关键解读

- `Using index` 是**最优状态**（覆盖索引），查询效率最高；
- `Using where; Using index` 组合：用索引过滤 + 覆盖索引，完美优化。

**二、低效关键字（需优化）**

这类关键字代表查询有性能瓶颈，必须优化。

| 关键字                          | 含义                                                     | 典型场景                                             | 优化方向                                                     |
| ------------------------------- | -------------------------------------------------------- | ---------------------------------------------------- | ------------------------------------------------------------ |
| `Using filesort`                | 无法用索引排序，需在内存 / 磁盘做文件排序                | `ORDER BY b` 但 b 无索引，或联合索引中范围字段后排序 | 给排序字段加索引，或调整联合索引顺序（把排序字段放范围字段前） |
| `Using temporary`               | 需要创建临时表存储中间结果（如排序 / 分组）              | `GROUP BY b` 但 b 无索引，或 `DISTINCT` 无索引       | 给分组 / 去重字段加索引，避免临时表创建                      |
| `Using join buffer (Hash Join)` | 哈希连接缓冲区：关联字段无索引，用哈希表做连接（性能差） | `t1 JOIN t2 ON t1.name=t2.name`，但 name 无索引      | 给关联字段加索引，改为索引连接                               |
| `Range checked for each record` | 逐行检查索引范围（无可用索引，性能极差）                 | 关联查询中，内层表的关联字段无索引                   | 给内层表关联字段加索引                                       |

关键解读

- `Using filesort` 和 `Using temporary` 是**两大性能杀手**，出现时必须优化；
- 比如 `SELECT * FROM t WHERE a=1 ORDER BY b`，若索引是 `(a,c)`，则 `b` 无索引，会触发 `Using filesort`。

### **type 的每个级别具体含义:**

- const：主键或唯一索引等值查询，最多一行匹配，最快

- eq_ref：连接查询里通过主键或唯一索引关联，每次只取一行

- ref：用非唯一索引查，可能返回多行

- range：索引范围扫描，用在 `BETWEEN`、`>`、`<`这类条件上

- index：扫描整棵索引树，比ALL好但还是很慢

- ALL：全表扫描，遇到大表直接起飞

**EXPLAIN 的两个增强版本**

​	MySQL 5.6+ 支持 `EXPLAIN FORMAT=JSON` ，输出更详细的JSON 格式，能看到每一步的成本估算。MySQL 8.0.18+ 还新增了`EXPLAIN ANALYZE`，这个更厉害，会真正执行査询并给出实际的执行时间和行数，不只是预估值。调试复杂查询的时候特别有用，


### **实战案例**

**从5000行扫描优化到500行**

```sql
CREATE TABLE employees (
    employee_id INT PRIMARY KEY,
    first_name VARCHAR(50),
    last_name VARCHAR(50),
    department_id INT,
    salary DECIMAL(10, 2),
    hire_date DATE,
    INDEX (department_id)
);
```

要查部门 ID 为 5 且薪水在 50000 到 100000 之间的员工，按薪水降序：

```sql
EXPLAIN SELECT employee_id, first_name, last_name, salary
FROM employees
WHERE department_id = 5 AND salary BETWEEN 50000 AND 100000
ORDER BY salary DESC;
```

执行计划输出：

| id   | select_type | table     | type | key           | rows | Extra                       |
| ---- | ----------- | --------- | ---- | ------------- | ---- | --------------------------- |
| 1    | SIMPLE      | employees | ref  | department_id | 5000 | Using where; Using filesort |

​	问题一眼就能看出来：走了 department id 索引但 rows 是 5000，而且 Extra 里有 Using filesort，说明虽然过滤用了索引，排序却要额外做一次文件排序。

优化方案是建一个复合索引，把 department id 和 salary 都包进去：

```sql
CREATE INDEX idx_department_salary ON employees (department_id, salary);
```

再一次 EXPLAIN：

| id   | select_type | table     | type  | key                   | rows | Extra       |
| ---- | ----------- | --------- | ----- | --------------------- | ---- | ----------- |
| 1    | SIMPLE      | employees | range | idx_department_salary | 500  | Using where |

​	rows 从 5000 降到 500，Using filesort 也没了。因为复合索引里 salary 已经排好序了，查询直接顺着索引拿数据就行，不用再单独排一遍。

**解读EXPLAIN变化原因**

| 字段    | 原值                          | 新值          | 原因                                                         |
| ------- | ----------------------------- | ------------- | ------------------------------------------------------------ |
| `type`  | `ref`                         | `range`       | 原来：`department_id = 5` 是等值 → `ref`现在：建立了新的联合索引 ，虽然 `department_id = 5` 是等值，但 `salary` 是范围条件（`BETWEEN`），整个查询被视为范围扫描 → `range` |
| `rows`  | 5000                          | 500           | 原来：先取出全部 5000 行，再过滤 `salary`现在：索引直接支持 `department_id=5 AND salary BETWEEN...`，现在：只扫描符合条件的约 500 行 |
| `Extra` | `Using where; Using filesort` | `Using where` | `Using filesort` 消失：因为新的联合索引中 `salary` 已有序，可直接按需读取（甚至反向扫描） |

**❌ 没有复合索引时：为什么 `rows = 5000`？**

你只建了 `INDEX(department_id)`。

执行过程如下：

1. **用 `department_id` 索引快速找到所有 `department_id = 5` 的记录** → 共 **5000 行**。
2. 但 **`salary` 不在索引里**，所以 MySQL 必须对这 5000 行**逐个回表**（去主键聚簇索引中读取完整行），才能知道每个人的 `salary`。
3. 然后在 Server 层判断：`salary BETWEEN 50000 AND 100000`？——最终筛出 500 行。
4. 再对这 500 行按 `salary` 排序（因为索引没排过 `salary`）→ 触发 `filesort`。

所以 `EXPLAIN` 中的 `rows = 5000` 表示：**MySQL 预估要读取 5000 行数据（回表 5000 次）才能完成过滤。**

**✅ 建了复合索引 `(department_id, salary)` 后：为什么 `rows = 500`？**

现在，索引的叶子节点存储的是：

```sql
(department_id, salary, 主键)
```

并且**按 `(department_id, salary)` 升序排列**。

执行过程变成：

1. 直接在索引中查找：
   - 先定位到 `department_id = 5` 的起始位置；
   - 然后在这个部门内，**只扫描 `salary` 在 50000～100000 范围内的索引项**。
2. 因为 `salary` 就在索引里，**不需要回表就能判断是否满足条件**！
3. 存储引擎可以直接跳过 `salary < 50000` 或 `> 100000` 的记录，**只读取符合条件的约 500 个索引项**。
4. 虽然最后还是要回表取 `first_name`, `last_name`（因为不在索引中），但**只需要回表 500 次，而不是 5000 次**。

**如果没有索引下推会怎么样？**

| 场景                | 执行流程                                                     | 核心差异                          |
| ------------------- | ------------------------------------------------------------ | --------------------------------- |
| 有联合索引 + 无 ICP | 1. 引擎层定位 `department_id=5` → 2. 将5000个主键返回给 Server 层 → 3. 回表 5000 条 →  4. Server 层再通过条件过滤5000条数据 | 过滤 `salary` 在**Server 层**完成 |
| 有联合索引 + 有 ICP | 1. 引擎层定位 `department_id=5` → 2. 引擎层在索引里过滤 `salary` 条件 → 3. 回表 500 条 → 4. 返回给 Server 层 | 过滤 `salary` 在**引擎层**完成    |

**关键痛点**：无 ICP 时，Server 层必须先回表拿到 5000 条完整数据，才能判断 `salary` 条件 —— 哪怕其中 4500 条是无效的，也得先回表，浪费大量 I/O。

## 索引失效的场景

​	索引失效是面试高频考点，场景不少，但背后的原因基本就两类：一是查询条件导致索引树的快速查找能力用不上，二是优化器算了一笔账觉得不划算。

1）联合索引不符合最左前缀

​	假设有个联合索引 `idx_name_age_id`，查询写成 `WHERE age=10 AND id=1` 跳过了 name 字段，最左前缀匹配失败，索引树的有序性利用不上，退化成全索引扫描甚至全表扫描。

2）索引列上做了运算

​	`WHERE id+3=8` 这种写法，MySQL 得把每行的 id 拿出来算一遍，没法直接在索引树上定位，只能全表扫描。

3）索引列上用了函数

​	`WHERE LOWER(name)=cong`，对索引列套了函数，索引树里存的是原始值，函数处理后的值根本不在树里，还是得全表扫。MySQL 8.0 可以建函数索引来解决这个问题。

```sql
-- 索引失效
SELECT * FROM users WHERE YEAR(birthday) = 1990;
-- 优化后
SELECT * FROM users WHERE birthday >= '1990-01-01' AND birthday < '1991-01-01';
```

4）LIKE 左侧带通配符

​	`WHERE name LIKE '%cong%'`这种写法，索引是按字符顺序排的，左边不确定就没法定位起始位置，只能全表扫。`LIKE 'cong%'`是可以走索引的。

5）OR 连接了非索引字段

​	`WHERE name='cong' OR age=18`，如果 age 没索引，MySQL 没法通过索引快速过滤 age 条件，整个查询可能退化成全表扫描。

6）隐式类型转换

​	name 是 varchar 类型，查询写成`WHERE name=1`，MySQL会做隐式转换，相当于`WHERE CAST(name AS signed int)=1`，就等于索引列上套了函数，索引失效。联表查询时两边字段编码不一致也有同样的问题。

```sql
-- name 是 varchar 类型，传入数字会触发隐式转换
SELECT * FROM users WHERE name = 1;  -- 索引失效
SELECT * FROM users WHERE name = '1';  -- 正常走索引
```

7）优化器认为全表扫描更划算

​	同一个索引，查热点数据可能走全表，查冷门数据走索引。比如订单表按商品 ID 查，热门商品占了 80% 的订单，走索引反而要回表几十万次，不如直接全表扫描。

8）ORDER BY 没配合好

​	ORDER BY 后面的字段不是主键，也不是覆盖索引，MySQL可能选择全表扫描再排序，而不是走索引

**记忆口诀**

> **“最左算盘糊，函隐二大爷，回排划不来。”**

- **最左**：最左前缀原则失效。
- **算盘**：索引列参与运算。
- **糊**：LIKE 开头百分号（模糊查询）。
- **函**：索引列用了函数。
- **隐**：隐式类型转换。
- **二大爷**：OR 连接了无索引字段（谐音“二”）。
- **回**：回表次数太多，优化器选全表。
- **排**：ORDER BY 没用好。

## 为什么索引生效了反而查询变慢了呢？

​	确认是否选对了索引！MySQL 根据优化器会评估成本选择对应的索引，但有时候 MySQL 因为估计值不准确，导致选错了索
引，因此查询速度反而更慢。

**关于使用索引的进一步认识**

为了故事可以顺利的发展，先来一张表，DDL如下:

![image-20260120164244903](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120164244903.png)

现在要执行这个语句 `SELECT * FROM yes.t1 where f3 = 11;`

你觉得用的是哪个索引?

​	很多同学可能会觉得虽然有 idx_f2_f3 这个联合索引，但是査询条件是 f3，没有 f2，不符合最左匹配原则，所以很显然只能进行全表扫描。

我们来 explain 一下，看看:

![image-20260120164409909](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120164409909.png)

​	可以看到结果，key 是 `idx_f2_f3` ，所以这个査询用上了 `idx_f2_f3` 这个索引！这里可能有人就理解不了，怎么不符合最左索引原则也能用上联合索引了呢?

​	从 explain 结果来看，确实用上的联合索引，但是它的 type 是 index，所以它不是你认为的那种用上索引，它等于全扫描的联合索引来获取结果。现在不太理解没事，听下面好好解释。

### **到底什么叫用了索引?**

​	我们都知道 InnoDB 是基于聚簇索引来构建数据的，在没有创建其它二级索引的前提下，你查询数据就必须且只能用聚簇索引，因为数据就只在这个索引上，那你找数据不用这个索引那用什么呢？

​	如果你建起了其他二级索引，那么查找数据就可能不用聚簇索引，而是只用上二级索引就能直接得到想要的数据（就是上面查询的例子）。

​	综上所述，你在 InnoDB 查找任何数据，都只能用索引。

​	那为什么平日里有人说这个不走索引，走了全表扫描呢？

​	我们都知道默认 InnoDB 的索引结构是 B+ 树，这个树有个特性，它的叶子节点之间是通过链表相连的。所以只要我们找到主键索引最左边的叶子结点，然后往右顺序遍历扫描，就能得到这张表的所有记录，这样的扫描方式就叫全表扫描。

![image-20260120164828684](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120164828684.png)

那什么叫用上索引？

![image-20260120164910051](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120164910051.png)

看红色的查询路线没，能利用树的快速查找能力来定位到数据所在的页，这样的查询才能算用上索引。

那从主键索引反推到二级索引，其实是一样的。能利用二级索引树的特性来查找数据，就是用上了索引。

但是如果用不上二级索引树的快速査找，是否有像全表扫描这样，直接扫描二级索引的所有叶子节点的操作呢？

有的，就是我们上面的例子，我再把执行结果的截图搬下来:

![image-20260120165136862](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120165136862.png)

这次査询 MySQL 就是全扫描二级索引`idx_f2_f3`来直接返回所要的数据。

原因就是二级索引已经包含了査询所要到全部数据：f1、f2、f3，所以直接全扫描二级索引即可。

可以看到 explain 的 type=index，即全扫描二级索引。

这也叫用上了索引。

此时我们换用 f2 来作为查询条件，这样就符合最左匹配原则了，我们来看看 explain 有什么区别:

![image-20260120165406376](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120165406376.png)

可以看到还是用了`idx_f2_f3`，只是 type 变成 ref，这个 ref 就表明可以与常量进行等值匹配时来快速查询得到结果。

这也叫用上了索引。

好了，我们来总结一下到底什么叫用了索引:

- 利用主键索引快速查找

- 利用二级索引快速查找

- 全扫描二级索引进行查找

​	以上这三种就是我们平日里所说的用上了索引，然后全扫描主键索引就是我们所说的全表扫描（等价于没用上索引，但是我们知道它其实是用上了主键索引对吧？）

至此，我想你应该已经清楚，到底什么叫用了索引了。

### **既然都要全扫描，为什么要扫描二级索引，而不是主键索引？**

因为主键索引存储了所有的数据，包括数据行相关的事务ID、回滚指针等等。

而二级索引不包含这些，它只有主键值和索引列的值。

所以相对而言直接读取二级索引开销会更小一些，所以在索引能覆盖返回值的时候，一般都会选择二级索引来查找。比如我把上面的表再加个字段：f4。

![image-20260120165716468](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120165716468.png)

现在我们再来执行`SELECT * FROM yes.t1 where f3= 11;`

![image-20260120165033313](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260120165033313.png)

可以看到，这个时候就没用上二级索引了，而是直接全表扫描了。原因就是二级索引无法覆盖返回值，因为多了个 f4 的字段。

如果用了`idx_f2_f3`这个索引，想要得到 f4 的值，还需要再得到的主键再去主键索引里面进行査找，然后才能得到 f4 的值这样回表的效率就低了。

当然其实结果还不一定，有时候也有可能 MSQL 的统计信息有误，用错了索引。因为 MSQL 是基于成本来选择执行计划的，有 I/O 成本和 CPU 成本，哪个索引成本低就用哪个索引。

## 三层B+树能存多少条数据？

三层 B+ 树大约能存 2000 万条记录，这是面试中最常考的结论。

具体算法是这样的：InnoDB 默认页大小是 16KB，非叶子节点存的是主键和指针，叶子节点存的是完整数据行。

假设主键是 bigint 占8字节，指针占6字节，那么一个非叶子节点能存的索引项数量是：16 x 1024÷14≈1170 个。

假设每条数据记录占 1KB，那么一个叶子节点能存的记录数是：16 / 1=16 条。

三层 B+ 树的结构是：1 个根节点 → 1170 个中间节点 → 1170 x1170 个叶子节点。

总记录数 = 1170 x 1170 x 16 ≈ 2190 万条。

![image-20260302113737894](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260302113737894.png)

实际场景中数据记录往往比 1KB 小，能存的数据量会更多。这个计算主要是让你理解 B+ 树为什么「矮胖」，三层就能撑住千万级数据。

![image-20260302113833368](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260302113833368.png)

### **页大小的影响**
`InnoDB`默认页大小是 16KB，可以通过`innodb_page_size`参数调整，支持 4KB、8KB、16KB、32KB、64KB 这几个档位页越大，单个非叶子节点能存的指针越多，树的扇出越大，树高越低，随机I/O越少。但页太大也有问题：

1）内存利用率下降，一个页只存了几条数据也要占 64KB 内存

2）刷脏页的粒度变大，写放大更严重，为了改一点数据要将整个页的数据都写入磁盘

总结：这是一个**平衡艺术**：

- **太小（4KB）：** 树太高，I/O 次数多；索引前缀压缩效果差。
- **太大（64KB）：** 刷脏压力大（写放大），内存利用率低（内部碎片）。

**另外，大页虽然能减少随机I/O，但 SSD 极大地弱化了随机 I/O 带来的惩罚。**

所以一般保持默认 16KB 就行，只有特殊场景才调整。比如做大数据分析，行数据特别宽，可以考虑调大。

**什么是“刷脏页”？**

**脏页（Dirty Page）是指在内存中被修改过，但还没有同步到磁盘上的数据页。**

为了性能，MySQL 修改数据时是先改内存（Buffer Pool），并记录日志（Redo Log），而不是直接写磁盘（磁盘太慢）。

- **过程：**后台线程会定期把内存里的修改后的页写回磁盘，这个动作叫**刷脏（Flushing）**。
- **页大小的影响：**如果你改了页里的 1 字节数据，刷脏时也要把整个 16KB（或 64KB）的页写回磁盘。
  - **写放大：**页越大，为了改一点点数据而必须写入磁盘的物理字节数就越多，对磁盘带宽压力越大。

### **不同场景下的存储量差异**

上面按每行 1KB 算的，实际业务中行大小差异很大:

1）用户表、配置表这种字段少的，一行可能就几百字节，一个叶子节点能存几十条，三层能存好几千万

2）文章表、评论表这种有大 text 字段的，一行可能好几 KB，三层可能就存几百万

3）如果主键不是 bigint 而是 uuid 字符串，非叶子节点每个索引项更大，扇出变小（16 x 1024 / 36 ≈ 390），三层存储的数据就会变少，所以那个 2000 万只是个估算值，面试答出这个数就行，但要知道实际会根据数据特征波动。

![image-20260302130537053](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260302130537053.png)

### **二级索引的三层 B+ 树能存多少数据?**

二级索引的叶子节点存的是主键值而不是完整行数据。假设主键是 bigint，二级索引也是 bigint 类型，叶子节点存的就是8字节的主键 + 8字节的二级索引值，一个叶子节点能存16KB / 16B ≈ 1000 条。三层二级索引能存 1170 x 1170 x 1000 ≈ 13.5 亿条。所以二级索引比主键索引能支撑的数据量大得多，但查数据要回表。

### **表数据量超过 2000 万就要分库分表吗?**

不一定，2000 万只是个参考值。关键看查询性能能不能满足业务需求。如果索引设计得好，查询都能走索引，几千万数据单表也没问题。真正需要分库分表的信号是:慢査询明显增多、单表写入 OPS 顶不住、磁盘空间告急。分库分表引入的复杂度很高，能不分就不分。

### **`innodb_page_size` 什么时候需要调整?**

绝大多数场景保持默认 16KB 就行。需要调整的情况比较少：

- 如果行数据特别小，比如只有几十字节的监控指标表,可以考虑调成 4KB 或 8KB，提高内存利用率；
- 如果行数据特别大，比如宽表场景，可以考虑调成 32KB。

但这个参数只能在初始化数据库时设置，一旦设定就不能改了，所以要慎重。

## MySQL中B+树查询数据的全过程是什么样的？

B+树查询数据分两个阶段：先从根节点往下定位到叶子节点，再在叶子节点内部定位到具体的数据行。

- 第一阶段是树的垂直查找。从根节点开始，把査询的键值跟节点中存储的索引键值做比较，用二分法确定落在哪个区间，然后顺着指针往下走到子节点。这个过程一直重复，直到到达叶子节点。

- 第二阶段是页内查找。叶子节点是一个 16KB 的数据页，里面存了很多条记录。InnoDB 用页目录来加速查找，页目录把记录分成若干个组，每个槽指向一个组的最大记录。先用二分法在页目录里定位到记录所在的组，再沿着组内的单向链表遍历找到目标记录。

整个过程就是:根节点 → 中间节点 → 叶子节点 → 页目录二分 → 组内链表遍历。

![image-20260302132342805](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260302132342805.png)

### **叶子节点的内部结构**

叶子节点不是简单地把记录堆在一起，内部有精心设计的结构。

一个 16KB 的数据页大概长这样：

1）文件头和页头：记录页的基本信息，比如页号、页类型、上一页和下一页的指针。叶子节点之间通过双向链表串起来，范围查询的时候可以沿着链表往后扫。

2）用户记录区：实际存储数据行的地方。每条记录按主键顺序排列，记录之间用单向链表串联。

3）页目录：这是加速査找的关键。lnnoDB 把记录分成若干组，每组 4-8 条记录，页目录里的每个槽指向对应组的最大记录。查找时先对槽做二分，快速缩小范围，再在组内遍历链表。

4）文件尾：用于校验页的完整性，存了 checksum。

![image-20260302132524813](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260302132524813.png)

### **页目录二分查找的细节**

数据从根节点找起，根据比较数据键值与节点中存储的索引键值（非叶子节点也有页目录，也能用二分查找，详细看下面叶子节点的分析），确定数据落在哪个区间，从而确定分支，从上到下最终定位到叶子节点。

![image-20260302133421687](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260302133421687.png)

定位到叶子节点后，因为一片叶子默认有 16KB 大小，所以理论上可以存多条记录。叶子节点的实际构造如下图所示

<img src="MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260302134154672.png" alt="image-20260302134154672" style="zoom:50%;" />

从上图可以知晓，叶子节点有页目录结构（非叶子节点也有，当前拿叶子节点分析，结构是一样的）它其实就是一个索引，通过它可以快速找到记录。

页目录分为了多个槽，每个槽都指向对应一个分组内的最大记录，每个分组内都会包含若干条记录。

通过二分查询，利用槽就能直接定位到记录所在的组，从而就能获取到对应的记录。

举个例子，现在有 5 个槽，如果想查找主键为 3 的记录，此时的流程是：

1）通过二分得到槽的中间位置，low=0，high=4，(0 + 4) / 2 = 2

2）通过槽定位到第二个分组中的主键为 4 的记录，4大于3，low = 0 不变，high = 2

3）继续二分(0 + 2) / 2 = 1；槽1中主键2小于3，low = 1，high = 2

4）此时 high - low =1，可以确定值在 high 即槽 2 中，但是槽 2 只能定位到主键为 4 的记录，又因为槽之间是挨着的，所以可以得到槽1的位置，从槽 1入手拿到，主键 2 的记录，然后因为记录是通过单向链表串起来的，往下遍历即可定位到主键 3 的记录。

以上就是利用二分查询的定位流程。通过槽可找到对应记录所在的组，或能直接定位到记录，或还需通过链表遍历找到对应的数据。

实际上，每个分组的记录数是有规定的，图中做了省略只画了两条，InnoDB规定:

- 第一个分组只有一条记录
- 中间的分组 4-8 条记录
- 最后一个分组 1-8 条记录

因此不必担心遍历很长的链表导致性能问题。

这题的重点是先简单提下从根节点遍历到子节点的过程，然后提到每页节点默认大小为 16KB，所以理论上能存储很多记录，从而引出页目录，再通过二分查找才能对应记录。

### **Buffer Pool 的作用**

实际查询时不是每次都从磁盘读，InnoDB 有个 Buffer Pool 会缓存热点数据页。查询流程实际是：

1）先在 Buffer Pool 里找目标页，命中就直接用，不用走磁盘
2）没命中就从磁盘读页到 Buffer Pool，再返回数据
3）根节点和热点的中间节点基本常驻 Buffer Pool，大部分査询只需要 1 次磁盘 I/O 读叶子节点

所以说 B+ 树査询只需要 3次 I/O 是理论上限，实际上因为 Buffer Pool 的存在，平均 I/O 次数要低得多

### **什么是“刷脏页”？**

**脏页（Dirty Page）是指在内存中被修改过，但还没有同步到磁盘上的数据页。**

为了性能，MySQL 修改数据时是先改内存（Buffer Pool），并记录日志（Redo Log），而不是直接写磁盘（磁盘太慢）。

- **过程：**后台线程会定期把内存里的修改后的页写回磁盘，这个动作叫**刷脏（Flushing）**。
- **页大小的影响：**如果你改了页里的 1 字节数据，刷脏时也要把整个 16KB（或 64KB）的页写回磁盘。
  - **写放大：**页越大，为了改一点点数据而必须写入磁盘的物理字节数就越多，对磁盘带宽压力越大。

## UUID可以用来做主键吗？

**优点：**

全局唯一性：理论上重复概率极低

安全性：相比自增ID，不会暴露数据量信息

**但是也存在问题：**

UUID如果以二进制存储，占用16字节或以字符串形式存储就占36字节，占用的存储空间大，这在大数据量的表中会对存储和索引的性能产生一定影响。

更重要的一点是，数据是由UUID构建的B+树存储的，树的内部储存的数据是已经排好序的，但是新数据的UUID是随机生成的无序的，所以索引可能会定位到一个已经满了的页（默认一个页16KB大小），这种情况下就会发生页分裂，大量随机的插入就整个容易导致整个树索引的频繁裂变，增加了IO开销，从而降低了查询和写入的性能。

## 什么是预读机制？

虽然 SSD 随机读很强，但 MySQL 依然保留了**预读机制**。如果你连续读取了同一个区的多个页，InnoDB 会认为你正在进行顺序扫描，它会提前把相邻的页加载进内存。这说明即便硬件变了，**“能顺序就别随机”**依然是程序员刻在骨子里的优化本能。

### **MySQL 的页是随机分布的吗？**

**答案是：在宏观上是随机的，但在微观上是“努力趋向顺序”的。**

如果 MySQL 的页完全随机分布在磁盘到处，那预读确实没意义了。为了解决这个问题，InnoDB 引入了一个中层结构：**区（Extent）**。

- **页（Page）：** 最小单位，16KB。
- **区（Extent）：** 连续的 **64 个页**，大小正好是 **1MB**。
- **段（Segment）：** 由多个区组成（如数据段、索引段）。

**InnoDB 的策略是：** 当它为表分配空间时，不是一页一页申请，而是**按“区”申请**。在一个“区”内部，这 64 个页在物理磁盘上是**尽量连续排列**的。

> **逻辑与物理的统一：** 虽然 B+ 树叶子节点是用指针（链表）连接的，但 InnoDB 会尽量让逻辑上相邻的页在物理上也掉进同一个“区”里。这样当你沿着链表读下一页时，磁头（或 SSD 控制器）其实是在读物理上相邻的数据。

**预读（Read-Ahead）到底在读什么？**

当 InnoDB 发现你连续读取了一个“区”里超过一定数量（默认 56 个）的页时，它会触发**线性预读**：它猜测你马上要读这个区剩下的页了，于是干脆把整个区（1MB）剩下的页一次性加载进内存。

## count(*)、count(1)、count(字段名)有什么区别？

三者都是统计行数的聚合函数，核心区别在于 对 NULL 值的处理方式不同。

count(*)和 count(1)会统计所有行，包含 NULL值的行；count(字段名)只统计该字段不为 NULL 的行数。

```sql
-- 假设 user 表有 100 行，其中 email 字段有 20 行是 NULL
SELECT count(*)    FROM user;  -- 返回 100
SELECT count(1)    FROM user;  -- 返回 100
SELECT count(email) FROM user; -- 返回 80
```

**性能上，count(*) 和 count(1)效率完全一样**

`count(字段名)`如果字段没索引就是全表扫描，还要额外判断是否为 NULL，所以一般比前两者慢一点。但如果字段是主键或有索引，差距就不大了。

![image-20260302201148282](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260302201148282.png)

### **为什么MyISAM的count(*)特别快**


MyISAM 引擎只支持表锁，对表的修改操作是串行的，所以它能维护一个精确的 行数计数器。执行不带 WHERE 条件的count(*)时，直接返回这个计数器的值，O(1)复杂度，几乎是瞬间返回。

```sql
-- MyISAM 表，不带 WHERE 条件
SELECT count(*) FROM myisam_table;  -- 直接返回维护好的行数，极快
SELECT count(*) FROM myisam_table WHERE status = 1;  -- 带条件就要扫描了
```

### **InnoDB 的count 优化策略**

InnoDB 支持行锁和 MVCC，同一时刻不同事务看到的数据可能不同，没办法像 MyISAM 那样维护一个全局计数器。但 InnoDB 也做了优化：

1）优先选择最小的索引扫描。主键索引是聚簇索引，叶子节点存的是完整行数据，体积大；二级索引叶子节点只存主键值，体积小得多。执行 count(*) 时，优化器会选择占用空间最小的二级索引来扫描，减少 I/O 开销。

2）MySQL8.0.17 之后，对InnoDB 的 count(*) 做了并行扫描优化，多线程同时扫不同数据页，速度提升明显。

```sql
-- 查看 MySQL 是否用了并行扫描
EXPLAIN SELECT count(*) FROM large_table;
-- Extra 列可能出现 Parallel scan
```

![image-20260302201949054](MySQL%E5%85%AB%E8%82%A1%E6%96%87.assets/image-20260302201949054.png)

### **如果要统计一张 5000 万行的订单表有多少条记录，直接count(*)太慢，你怎么优化?**

首先看业务对精确度的要求

- 如果允许一定误差，直接用 `SHOW TABLE STATUS LIKE 'user';` 看 Rows 列，拿估算值，毫秒级返回。
- 如果要精确值又要快，就得用缓存方案，在 Redis 里维护一个计数器，每次订单增删时同步更新，读的时候直接査 Redis。要注意处理好缓存和数据库的一致性问题，比如用事务消息或者定期校对。

## char和varchar有什么区别？

最核心的区别就是 CHAR 定长，VARCHAR 变长。

- CHAR(10)不管你存几个字符，都固定占 10 个字符的空间，不够的用空格填充。
- VARCHAR(10)存多少占多少，另外再花1~2 个字节记录实际长度。

```sql
CREATE TABLE demo (
    c1 CHAR(10),
    c2 VARCHAR(10)
);

INSERT INTO demo VALUES ('abc', 'abc');

-- CHAR: 存储时填充空格变成 'abc       '，占 10 个字符空间
-- VARCHAR: 存储 'abc' + 1 字节长度信息，实际占 4 字节
```

性能上 CHAR 理论上快一点点，因为定长不需要额外计算长度，但这点差距在实际业务中可以忽略。选型原则很简单：固定长度的短字符串用 CHAR，比如 MD5 摘要、国家代码；其他场景一律用 VARCHAR。

**VARCHAR 支持的最大长度**

MySQL 单行最大 65535 字节，所以 VARCHAR 的理论上限就是这个数，减去必要开销：

1）2 字节存长度信息(超过 255 字节时需要 2 字节)

2）如果允许 NULL，还要1字节存 NULL 标记

所以 NOT NULL的 VARCHAR 最大 65533 字节，允许 NULL 则是 65532 字节，

**CHAR 读取时会自动去掉尾部空格**

CHAR 存储时会用空格填充到定长，读取时 MySQL 会自动去掉尾部空格。这可能导致意想不到的问题

```sql
CREATE TABLE t (c CHAR(5));
INSERT INTO t VALUES ('abc  ');  -- 故意存两个空格
SELECT CONCAT('[', c, ']') FROM t;
-- 结果是 [abc]，尾部空格被去掉了
```

如果业务真的需要保留尾部空格，只能用 VARCHAR
